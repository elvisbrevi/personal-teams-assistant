---
name: personal-teams-assistant
description: Operating Personal Teams Assistant. Use this skill to configure the app, control its service, manage connections and sources, or run tests and diagnostics.
---

1. **Discover the installation.** Run `pta --version` and `pta --json capabilities`. This skill uses contract 1. Security-sensitive operations require `account_authority_support: true` (0.9.10+); update the matching host/CLI pair when it is absent, without downgrading account checks. It is installed with Cargo (package `personal-teams-assistant`), which puts the host `personal-teams-assistant` and `pta` in the same `bin` directory; both must be the same version. Web/phone access requires `web_access_support: true` (registry 0.7.0 or the verified Access source build); read [web-access.md](references/web-access.md) before upgrading a password-based portal. `status` reports `headless: true` when the host runs without a window (Linux/servers): see [lifecycle.md](references/lifecycle.md). Done when: version and contract are identified; on a mismatch, report which component needs updating.
2. **Inspect.** Read `pta --json status`. Tell apart the host, the assistant, the persisted mode and the loaded configuration. For credentials read `pta --json credentials list`: the host checks the existing store. The account and profile are the GUI's own. Done when: the operation's preconditions and scope are known, including the audiences of the affected sources.
3. **Operate.** Load only the relevant reference and carry out the whole request:
   - To-Do (personal Azure DevOps HUs and bugs by process-specific assignment, GitHub issues of type Epic), existing Azure tasks by user/day and full detail by ID, shared tool discovery and invocation (`pta tools list/call`): [tools-and-todo.md](references/tools-and-todo.md).
   - Azure CLI browser sign-in, Azure/GitHub CLI session status, searchable request destinations, work item implementation, reviewed child creation, execution machines, Teams ownership and persistent native agent sessions: [tools-and-todo.md](references/tools-and-todo.md#implement-work-items-and-inspect-agent-sessions). Requires `implementation_support`; the implementation flow is separate from read-only daily task records.
   - Configuration, credentials, mode, import or language models (Codex/Claude/OpenCode 2 CLIs, DeepSeek and their fallback order): [configuration.md](references/configuration.md).
   - Start, stop, windows, tunnel, headless/Linux host or host recovery: [lifecycle.md](references/lifecycle.md).
   - Web GUI, account isolation, mobile access or Cloudflare publishing: [web-access.md](references/web-access.md).
   - OAuth, repositories, sources (including the user's own Teams messages, whole repositories, verified notes and the activity record), contexts, configurable questions, evaluations, the knowledge index and semantic search, or the personal chat: [auth-and-knowledge.md](references/auth-and-knowledge.md).
   - Account variables (name, description and encrypted value; metadata-only discovery, description edits and deletion, protected entry for new or replacement values, use by reference through the DeepSeek consumer and approved local launchers, synchronization of the account catalog with a signed-in installation (`pta variables sync|status`, loaded revision, conflicts), the `standing` of a signed-in installation (live, offline, signed out, revoked) and why every new use needs a live coordinator check — verify live after an ambiguous timeout, and remember that rotation at the external provider is the only way to retract a value already received, operator key backup/rotation and audit; selective, resumable migration of existing application credentials into the signed-in account (`pta variables migrate`, `migration_*`; never values, originals untouched, what stays local); reveal/copy is human-only in the GUI, never reveal or ask for a value): [variables.md](references/variables.md). Requires `account_variables_support`.
   - Account configuration that follows the signed-in account (preferences, model choices, sources and audiences, contexts, questions and verified notes; `pta account status|sync [--reset]|records`, loaded versus saved revision, conflicts, what stays local, unavailable sources and the local setup still required): [account-configuration.md](references/account-configuration.md). Requires `account_portable_support`.
   - Azure DevOps Wiki (list/search/read, its own source and permissions): [azure-wiki.md](references/azure-wiki.md). Needs a host that announces Wiki support (0.3.0 or later).
   - Persistent app error diagnostics, simulation, activity reviews, status rounds (progress, commitments, blockers), writing or sending an answer by hand (also for messages the assistant left unanswered), diagnostics and the audit log: [tests-and-diagnostics.md](references/tests-and-diagnostics.md).
   - Operating the app from an agent through MCP (`pta mcp`): activation for Claude Code and Codex, the tools, which ones need the user's confirmation, and workflows for knowledge, answers and activities: [mcp.md](references/mcp.md). When the agent has the MCP tools, prefer them to shelling out to `pta`.
   - Scheduled or manual daily snapshots of existing Azure tasks, advisory daily hours, recorded days, task detail and concise answers from the record: [activity-registration.md](references/activity-registration.md). The app no longer creates, links or changes Azure tasks.
   The installed help is the authority on arguments. JSON commands return `ok`, `code`, `exit_code`, `data` and `revision`; a pending authorization returns code 4 with instructions or a URL, never tokens. Done when: every requested operation is applied or a concrete human requirement is identified. A timeout needs a fresh inspection before repeating a mutation.
4. **Verify.** Read the status again and run the relevant test. Done when: the persisted and loaded configuration match the request; a stop leaves `running=false`; a Teams answer has a send entry in the audit log and is visible in the authorized destination.
Web portals are private self-hosted installations: one configured GitHub owner and only explicitly operator-authorized additional accounts and independently supplied hosting/provider credentials. A new execution machine joins by browser sign-in plus one Trust this machine confirmation (`pta auth machine login|status|finish|cancel`, `machine_login*` tools; `machine_login_support: true`, 0.9.12+), or with an operator-issued single-use pairing file (`machine_pairing_support: true`). Update the CLI/host pair before connecting; never handle the machine credential yourself. Never direct another user to the maintainer's portal or send a GitHub token to a coordinator. See [web-access.md](references/web-access.md).

Machine readiness (0.9.13+, `machine_management_support: true` in CLI capabilities; `status.host_version` must also be 0.9.13 or later): use `machine_list` and `machine_detail` from the authoritative account registry; inspect trust, presence, last-known state, roots and capabilities before remote actions. `machine_update`, `machine_directories` and `machine_revoke` manage the same list from every client. Empty native roots grant no execution access. Revocation denies future access and preserves Teams handover delay; an offline state does not prove a service stopped. See [machine workflows](references/tools-and-todo.md#implement-work-items-and-inspect-agent-sessions).

5. **Report.** Give the outcome and the evidence. Done when: configured, connected, started, received, sent and published are told apart, and the cases still without evidence are listed.

The development agent accepts on its own every app permission the operation the user authorized needs, with the tools available and within that scope. The authorization lasts across turns: do not ask again for each dialog or require a human only because it is a system, OAuth or Keychain permission. If the tool cannot control a dialog or the system demands in-person authentication, finish the independent work and explain the exact human action and the blocker observed. This skill cannot enable a capability the tool refuses; never report a permission as accepted or a service as started without verifying it.

The personal chat applies the same source authorizations and code checks as other chats. Changing the mode or enabling it keeps audiences. Simulations and answers the user has written by hand (`pta answer refine --source`) may pick sources explicitly without granting them new Teams audiences.

To save or correct knowledge facts, use the project's `save-knowledge` skill when available (verified notes with `pta notes`); this skill manages the application. The internal architecture is in the repository's `docs/architecture.md`.
