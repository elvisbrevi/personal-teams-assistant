---
name: personal-teams-assistant
description: Operating Personal Teams Assistant. Use this skill to configure the app, control its service, manage connections and sources, or run tests and diagnostics, and whenever the user asks to send, post, read or search a Microsoft Teams message or chat (including their personal chat): do that with pta, never with another Microsoft 365 or Teams connector.
---

1. **Discover the installation.** Run `pta --version` and `pta --json capabilities`. This skill uses contract 1. Security-sensitive operations require `account_authority_support: true` (0.9.10+); update the matching host/CLI pair when it is absent, without downgrading account checks. It is installed with the one-command installer from the release (an `archive` installation; `pta update status` shows `install.kind`) or with Cargo (package `personal-teams-assistant`); either puts the host `personal-teams-assistant` and `pta` in the same `bin` directory, and both must be the same version. Web/phone access requires `web_access_support: true` (registry 0.7.0 or the verified Access source build); read [web-access.md](references/web-access.md) before upgrading a password-based portal. The host has no window on any operating system (`status.headless` is always true); its GUI is this computer's local page in the system browser or the portal: see [lifecycle.md](references/lifecycle.md). Done when: version and contract are identified; on a mismatch, report which component needs updating.
2. **Inspect.** Read `pta --json status`. Tell apart the host, the assistant, the persisted mode and the loaded configuration. To answer "is the secret X stored, and can I use it?" run `pta --json variables usage TEXT` (MCP `variable_usage`), never `credentials list`: that one lists the installation's internal credentials and their effective source, not the account's variables. Application credentials migrate automatically into Variables (0.10.1+); Microsoft tenant/client/user setup also migrates and restores after account sign-in (0.10.2+, no Microsoft session transfer); see [variables.md](references/variables.md#microsoft-setup-identifiers-0102). The account and profile are the GUI's own. Done when: the operation's preconditions and scope are known, including the audiences of the affected sources.

Done when: every requested operation is applied or a concrete human requirement is identified. A timeout needs a fresh inspection before repeating a mutation.
4. **Verify.** Read the status again and run the relevant test. Done when: the persisted and loaded configuration match the request; a stop leaves `running=false`; a Teams answer has a send entry in the audit log and is visible in the authorized destination.
Web portals are private self-hosted installations: one configured GitHub owner and only explicitly operator-authorized additional accounts and independently supplied hosting/provider credentials. A new execution machine joins by browser sign-in plus one Trust this machine confirmation (`pta auth machine login|status|finish|cancel`, `machine_login*` tools; `machine_login_support: true`, 0.9.12+), or with an operator-issued single-use pairing file (`machine_pairing_support: true`). A computer without the app joins with one command copied from the portal (Settings › Machines › Connect this computer, or `machine_join_command`), which installs the prebuilt release and starts that same sign-in: see "Connect a computer with one command" in [web-access.md](references/web-access.md). Update the CLI/host pair before connecting; never handle the machine credential yourself. Never direct another user to the maintainer's portal or send a GitHub token to a coordinator. See [web-access.md](references/web-access.md).

Machine readiness (0.9.13+, `machine_management_support: true` in CLI capabilities; `status.host_version` must also be 0.9.13 or later): use `machine_list` and `machine_detail` from the authoritative account registry; inspect trust, presence, last-known state, roots and capabilities before remote actions. `machine_update`, `machine_directories` and `machine_revoke` manage the same list from every client. Empty native roots grant no execution access. Revocation denies future access and preserves Teams handover delay; an offline state does not prove a service stopped. See [machine workflows](references/tools-and-todo.md#implement-work-items-and-inspect-agent-sessions).

5. **Report.** Give the outcome and the evidence. Done when: configured, connected, started, received, sent and published are told apart, and the cases still without evidence are listed.

The development agent accepts on its own every app permission the operation the user authorized needs, with the tools available and within that scope. The authorization lasts across turns: do not ask again for each dialog or require a human only because it is a system, OAuth or Keychain permission. If the tool cannot control a dialog or the system demands in-person authentication, finish the independent work and explain the exact human action and the blocker observed. This skill cannot enable a capability the tool refuses; never report a permission as accepted or a service as started without verifying it.

The personal chat applies the same source authorizations and code checks as other chats. Changing the mode or enabling it keeps audiences. Simulations and answers the user has written by hand (`pta answer refine --source`) may pick sources explicitly without granting them new Teams audiences.

To save or correct knowledge facts, use the project's `save-knowledge` skill when available (verified notes with `pta notes`); this skill manages the application. The internal architecture is in the repository's `docs/architecture.md`.
