Azure CLI: `pta auth azure login` returns the Microsoft device verification URL and user code. Complete sign-in in the browser and use `pta auth azure finish --wait`; `status` reads the Azure DevOps session and `cancel` stops a pending login. Home offers the same flow from an unavailable Azure CLI status row and updates automatically on completion.

Microsoft: `pta auth microsoft login --no-browser` returns a PKCE URL; authorize it in the browser and check `pta auth microsoft finish --wait`. Without `--no-browser` the browser opens, except in non-interactive mode. `cancel` cancels the wait; `logout` stops the service and deletes local tokens. GitHub: `pta auth github login CLIENT_ID` returns a device code and URL; then use `pta auth github finish --wait`. Each wait lasts at most 600 seconds; pending is exit 4. A local logout does not revoke the remote authorization.

`pta github repos` lists the authorized catalog. `pta repos clone OWNER/REPO ALIAS` adds a managed checkout; `sync ALIAS` requires a clean checkout and a fast-forward. Local repositories are added with `repos add ALIAS PATH`, edited with `edit` and removed with `remove`. Removing keeps the files and fails if it would leave a dependent source invalid; change those sources first.

`sources add` reads a Resource JSON on stdin, initially disabled, without audiences and without external processing. `sources edit ID` replaces the whole Resource. `sources audience ID` reads a JSON object with allowed_conversations, allowed_senders and/or external_processing; the permission requested must be explicit. `sources enable ID` enables that source. Identify each type and its limits with `sources show ID` and the map; the same allowlists apply to files, URLs and tools.

Azure task access is read-only. Existing read credentials and catalogs are reused for daily task snapshots and detail. Legacy `link_secret_ref` fields and stored write credentials remain compatible but cannot enable creation or linking; no new write credential is needed.

**Azure DevOps catalog.** The activity (`azure_devops_status`) and Wiki (`azure_devops_wiki`) tools read the organizations, projects and the user's author email from a catalog. Write it in the map itself, so no knowledge repository is needed: `"catalog":[{"organization":"https://dev.azure.com/ORG/","projects":["*"],"author_email":"me@example.com"}]` (at most five organizations and ten projects; `["*"]` = the projects of the teams the user belongs to). Older maps point to a TOML file instead (`"repository":"ALIAS","path":"azure-devops.toml"`, with `[[sources]]` entries of the same fields); a tool has one or the other, never both. To move a file catalog into the map, `sources show ID`, replace `repository` and `path` with `catalog` and save it with `sources edit ID`; then the repository can be removed if nothing else uses it.

**Whole repositories.** A repository can be a source of its own, with its description: `{"id":"handbook","description":"Runbooks and procedures of the payments team","topics":[],"enabled":false,"external_processing":false,"allowed_conversations":[],"allowed_senders":[],"kind":"repository","repository":"ALIAS"}`. Each answer that may read it searches it by relevance: the app keeps its Markdown and text files (md, txt, rst, adoc, json, toml, yaml; at most 5000 files of 1 MB, skipping hidden folders, `node_modules`, `target`, `vendor`, `dist`, `build` and `bin`) as sections in the knowledge index (`knowledge-index.db` in the data directory) and gives the model the eight that best match the request (trace step `index`, audit tool `search_repository`). The index compares file sizes and times on each read, so an edited checkout is up to date without a restart; `pta index refresh [ID]` does it at once and `pta index status` shows what each source holds. The GUI's Repositories tab turns a checkout into a source with «Use as a source». Recaps, status rounds and activity reviews do not search repositories or notes.

**Verified notes.** Facts the user verified (`pta notes add|edit ID|remove ID|list|search`, the Knowledge › Notes tab, or the `save-knowledge` skill) are searched like a repository through the notes source: `{"id":"notes","description":"Facts I verified","topics":[],"enabled":false,"external_processing":false,"allowed_conversations":[],"allowed_senders":[],"kind":"notes"}`, optionally with `"contexts":["cobros"]` to keep only those contexts' notes and the general ones. A note has `title`, `text`, `contexts`, `keywords`, `origin` (`user`, `agent`, `answer`, `import`) and an optional `reference`; one with sensitive data (secrets, emails, phone numbers, national IDs) is refused. Notes are data, not profile: saving one needs no restart or revision.

**Contexts.** A context is a subject (`pta contexts add|edit ID|remove ID|list|show ID`, or Knowledge › Contexts): `{"id":"cobros","name":"Cobros","description":"…","keywords":["conciliación bancaria","factura"],"sources":["wiki-cobros","handbook","notes"],"instructions":"…"}`. A request that names it — one of its keywords or its name, as whole words, ignoring case and accents; the most matches win — reads only that context's sources among those the conversation may read (documents, and the tools the general routing chooses from), the notes of that context and the general ones, and passes its instructions to the model (`audit.context`, trace step `context`). It never authorizes a source, does not change recaps, status rounds or reviews, and sources the user chose by hand are read as they are. To split Wikis by subject, add one Wiki source per wiki (`wiki_ids`) and list each in its context.

**Questions.** Knowledge › Questions (`pta questions list|show ID|add|edit ID|remove ID`) configures question text, selected source IDs and associated requests. A new profile starts with “What did you do today?” using the activity record. Equivalent wording is recognized by meaning; the actual requested dates remain parameters. Unknown messages stay unanswered for review; `pta questions associate RESOURCE` takes `question_id` (existing) or `text` (new), plus `sources`, saving the message as an example in Questions without sending. Every selected source must still be enabled, allowed external processing and authorized for that conversation. Legacy cases remain readable but do not govern loaded profiles. Good/bad ratings automatically guide later answers within the same question and authorized source set; old facts are never reused.

**Exact URLs.** Knowledge › Sources can add 1–10 public HTTPS URLs as `kind="urls"`, `urls=[...]`. For protected Azure DevOps Wiki pages choose an existing Wiki connection; the new source copies its catalog/credential reference and sets nonempty `tool.page_urls`, reading those exact pages through the native API without Search or repository discovery. It starts disabled, with no audience/external processing. Enable and authorize it, then choose it for the question.

**People.** How the user addresses each person (`pta people list|show ID|add|edit ID|remove ID`, Knowledge › People): `{"id":"ana","name":"Ana Pérez","senders":["GRAPH-USER-ID"],"aliases":["Ana P."],"address":"Informal, by first name, two sentences","notes":"Leads the payments team"}`. When the assistant answers that person (by Teams ID, or by name or another name), the profile guides the form of address, tone and length; it never reaches another person's answer, the personal chat or the evidence. A message's sender ID and name are in `pta audit show RESOURCE --content` (`sender_id`, `sender_name`), and the GUI adds a person from a message.

**Semantic search.** Full-text search (BM25, accents folded, word stems) always works. With an OpenAI-compatible embeddings endpoint, sections are also ranked by meaning and both rankings are fused: `pta config set knowledge_index '{"embeddings":{"url":"https://api.openai.com/v1","model":"text-embedding-3-small","secret_ref":"secret://knowledge/embeddings"}}'`, map the reference in `[secrets]` (`pta config set secrets '{…,"secret://knowledge/embeddings":"OPENAI_API_KEY"}'`) and store the key with `pta credentials set OPENAI_API_KEY`; a local server (Ollama, `http://127.0.0.1:11434/v1`) needs no credential. The searched sections (redacted) and the request are sent to that endpoint; up to 256 sections get their vector per search, and changing the model drops the old vectors. Any failure leaves full-text search alone. The web portal accepts only HTTPS endpoints.

**Activity record.** What the Activities section recorded — existing Azure tasks saved by day, with verified links, descriptions, optional HU and daily hours, plus legacy records — is a source of its own: `{"id":"activity-record","description":"Existing tasks saved by day: links, HU and hours","topics":["activity","tasks"],"enabled":false,"external_processing":false,"allowed_conversations":[],"allowed_senders":[],"kind":"tool","tool":{"type":"activity_record"}}` (the GUI's Knowledge section adds it with «Add activity record»). It is read locally, with no credential, when it is authorized for the conversation: a question about what the user did on a day or period is answered from it alone, status rounds and activity reviews add it, the model may choose it for other questions about the user's work, and the user may choose it on its own when answering a message from the app (the days the request names, or the last two weeks). Registered tasks show wherever the record is authorized (they are existing tasks read from Azure DevOps); work not registered yet that came from Wiki pages or Teams messages shows only where those sources are authorized too. In a map without this source, the record follows the Azure DevOps activity source's authorization, as before.

The user's own Teams messages are a source of their own, used to review their activity ("what work did I do that is not registered?"): `{"id":"teams-activity","description":"My own messages in Teams chats, to review the work I did","topics":["teams","activity"],"enabled":false,"external_processing":false,"allowed_conversations":[],"allowed_senders":[],"kind":"tool","tool":{"type":"teams_messages"}}`. It reads, with the Microsoft session already granted (`Chat.Read`, no new scope), only the messages the user wrote in the window, in chats the profile may read (`discover_all_chats` or `allowed_chats`), leaving the personal chat out. Those messages reach the language models only after `external_processing` is authorized; authorize it for the personal chat only (`{"allowed_conversations":["chats/48:notes"],"external_processing":true}`) unless the user asks otherwise. The local test chat (`pta chat`) has no Microsoft session, so there it reports the source as unread.

`pta self-chat enable [CHAT_ID]` validates the personal conversation against the Graph account (members in normal chats, delegated scope and authors in notes), persists the activation limit and keeps audiences. Without an ID it tries discovery. `self-chat status` shows the configuration and the polling cursor. Authorize only the chosen sources for the exact audience `chats/CHAT_ID`, keeping earlier audiences. `self-chat disable` applies the deactivation.

Outputs in the personal chat carry a PTA link with a durable identifier, to recognize an answer even if Graph loses the send result. The test needs a new human question in Teams and a send entry in the audit log; check there are no loops after a restart and with a human text identical to an earlier answer. A failed discovery or membership check never authorizes a global exception for own messages.

After an ambiguous output without a recoverable marker, `self-chat status` lists pending_outputs with nonce and date. Once the person identifies their message in Teams/Graph, `pta self-chat reconcile NONCE MESSAGE_ID` records the explicit match; it validates account, conversation and date and resends nothing. The agent needs the person to identify that output if Graph did not keep the marker.

**Report tasks.** Registration reminders such as «registra tus horas» take priority over an unregistered-work footer. This case reads only the authorized local activity record, for the dates requested or today in the registration timezone by default. It includes saved tasks and empty-day snapshots plus legacy `done` and `already_registered` entries, excluding pending, uncertain and dismissed work. It never queries Teams messages, Wiki pages or Azure DevOps activity for evidence, and never creates tasks. If no confirmed registrations exist, it says so without claiming hours were logged. `report_tasks` supports enabled, keywords and instructions; its source cannot be changed to another kind.
