`pta start`, `pta stop` and `pta restart` manage the assistant; `pta status` (without `--json`) summarizes whether the host and the assistant run, the mode, Teams and the models. `pta help` describes every command.

**Update.** From the application or `pta update` (below) for every supported installation: one made with the one-command installer (`install.kind: archive` in `pta update status`; preparing downloads the release's archive for its target and checks its published SHA-256, no Rust needed; running the install command again also upgrades it), `cargo install` or `cargo binstall`; by hand, `cargo install personal-teams-assistant --locked` (the same command on macOS, Windows and Linux, with no GTK or WebKit packages; or `cargo binstall personal-teams-assistant` for the prebuilt archive, in seconds; quit the host first on Windows, where a running program cannot be replaced) replaces the binaries (if the old `personal-teams-desktop` package is still installed, first `cargo uninstall personal-teams-desktop`: both install `pta`), but the previous host keeps running until the new version is first used: the first `pta` or launching `personal-teams-assistant` stops it (assistant and tunnel). If the assistant was running, the terminal asks whether to keep it running with the new version; with `--json`, `--non-interactive` or without a terminal the previous state is kept (it starts again). Verify afterwards with `pta status`. A host started from another path is never stopped this way, except the `personal-teams-desktop` host of the old package in the same folder or a host whose executable was already uninstalled. Repeated starts and stops are safe. The host has no window: it runs in the background, with or without the service started. Launching `personal-teams-assistant` starts it and opens this computer's GUI in the system browser (the [local page](#local-page)); launching it again, `pta app open` or `pta activity open` (the activities are a tab of that GUI) open the running host's page. `pta` starts the host with `--host` and never opens the page. `pta app quit` ends the host after stopping the service and its tunnel. A short CLI call may end while the host or service it asked for keeps running.

`pta --json status` tells the persisted and loaded configuration apart; an older version without a control channel must be closed by hand before starting the new one. An open listener alone does not prove Teams authorization or reception. Check the subscription health and the audit log too: `pta status` shows `Teams: N active subscription(s)`.

**Prepare an update (this computer only).** `pta update status` shows the `running`, `installed` and `available` versions separately, how this installation was built (features, target, or `prebuilt` for one made with `cargo binstall`, which is prepared by downloading the release's archive instead of compiling) or why it cannot be updated from here, the last check and any prepared update; it makes no network call. `pta update check` reads the newest **stable, not yanked** release of this package from the pinned public registry (crates.io's index; prereleases, yanked and equal or lower versions are ignored). `pta update stage VERSION --confirmed` (MCP `update_stage`, the GUI's Prepare update) builds exactly that version with Cargo (locked dependencies, the installed features and target) into the profile's `maintenance/` directory and verifies the application and `pta` pair; it needs Cargo (and a C toolchain) and runs in the background (`state: staging` with progress in `pta update status`). **Preparing is not installing:** nothing is replaced and the installed version keeps running, so never tell the user they are on the new version until `installed` and `running` say so. For an archive installation preparing downloads exactly that release's archive for the recorded target from this package's GitHub release (the address is fixed in code; only the release host's own redirect is followed) and refuses it, staging nothing, on a size or SHA-256 mismatch, a missing archive for the target (also the minutes before a new release's archives are attached), a truncated download or an archive with paths outside its directory or links; relay the reason. `pta update dismiss VERSION` hides the notice for that release. Only the owner of the computer can check or stage (a portal session, machine credential or another account only sees that the operator manages updates); the registry, crate, directory and command cannot be chosen, the version must be the one the check just offered, and the build runs without any account variable or credential. A failure message (no Cargo, old Rust, no C compiler, no disk space, network) says what to fix; relay it and let the user repeat. Do not install over a prepared build or touch `maintenance/` by hand; the shared server's own timer updates the server independently.

**Unattended updates (this computer only).** `pta update unattended on|off --confirmed` (or the checkbox in Settings › Advanced › Updates on the local page; `install.sh --unattended-updates` / `install.ps1 -UnattendedUpdates` at installation) lets this computer prepare and install newer releases by itself when nothing would be interrupted. It is off unless the person turns it on, applies only to this computer, is never part of the synchronized account configuration and cannot be changed from the portal, a machine credential, a remote agent or any MCP tool: only ask the user to change it, never do it on your own initiative. `pta update status` shows `unattended` (`enabled`, `waiting`, `skipped`, `history` of changes and attempts). With it on, the usual deferral applies (`deferred.unattended: true`), and it also waits while the Microsoft session needs renewal (sign in again with `pta auth microsoft login`, then it proceeds); a release that was rolled back or whose unattended wait was cancelled is not tried again by itself (`unattended.skipped`) until a newer one exists, though the user may still install it. On a Mac whose credentials are in the Keychain it only prepares (`unattended.waiting`): each new version must be allowed in the Keychain, so the user installs it and chooses Always Allow.

**Install a prepared update (this computer only).** `pta update apply VERSION --confirmed` (MCP `update_apply`, the GUI's Install update) installs the prepared version after the user confirmed that exact action: it waits for work in progress (`state: deferred` with fixed reasons; it never interrupts an answer, a send, an implementation, a creation or a migration; `pta update cancel` withdraws the wait), then quits the host, replaces the host and `pta` together, starts the host with its previous launch flags (in the background; the page does not open by itself), restores the assistant only if it was running and checks health. If the new version does not start and report healthy, the previous pair is put back automatically (`apply.state: rolled_back` with the reason); if even that fails, `apply.state: failed` carries the recovery path (reinstall the exact version with `cargo install personal-teams-assistant --version X.Y.Z --locked --force`, or run the install command again with `--version X.Y.Z` for an archive installation; nothing is deleted). An assistant whose Microsoft session already needed renewal does not count against the new version: the update is kept and `apply.notes` say to sign in again. The application restarts, so poll `pta update status` (it reads the update journal while the application is down) until `apply.state` is `success`, `rolled_back` or `failed`; `installed` alone never means done. While an update is applying no `pta` command starts a host: wait and retry. A host whose profile has a current [start-at-login](#start-at-login) entry is stopped with the ordinary quit and started again **through the service manager** (also on rollback), so the manager keeps tracking it. A host started by a hand-written systemd unit with `--headless` (such as the shared server's) is refused (`apply_unsupported`): update it with `cargo install … --locked --force` and restart the unit, or replace the unit with `pta service install`. After `success` read `apply.notes`: the application's own skill copies (installed with `pta skill install`) were refreshed only if unmodified; copies you changed are listed and untouched; agents that keep `pta mcp` running must reconnect to read the new catalog. Never delete `maintenance/`, kill the helper or run `cargo install` for this package while an update is applying; an interrupted update is undone automatically by the next status or host start.

**Windows startup stack overflow (0.9.8).** A host crash with `has overflowed its stack` or Windows exception `0xc00000fd` can prevent `pta app open` even when `pta --version` and `pta doctor --offline` work. From 0.9.9, Windows MSVC builds link only the host with an 8 MiB stack reserve (default commit), so a normal Cargo installation retains the fix without EDITBIN. This addresses the confirmed 1 MiB startup limit; the function consuming that stack is still unidentified. Verify `pta --json status` (`host_running: true`, matching `host_version`), `pta app open` in a desktop session and `pta app quit` followed by launching the host again. Opening the page does not start Teams; keep `running: false` for a startup-only check and do not change credentials.

`pta tunnel configure token`, `pta tunnel configure file PATH` or `pta tunnel configure external` choose a mode. The token is stored as `CLOUDFLARE_TUNNEL_TOKEN` with credentials set, never in arguments. `pta tunnel validate` checks the mode and the local requirements; it does not prove connectivity from the Internet.

The administrative channel uses another loopback port, an instance token in a private file and a profile lock. The Graph tunnel keeps only its configured origin. Changing the configuration validates first; a failed restart requires checking whether it was applied and stopped. After an abrupt crash, the next host recovers the pending configuration transaction; ambiguous Graph sends are never resent.

**Start at login.** <a id="start-at-login"></a>`pta service install --confirmed` (MCP `service_install`, the local page's Settings › Start at login; `service_support: true`) registers this profile's host with the operating system's service manager so it starts when the user logs in, per user and without administrator rights: a LaunchAgent on macOS (`launchctl bootstrap gui/UID`), a systemd user unit on Linux (enabled, not started), a scheduled task at logon on Windows (no console window, no WSL). Exactly one entry per profile, named after a hash of the profile (`pta service status` shows `name`, never a path); repeating the install changes nothing (`changed: false`). The entry starts `personal-teams-assistant --host --service` (plus `--profile-dir` for a profile that is not the standard one): no page opens, and it **never starts the assistant by itself**: after a login the assistant runs only if the person left it running (their last `pta start`/`pta stop`, from any surface) and this computer still holds the Teams selection and lease; otherwise it stays stopped. Its environment is only a fixed `PATH` (macOS and Linux; a task inherits the user's environment) and it holds no account variable or credential; the coding CLIs, `az`, `gh` and `git` are found as when a desktop session starts the host. `pta service status` reports `installed`, `current` (it starts this executable for this profile), `running`, `last_error` (the manager's exit code or result) and, on Linux, `linger`: with lingering off the host runs only while the user is logged in; to keep it running without a session run `loginctl enable-linger`. Without a systemd user manager the install answers `not_ready`. A second start while a host owns the profile exits cleanly. The entry installed from a host `pta` started does not take over that host: it starts at the next login (or the next update). `pta service uninstall --confirmed` removes only the entry install created (an entry with the same name that pta did not write is refused and left alone); a host it runs keeps running until `pta app quit`. Only the owner at this computer can use these; a portal session, a machine credential or a remote agent is refused.

**Servers and systemd.** The host is the same on every operating system (`--headless` and `PTA_HEADLESS` are accepted and ignored; `pta --json status` always shows `headless: true`). `app open` opens the [local page](#local-page) when the host runs in a desktop session and otherwise answers `not_ready` with the next step; `app quit`, SIGTERM or Ctrl-C stop the service and tunnel before exiting. `--start` tries to start the service at launch and keeps the host alive if it fails, to diagnose it. On Linux, credentials are stored with `pta credentials set NAME` in `~/.config/dev.personalteams.assistant/credentials/default/` (0600) or given as `NAME`/`NAME_FILE` in the host's environment. Remote login: `pta auth microsoft login --no-browser`, authorize the URL on any device and paste the `http://localhost:PORT/?code=…` address the browser could not open into `pta auth microsoft finish --redirect 'URL'`. On a personal computer use [start at login](#start-at-login) instead of writing a unit. A unit written by hand, such as the shared server's in `~/.config/systemd/user/pta.service` (`systemctl --user enable --now pta`, with `loginctl enable-linger` so it keeps running without a session), keeps `--headless` in `ExecStart`, which tells `pta update apply` that that unit owns the host and that it updates through it:

```ini
[Unit]
Description=Personal Teams Assistant (headless)
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=%h/.cargo/bin/personal-teams-assistant --headless --start
Restart=on-failure
RestartSec=10

[Install]
WantedBy=default.target
```

**Automatic server updates.** New versions reach crates.io when a version change is merged (the repository's release workflow publishes it after CI passes). A server running the web portal can install each one by itself with the repository's updater (`scripts/vps-update.py` and its systemd user timer, see [delivery](https://github.com/elvisbrevi/personal-teams-assistant/blob/main/docs/delivery.md)): every five minutes it compares `pta --version` with crates.io, waits while an activity review, a task write or a Teams answer is in flight, installs it, restarts the portal service, verifies `pta status` and restores the previous version if the new one is not healthy. `~/.local/state/personal-teams-assistant-update/history.log` records each update, deferral and rollback; `personal-teams-assistant-update --check` tells what it would do. Do not update that server by hand as well.

For a requested product delivery, include a new, unpublished version in `Cargo.toml` and `Cargo.lock` before the pull request. After CI passes and it merges, verify crates.io publication and the server's running version and health. A merge and push, or a successful release workflow that skipped an existing version, do not prove publication or installation.

Never keep two instances of the same account active at once (another computer, the local GUI or a server): they would duplicate answers and cause loops in the personal chat. Leave the other one stopped or in `pta mode observe`.

**Local page.** <a id="local-page"></a>Every host of the installation's own profile (not a portal account's host) serves the same GUI on `127.0.0.1` at a port derived from the profile, for the person at this computer: its only local GUI, with the owner's authority (reveal and copy a value, approve launchers and delivery destinations, account sign-in and Synchronize, allowed roots and local checkouts, update notices, start and stop). Only the host signs a browser in: launching `personal-teams-assistant`, or `pta app open`, hands the system browser an owner-only file that carries a single-use code expiring within a minute (the code never travels in a process argument); the page exchanges it for a browser-session cookie and a key that only that tab keeps, so closing the browser, restarting the host or `pta app quit` ends the session, and a new tab needs `pta app open` again. `pta app open` reports only `opened`, never a link, code or cookie, and nothing else (CLI, MCP, tools, logs, diagnostics) shows one: an agent that runs it cannot use the page, and the local channel it holds is still refused reveal and approval. Without a desktop session (no display, an SSH or service session) it answers `not_ready`: run it in a desktop session on that computer. A second profile on the same computer gets its own address and session. If the page says its sign-in ended, run `pta app open` again. On Linux, a browser installed as a snap or flatpak cannot read the handoff file (it lives under the hidden `~/.config/dev.personalteams.assistant/page-open/`) and shows «file not found» or «access denied»: make a browser that is not sandboxed the default for HTML files (for example `xdg-mime default firefox.desktop text/html` with the distribution's Firefox package) and run `pta app open` again.
