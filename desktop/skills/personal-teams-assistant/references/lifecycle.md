`pta start`, `pta stop` and `pta restart` manage the assistant; `pta status` (without `--json`) summarizes whether the host and the assistant run, the mode, Teams and the models. `pta help` describes every command.

**Update.** `cargo install personal-teams-assistant --locked` (or `cargo binstall personal-teams-assistant` for the prebuilt macOS/Windows archive, in seconds) replaces the binaries (if the old `personal-teams-desktop` package is still installed, first `cargo uninstall personal-teams-desktop`: both install `pta`), but the previous host keeps running until the new version is first used: the first `pta` or opening the app stops it (assistant and tunnel). If the assistant was running, the terminal asks whether to keep it running with the new version; with `--json`, `--non-interactive` or without a terminal the previous state is kept (it starts again); the app shows a notice with «Keep running» / «Leave it stopped». Verify afterwards with `pta status`. A host started from another path is never stopped this way, except the `personal-teams-desktop` host of the old package in the same folder or a host whose executable was already uninstalled. Repeated starts and stops are safe. The host can live hidden without the service started; `pta app open` shows its window, `pta app hide` hides it and `pta app quit` ends the host after stopping the service and its tunnel. A short CLI call may end while the host or service it asked for keeps running.

`pta --json status` tells the persisted and loaded configuration apart; an older version without a control channel must be closed from its GUI before starting the new one. An open listener alone does not prove Teams authorization or reception. Check the subscription health and the audit log too: `pta status` shows `Teams: N active subscription(s)`.

**Prepare an update (this computer only).** `pta update status` shows the `running`, `installed` and `available` versions separately, how this installation was built (features, target) or why it cannot be updated from here, the last check and any prepared update; it makes no network call. `pta update check` reads the newest **stable, not yanked** release of this package from the pinned public registry (crates.io's index; prereleases, yanked and equal or lower versions are ignored). `pta update stage VERSION --confirmed` (MCP `update_stage`, the desktop's Prepare update) builds exactly that version with Cargo (locked dependencies, the installed features and target) into the profile's `maintenance/` directory and verifies the application and `pta` pair; it needs Cargo (and a C toolchain, plus the GTK/WebKit packages for the desktop app) and runs in the background (`state: staging` with progress in `pta update status`). **Preparing is not installing:** nothing is replaced and the installed version keeps running, so never tell the user they are on the new version until `installed` and `running` say so. `pta update dismiss VERSION` hides the notice for that release. Only the owner of the computer can check or stage (a portal session, machine credential or another account only sees that the operator manages updates); the registry, crate, directory and command cannot be chosen, the version must be the one the check just offered, and the build runs without any account variable or credential. A failure message (no Cargo, old Rust, no C compiler, no disk space, network) says what to fix; relay it and let the user repeat. Do not install over a prepared build or touch `maintenance/` by hand; the shared server's own timer updates the server independently.

**Install a prepared update (this computer only).** `pta update apply VERSION --confirmed` (MCP `update_apply`, the desktop's Install update) installs the prepared version after the user confirmed that exact action: it waits for work in progress (`state: deferred` with fixed reasons; it never interrupts an answer, a send, an implementation, a creation or a migration; `pta update cancel` withdraws the wait), then quits the application, replaces the application and `pta` together, starts the application the way it was started, restores the assistant only if it was running and checks health. If the new version does not start and report healthy, the previous pair is put back automatically (`apply.state: rolled_back` with the reason); if even that fails, `apply.state: failed` carries the recovery path (reinstall the exact version with `cargo install personal-teams-assistant --version X.Y.Z --locked --force`; nothing is deleted). The application restarts, so poll `pta update status` (it reads the update journal while the application is down) until `apply.state` is `success`, `rolled_back` or `failed`; `installed` alone never means done. While an update is applying no `pta` command starts a host: wait and retry. A headless host started by a systemd unit is refused (`apply_unsupported`): update it with `cargo install … --locked --force` and restart the unit. After `success` read `apply.notes`: the application's own skill copies (installed with `pta skill install`) were refreshed only if unmodified; copies you changed are listed and untouched; agents that keep `pta mcp` running must reconnect to read the new catalog. Never delete `maintenance/`, kill the helper or run `cargo install` for this package while an update is applying; an interrupted update is undone automatically by the next status or host start.

**Windows startup stack overflow (0.9.8).** A host crash with `has overflowed its stack` or Windows exception `0xc00000fd` can prevent `pta app open` even when `pta --version` and `pta doctor --offline` work. From 0.9.9, Windows MSVC builds link only the host with an 8 MiB stack reserve (default commit), so a normal Cargo installation retains the fix without EDITBIN. This addresses the confirmed 1 MiB startup limit; the function consuming that stack is still unidentified. Verify `pta app open`, `pta --json status` (`host_running: true`, matching `host_version`, `headless: false`), closing/reopening the window and `pta app quit` followed by opening again. Opening the window does not start Teams; keep `running: false` for a startup-only check and do not change credentials.

`pta tunnel configure token`, `pta tunnel configure file PATH` or `pta tunnel configure external` choose a mode. The token is stored as `CLOUDFLARE_TUNNEL_TOKEN` with credentials set, never in arguments. `pta tunnel validate` checks the mode and the local requirements; it does not prove connectivity from the Internet.

The administrative channel uses another loopback port, an instance token in a private file and a profile lock. The Graph tunnel keeps only its configured origin. Changing the configuration validates first; a failed restart requires checking whether it was applied and stopped. After an abrupt crash, the next host recovers the pending configuration transaction; ambiguous Graph sends are never resent.

**Headless host (Linux/servers).** Install it with `cargo install personal-teams-assistant --no-default-features --locked` (no Tauri/WebKit) or force it with `personal-teams-assistant --headless` / `PTA_HEADLESS=1`. `pta --json status` shows `headless: true`; `app open/hide` answer `not_ready`; `app quit`, SIGTERM or Ctrl-C stop the service and tunnel before exiting. `--start` tries to start the service at launch and keeps the host alive if it fails, to diagnose it. On Linux, credentials are stored with `pta credentials set NAME` in `~/.config/dev.personalteams.assistant/credentials/default/` (0600) or given as `NAME`/`NAME_FILE` in the host's environment. Remote login: `pta auth microsoft login --no-browser`, authorize the URL on any device and paste the `http://localhost:PORT/?code=…` address the browser could not open into `pta auth microsoft finish --redirect 'URL'`. systemd user service in `~/.config/systemd/user/pta.service` (`systemctl --user enable --now pta`, with `loginctl enable-linger` so it keeps running without a session):

```ini
[Unit]
Description=Personal Teams Assistant (headless)
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=%h/.cargo/bin/personal-teams-assistant --headless --start
Restart=on-failure
RestartSec=10

[Install]
WantedBy=default.target
```

**Automatic server updates.** New versions reach crates.io when a version change is merged (the repository's release workflow publishes it after CI passes). A server running the web portal can install each one by itself with the repository's updater (`scripts/vps-update.py` and its systemd user timer, see [delivery](https://github.com/elvisbrevi/personal-teams-assistant/blob/main/docs/delivery.md)): every five minutes it compares `pta --version` with crates.io, waits while an activity review, a task write or a Teams answer is in flight, installs headless, restarts the portal service, verifies `pta status` and restores the previous version if the new one is not healthy. `~/.local/state/personal-teams-assistant-update/history.log` records each update, deferral and rollback; `personal-teams-assistant-update --check` tells what it would do. Do not update that server by hand as well.

For a requested product delivery, include a new, unpublished version in `Cargo.toml`, `Cargo.lock` and `desktop/tauri.conf.json` before the pull request. After CI passes and it merges, verify crates.io publication and the server's running version and health. A merge and push, or a successful release workflow that skipped an existing version, do not prove publication or installation.

Never keep two instances of the same account active at once (another computer, the local GUI or a server): they would duplicate answers and cause loops in the personal chat. Leave the other one stopped or in `pta mode observe`.
