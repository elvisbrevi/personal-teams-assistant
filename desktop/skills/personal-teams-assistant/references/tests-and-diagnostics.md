`pta doctor --offline` validates local files without opening the database in recovery mode or calling providers. `pta doctor` inspects configuration, credentials and connection; its result says explicitly that it did not test the network. Errors and pending items have a non-zero exit code.

Microsoft's saved session can require renewed interactive verification even when
the account still appears connected locally. `pta start` and `pta test connectivity`
then return `not_ready` with a fixed instruction to reconnect Microsoft in Settings.
Use `pta auth microsoft login`, complete the browser verification and check
`pta auth microsoft finish` followed by `pta test connectivity`. Preserve the profile,
encryption key and scopes; do not log out or replace credentials to renew MFA.
Failed token renewal never deletes the saved session or prints provider text.

`pta chat` or `pta test simulate` read a SimulationRequest JSON on stdin: session, text, group, mentioned, sources. Use enabled sources that allow external processing. The simulation calls the configured providers and may cost; it never sends messages to Graph or widens audiences.

`pta test self-chat` checks the membership of the configured conversation. It does not prove sending or reception. For the real check, the person writes a new question there and verifies the answer. Read `pta audit list --limit 20` and `pta self-chat status`. Repeat after a restart. The assistant's answers must be ignored without producing another send.

`pta audit show RESOURCE` and `pta logs --limit 50` are read-only queries. The audit omits content by default (`question`, `resolved_question`, `topic`, `proposed`, `sent`); `--content` is an explicit private query. Each entry has `created_at`, `intent` (`question`, `activity_review` or `greeting`), `trace` (timed steps whose detail never contains message content: received, eligibility, intent, context, follow-up, activity review, sources, evidence, model, references, withheld/notice, send; audits written before 0.6.1 have Spanish step names), `history_messages` (earlier messages used as context), `provider` and `provider_fallbacks`, `reference_selection` (`llm` or `code`) and `withheld_notice`. In the GUI, the **Messages** tab shows the same for the last 100 messages, with filters (Answered, Withheld or unanswered, Errors, In progress). Release files and shared reports carry metadata and results, never personal messages or credentials.

If a documentation question gets no answer, first check `trace`, `source` and `tools` in the audit: no `search_azure_devops_wiki` means the Wiki was not read. In a follow-up, the log event `follow_up_resolution_unavailable` means the topic could not be resolved with the previous exchange and the literal request was searched. `informational_message` means the message informed without asking for an answer; `personal_request`, that it asked the person for a call, a meeting, a joint review or their availability (outside the personal chat it is not answered, even with `?`). `invalid_references` (an invented ID, an entity without a verified reference or a URL not in the evidence) and `unsafe_proposal` (sensitive data or size) are withheld by code: the proposal stays in `proposed` and, in the personal chat, a fixed notice is sent once (`withheld_notice`). Models never withhold answers: the chain classifies ambiguous messages (which may leave them unanswered as `informational_message` or `personal_request`) and picks the references an answer uses among those code did not see named. If no model can choose, code cites the entities it sees named and lists the consulted Wiki pages (`reference_selection: code`, section «Páginas consultadas», or «Pages consulted» in English). `reference_selection_failed`, `final_gate` and `final_check` appear only in audits written before 0.6.1. Wiki attribution in citations is built by code from verified metadata. The language model writes the text and never copies source IDs. `audit.provider` names the provider that wrote the answer (`codex:model:effort`, `claude:…` or `deepseek:…`); the log events `llm_provider_unavailable` (with `failure`: `usage_limit`, `not_installed`, `invalid_answer` or `failed`) and `llm_fallback_used` show when a fallback answered. Never widen audiences to fix a selection failure. The context of a follow-up is the conversation's 10 earlier messages with author and date/time (`history_messages`), plus the last exchange; `conversation_history_unavailable` in the log means Graph did not return them.

**Activity reviews.** A question about the user's work that no task records («¿qué tareas o trabajo he realizado que no están registrados?», "what work did I do that isn't logged?") is an activity review: code recognizes the clear phrasings and the model chain classifies other questions about the user's work. It reads every authorized activity source at once: Azure DevOps (`get_azure_devops_status`: own commits, pull requests, pipeline runs the user queued, releases the user created and approvals the user gave, compared with the user's work items and their links), the Wiki (pages the user created or edited) and, if authorized, the user's own Teams messages (`get_own_teams_messages`). The window is two weeks unless the request names one («hoy», «esta semana», «este mes», «últimos N días», "today", "this week", "last N days"; at most 31 days), and the answer states it. The answer is a short reply: the period and how many pieces of work have no linked work item, one bullet per piece (date, what, identifiers) with the work items where it could be registered — code suggests up to three of the user's own whose titles match it, with verified links — and one question asking where to register each. Registered work is not summarized, and only work items Azure DevOps returns are named by number. In the personal chat, with a write credential, the review itself ends with «Propuesta de registro»: per piece of work, the existing work item to link it to or a new task to create in an HU, with the reason, and «¿Quieres que las registre?». Nothing is written until the user replies «sí» or «confirmo» (or «cancelar»); a reply such as «la segunda en la #4321» replaces the plan with that change. Plans and offers last an hour (trace step `proposal` says how many proposals code kept). Each link is recorded before its request and never retried: the reply and `audit.links` say `linked`, `already_linked`, `failed` or `uncertain` (check the work item by hand), and `created` holds a new task's ID. Check `intent: link` and the reasons `links_planned`, `links_applied`, `links_cancelled`, `links_unresolved` or `links_not_configured` in the audit. Linking needs `link_secret_ref` on the Azure DevOps activity source (see [auth-and-knowledge.md](auth-and-knowledge.md)); without it the app only reads Azure DevOps and says how to set it up. A source that cannot be read or is cut to fit the context is named in the evidence (`trace` step `activity review` for unread ones) and coverage becomes partial; the answer still goes out. Raising `policy.max_context_chars` (up to 32000) gives a review more room. Check `intent: activity_review`, `tools` and `source` in the audit. The Azure DevOps read takes about half a minute; the whole answer about one to two minutes with Codex at medium effort.

`pta test providers` tests each active provider of `llm.chain` on its own with synthetic facts: two answers (a brief one and a detailed one) and one intent classification. A provider passes when it returns non-empty answers in the JSON contract; the detailed mode it chose and the intent are reported in `checks` but not required. It uses API credit or subscription quota. `provider_checks` holds `ok` and, on failure, `failure` per provider (`empty_answer`, `invalid_answer`, `usage_limit`, `not_installed` or `failed`); `all_passed` is false if any failed. If none passes, the command fails with exit 5 (`dependency_or_network`), a message naming each provider's failure, and keeps `provider_checks` in `data`. `pta test connectivity` validates the connected Graph account by reading, without sending.
