`pta doctor --offline` validates local files without opening the database in recovery mode or calling providers. `pta doctor` inspects configuration, credentials and connection; its result says explicitly that it did not test the network. Errors and pending items have a non-zero exit code.

Microsoft's saved session can require renewed interactive verification even when
the account still appears connected locally. `pta start` and `pta test connectivity`
then return `not_ready` with a fixed instruction to reconnect Microsoft in Settings.
Use `pta auth microsoft login`, complete the browser verification and check
`pta auth microsoft finish` followed by `pta test connectivity`. Preserve the profile,
encryption key and scopes; do not log out or replace credentials to renew MFA.
Failed token renewal never deletes the saved session or prints provider text.

A simulation that may read the user's own Teams messages source uses the host's Microsoft session (the running assistant's, or the profile's for that simulation); without one the review says why in its `activity review` step and in `warnings` («this profile has no Microsoft session…», «the Microsoft session needs renewal…»).

`pta chat` or `pta test simulate` read a SimulationRequest JSON on stdin: session, text, group, mentioned and optionally sources. Named sources must be enabled and allow external processing (otherwise `invalid_input`). Without `sources`, a map with questions offers every such source and the identified question reads its own (no question matched: `no_matching_question`, like in Teams); a map without questions reads the sources authorized for every conversation (`*`). When none can be read, the reply is `invalid_input` and says what is missing. The simulation calls the configured providers and may cost; it never sends messages to Graph or widens audiences.

`pta test self-chat` checks the membership of the configured conversation. It does not prove sending or reception. For the real check, the person writes a new question there and verifies the answer. Read `pta audit list --limit 20` and `pta self-chat status`. Repeat after a restart. The assistant's answers must be ignored without producing another send.

`pta audit list [--limit N] [--content] [--since DATE] [--until DATE] [--before CURSOR]` (MCP `messages_list`) returns `{entries, next_cursor, total, oldest_at}`: entries newest first (50 by default, at most 1000 per page, and a page stops early before 1.5 MB), `next_cursor` the last entry's resource when more remain (pass it as `--before`; a day or RFC 3339 instant works too), `total` how many messages the window holds and `oldest_at` when the oldest message in the audit was received. The audit keeps every message: nothing is deleted, so paging reaches the first one. A group message that does not mention the user is recorded `ignored` with reason `ineligible_message` and no text (the audit never copies a message that was not addressed to the assistant); read it with `pta teams messages RESOURCE` (see [Reading chats](#reading-chats)).

`pta audit show RESOURCE` and `pta logs --limit 50` are read-only queries. From 0.9.6, failed app commands also persist `app_operation_failed`: operation, error/exit code, elapsed milliseconds, source file/line, available app stack frames and typed causes (I/O kind/OS code, HTTP status/timeout/connection, parse position, SQLite code or Azure login stage/reason/exit code/output size, AADSTS codes and transport category). These records survive restarts and are available even with the assistant stopped. Pending authorization is progress and is not recorded as an error. No raw exception/provider text, command arguments, tokens, login codes or message content is stored. If the configured log destination is unavailable, inspect the host stderr/systemd journal for `app_error_log_unavailable` and its typed cause. The audit omits content by default (`question`, `resolved_question`, `topic`, `proposed`, `sent`); `--content` is an explicit private query. Jobs are `pending`, `processing`, `refining` (an answer being written at the user's request), `ignored`, `dry_run`, `failed`, `sending`, `sent` or `uncertain`. Each entry has `created_at`, `intent` (`question`, `activity_review`, `greeting`, `shared_link` or `link`; for a message left unanswered since 0.7.18, `statement` (informational) or `personal` (a request for the person)), `trace` (timed steps whose detail never contains message content: received, eligibility, intent, context, follow-up, activity review, sources, evidence, model, references, withheld/notice, send; audits written before 0.6.1 have Spanish step names), `history_messages` (earlier messages used as context), `provider` and `provider_fallbacks`, `reference_selection` (`llm` or `code`) and `withheld_notice`. In the GUI, the **Messages** tab shows the same for the last 100 messages, with filters (Answered, Withheld or unanswered, Errors, In progress). Release files and shared reports carry metadata and results, never personal messages or credentials.

If a documentation question gets no answer, first check `trace`, `source` and `tools` in the audit: no `search_azure_devops_wiki` means the Wiki was not read. In a follow-up, the log event `follow_up_resolution_unavailable` means the topic could not be resolved with the previous exchange and the literal request was searched. `informational_message` means the message informed without asking for an answer; `deterministic_thanks`, that it only shared a link (a `?` inside a URL does not make it a question) and the sender was thanked by first name; `personal_request`, that it asked the person for a call, a meeting, a joint review or their availability (outside the personal chat it is not answered, even with `?`). `invalid_references` (an invented ID, an entity without a verified reference or a URL not in the evidence) and `unsafe_proposal` (sensitive data or size) are withheld by code: the proposal stays in `proposed` and, in the personal chat, a fixed notice is sent once (`withheld_notice`). Models never withhold answers: the chain classifies ambiguous messages (which may leave them unanswered as `informational_message` or `personal_request`) and picks the references an answer uses among those code did not see named (or cannot link by a distinctive name), with the words of the answer that name each one. Answers carry no sources section: code links each reference on those words; a page used but not named is linked in one closing sentence («Más detalle en …»). If no model can choose, code links the entities it sees named and the Wiki pages read (`reference_selection: code`). The full list stays in `references`/`used_sources` (Messages tab: «Cited references», «Wiki pages read, not cited»). A word shared by a project and a stage («Área Desarrollo» / stage «Desarrollo») is not linked without the model. `reference_selection_failed`, `final_gate` and `final_check` appear only in audits written before 0.6.1; answers before 0.7.15 end with «Fuentes»/«Páginas consultadas». Wiki attribution is built by code from verified metadata. The language model writes the text and never copies source IDs. `audit.provider` names the provider that wrote the answer (`codex:model:effort`, `claude:…` or `deepseek:…`); the log events `llm_provider_unavailable` (with `failure`: `usage_limit`, `not_installed`, `invalid_answer` or `failed`) and `llm_fallback_used` show when a fallback answered. Never widen audiences to fix a selection failure. The context of a follow-up is the conversation's 10 earlier messages with author and date/time (`history_messages`), plus the last exchange; `conversation_history_unavailable` in the log means Graph did not return them.

**Activity reviews.** A question about the user's work that no task records («¿qué tareas o trabajo he realizado que no están registrados?», "what work did I do that isn't logged?") is an activity review: code recognizes the clear phrasings and the model chain classifies other questions about the user's work. It reads every authorized activity source at once: Azure DevOps (`get_azure_devops_status`: own commits, pull requests, pipeline runs the user queued, releases the user created and approvals the user gave, compared with the user's work items and their links), the Wiki (pages the user created or edited) and, if authorized, the user's own Teams messages (`get_own_teams_messages`). The window is two weeks unless the request names one («hoy», «esta semana», «este mes», «últimos N días», "today", "this week", "last N days"; at most five weeks), and the answer states it. The answer is a short reply: the period and how many pieces of work have no linked work item, one bullet per piece (date, what, identifiers) with the work items where it could be registered — code suggests up to three of the user's own whose titles match it, with verified links — and no request to register work. Registered work is not summarized, and only work items Azure DevOps returns are named by number. Activity reviews never create, link or change Azure tasks. No proposal or confirmation flow is offered by these reviews; old activity plans cannot write. Reviewed child creation belongs only to the separate implementation workflow (see [tools-and-todo.md](tools-and-todo.md)). Daily task snapshots are separate read-only operations (see [activity-registration.md](activity-registration.md)). A source that cannot be read or is cut to fit the context is named in the evidence (`trace` step `activity review` for unread ones) and coverage becomes partial; the answer still goes out. Raising `policy.max_context_chars` (up to 32000) gives a review more room. Check `intent: activity_review`, `tools` and `source` in the audit. The Azure DevOps read takes about half a minute; the whole answer about one to two minutes with Codex at medium effort.

**Rating answers.** `pta answer feedback RESOURCE` takes `{"rating":"good"|"bad"|null,"comment":"…"}` on stdin, also available on Messages and Test chat answers. The rating stays in the audit and, for an identified question, becomes retrievable guidance for that question: good suggests the approach, bad tells the model which mistake to avoid. Current facts come only from fresh evidence. Code blocks identical rejected repeats; broader avoidance depends on the model. Clearing the rating removes indexed guidance. Unknown messages offer **Associate question**, which saves an existing/new question and its selected sources without sending an answer.

**Status rounds.** A status question (avance, compromisos, riesgos o bloqueos, HU, pipelines…; "progress", "commitments", "blockers") reads the Azure DevOps activity source and, when a Wiki source is authorized for the conversation, the user's own Wiki pages of the last month (`tools`: `get_azure_devops_status` and `read_own_wiki_pages`; a Wiki read failure only makes coverage partial). A work item the request names («HU #41553», «bug 4512», «#41553»; not «run #345» or «PR #12») is read directly inside the catalog's projects, whoever holds it now, and described only if the user took part in it (assigned now or before, created or changed it, a child item or a comment of theirs; otherwise the answer says it is not theirs and who holds it): its state and since when, current assignee, dates on the item (target, due or custom commitment dates by their display name), parent and, from the last five weeks only, state and assignment changes, child items, linked commits and pull requests and comments. No activity read looks back more than five weeks, and all of them are limited to the user's own activity or work they took part in. Status rounds and activity reviews also read what the Activities section recorded, by day (`read_recorded_activities`), when the activity record source is authorized for the conversation (in a map without one, when Azure DevOps activity is): registered tasks with their links and detected work not registered yet; detected work drawn from Wiki pages or Teams messages shows only where those sources are authorized too. The user's work items also include the ones previously assigned to them and now held by someone else (handed over to validation). The answer goes part by part: progress from the item's state (development: tasks, code and comments with dates; past development: since when and who holds it now), the commitment from dated work items within two weeks and the user's production deployment pages, and blockers from pending items in those pages or comments. A named work item outside the catalog's projects is reported as not found and never named. Check the evidence step and `source` in the audit.

**What the user did on a day or period.** A question about the user's own work that names a day or period («¿qué hice ayer?», «¿qué hiciste el martes?», «mi actividad del 10 de octubre», «del 5 al 9 de octubre», «10/10», «la semana pasada», «en septiembre», "what did I do yesterday?", "October 5 to 9"; numeric dates are day/month, a date without a year is the latest one not after today) is answered from what the Activities section recorded for exactly those days, when it recorded anything there: saved existing tasks (with verified task links and an HU when available), explicit empty-day records and legacy activity. No other tool is read (`tools`: only `read_recorded_activities`; trace step `activity history` names the days) and the answer is a short day-by-day summary. It needs the Azure DevOps activity source authorized for the conversation, and an entry shows only if every source its activities come from is authorized there. Questions that name a work item, a status round (avance, compromiso, bloqueos, pipelines, releases…) or unregistered work keep their usual routes, and a period with nothing recorded falls back to them too. Older days are not limited to five weeks: the record is local.

**Answering a message by hand.** A message addressed to the assistant that was not sent an answer can get one written and sent from the app, with the assistant running: one the assistant left unanswered (informational, a request for the person, no authorized source) and one whose answer was withheld by the code checks or observed in observation mode. A message with sensitive data never can. `pta answer refine RESOURCE [--context-stdin] [--source ID]...` (or **Generate answer** in the Messages tab, then **Regenerate answer**) writes it in the background, never sending it: with the user's context (plain text, at most 4000 characters, without credentials or personal data), the previous proposal if any and freshly read sources. A message left unanswered keeps its intent (`statement` or `personal`) and is replied to, not answered as a question. `--source` (repeatable; the GUI's **Sources** chooser) restricts the answer to the chosen sources and reads every one of them: any enabled source with external processing, even one outside the conversation's audiences, because the user reviews and sends the result (an unknown, disabled or unauthorized one is `invalid_input`); without it, the conversation's authorized sources and the normal routing are used. The job shows `refining` and ends `ignored` with reason `draft_ready` (it passed the checks), a withheld reason, the reason the run stopped before writing (`no_authorized_resource`, `message_changed`) or `refinement_failed` (an earlier proposal is kept). Nothing is sent and no notice goes to the personal chat. `pta answer send RESOURCE` (or **Send answer**, which asks for a second tap) sends the shown proposal once, as the user: it requires a proposal and the message text unchanged, refuses sensitive data or an oversized answer, records `sending` before the request and ends `sent` (reason `manual_send`) or `uncertain` (check Teams by hand; never retried). A sent, sending or refining message cannot be written or sent again (`state_conflict`). The audit keeps the context in `refinement` (omitted without `--content`), the chosen sources in `chosen_sources` and the steps `refine`, `draft` and `manual send`. A restart while writing leaves the job `ignored` with `refinement_failed`; it is never queued again.

`pta test providers` tests each active provider of `llm.chain` on its own with synthetic facts: two answers (a brief one and a detailed one) and one intent classification. A provider passes when it returns non-empty answers in the JSON contract; the detailed mode it chose and the intent are reported in `checks` but not required. It uses API credit or subscription quota. `provider_checks` holds `ok` and, on failure, `failure` per provider (`empty_answer`, `invalid_answer`, `usage_limit`, `not_installed` or `failed`); `all_passed` is false if any failed. If none passes, the command fails with exit 5 (`dependency_or_network`), a message naming each provider's failure, and keeps `provider_checks` in `data`. `pta test connectivity` validates the connected Graph account by reading, without sending.

## Reading chats

Read Teams through these commands, never through another Microsoft connector or a raw Graph call. They and `pta teams send` (tool `teams_post`) work on every computer of the account that signed in to Microsoft, whichever machine is selected to answer Teams: that selection only decides who receives and answers on its own. All are reads (no confirmation), use the running service's Microsoft session or the profile's own when the assistant is stopped (`Chat.Read`, already consented) and only read the chats this computer may read on request: those it receives (the personal chat, `graph.allowed_chats`, or every chat with `graph.discover_all_chats`) plus those the account allows every computer to read (`teams_reading`, see [account configuration](account-configuration.md#teams-chats-read-on-request)). Nothing is sent or stored; web-portal accounts do not have these operations.

- `pta teams chats [QUERY] [--limit N] [--offset N]` (tool `teams_chats`) lists the chats the user belongs to — 1:1, group and meeting — newest first, with `id`, `type`, `topic` (the other members' names when a chat has none), `members`, `last_updated` and `readable` (whether `teams messages` may read it), plus `total`, `offset` and `next_offset` (pass it as `--offset`; absent on the last page). `QUERY` keeps those whose topic or a member name contains it. 50 per call by default, at most 500.
- `pta teams messages CHAT [--since DATE] [--until DATE] [--limit N] [--before CURSOR]` (tool `teams_messages`) reads a chat's history from every author, newest first: `id`, `resource` (`chats/CHAT/messages/ID`, as the audit names messages), `created_at`, `author` (display name, never an address), `mine`, `assistant` (an answer or post this app sent), plain `text` (HTML and cards converted; `truncated` past 4000 characters), `edited`, `replies_to` (the messages it replies to or quotes, with author and preview) and `url` when Graph gives one. `CHAT` is an ID from `teams chats`, `self` (the personal chat) or one message's resource (reads just that message, for example one the audit lists as `ineligible_message`). `next_cursor` goes to `--before` for the older messages; it is absent when the window is exhausted. One call reads at most 1000 messages of the chat; past that it returns `next_cursor` and a warning. 50 messages by default, at most 200. An unknown chat, one that does not list the user or one this computer may not read is `invalid_input` («This profile may not read that chat…»): on a computer of the account, check `pta config get teams_reading` (the account's) before changing this computer's own reception.
- `pta teams messages --mine [--since DATE] [--until DATE] [--limit N] [--before CURSOR]` (tool `teams_messages` with `mine: true`) reads the user's own messages across the chats this profile reads (the personal chat left out), last 30 days unless `--since` says otherwise. It reads the 40 chats with the latest messages in the window and 500 messages of each; past that `partial` is true and `warnings` say what to narrow.
- `pta teams search TEXT [--chat ID]... [--from NAME] [--since DATE] [--until DATE] [--limit N] [--before CURSOR]` (tool `teams_search`) finds messages in those chats with the same fields. It uses Microsoft Search (`method: microsoft_search`); `--chat` keeps those chats, `--from` a part of the author's name (accents and case ignored) and the window narrows the dates. If Microsoft Search cannot be used, it reads the chats' history directly (`method: chat_history`) — the named chats, or the 40 with the latest messages since `--since` (last 30 days by default) — keeping messages that contain every word of `TEXT`, and `warnings` say so; its `next_cursor` goes to `--before` for older matches. Some tenants refuse Microsoft Search for chat messages with the consented scope (HTTP 403); there the direct reading always runs. `partial` is true when more messages match than were returned or something was not read. 25 by default, at most 100.

`DATE` is `YYYY-MM-DD` in this computer's time zone (`--until` includes that day) or an RFC 3339 instant; a cursor is the RFC 3339 instant `next_cursor` returned.

## Posting a new message

`pta teams chats [QUERY]` (tool `teams_chats`, a read; see [Reading chats](#reading-chats)) finds the chat ID to post in. `pta teams send CHAT` (tool `teams_post`, needs the user's confirmation of the exact chat and text) reads Markdown on stdin and posts it once, as the user, in that chat (an `id` from `teams chats`, or `self` for the personal chat). The text is rendered like the assistant's answers (bold, italics, strikethrough, code and code blocks, headings, lists, quotes, tables, HTTPS links, colors) and, with `message_style` on, sent as the same styled card with its stripe and band; a message with mentions, or one whose card would not fit, is sent as plain HTML. `@[Display Name]` mentions a member of that chat: an exact display name (case-insensitive) or the only member whose name contains it; an unknown or ambiguous name refuses the whole message (`invalid_input`: «A mention names nobody in this chat…», «A mention matches several members…») and nothing is sent. An invalid chat ID, a chat that does not list the user and an oversized message are `invalid_input` too. Mentions are not available in the personal chat. The chat must list the user as a member; channels are not supported (their send permission is not consented). It uses the running service's Microsoft session, or the profile's own when the assistant is stopped.

Images and GIFs go inside the message itself, with no external host and no link: `pta teams send CHAT --image PATH [--alt TEXT]` (repeatable; each `--alt` describes the `--image` before it) or the tool's `images: [{"path": "/home/me/memes/homero.gif", "alt": "Homero"}]` (`data` with base64 instead of `path` for a small generated image). At most 4 images, 2.9 MB together; PNG, JPEG and GIF only (animated GIFs included), recognized by their bytes whatever the file is called (WebP and SVG are refused). They follow the text, which may then be empty (`pta teams send self --image meme.gif` with nothing on stdin). The file is read by the `pta` process that receives the call, never by the host, and the confirmation names each image with its type, dimensions, size and the first 8 digits of its SHA-256: those very bytes are sent, once. A message with images is sent as plain HTML even with `message_style` on (the result's `style` says so). Refusals are `invalid_input`: «A message carries at most 4 images.», «The images exceed 2.9 MB together…», «Only PNG, JPEG and GIF images can be posted…», «The image could not be read…». The `teams_post` event records how many images and bytes, never their content. Reading a chat later, each image appears as `[image]` or `[image: alt]` in `text`, and `images` counts them. A `pta` with images refuses an older host («update the host and CLI together»).

Like every send it happens at most once: a refusal by Teams (4xx) means nothing was sent, while any other failure says «The result is unknown; check Teams by hand» (`operation_failed`) — never repeat it automatically. Posts in the personal chat carry the same output marker as the assistant's answers, so the assistant never answers them. `events` records `teams_post` with `sent`, `refused` or `uncertain`, never the content. Web-portal accounts do not have these operations.
