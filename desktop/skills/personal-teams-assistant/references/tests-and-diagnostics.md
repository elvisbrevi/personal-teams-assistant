`pta doctor --offline` validates local files without opening the database in recovery mode or calling providers. `pta doctor` inspects configuration, credentials and connection; its result says explicitly that it did not test the network. Errors and pending items have a non-zero exit code.

Microsoft's saved session can require renewed interactive verification even when
the account still appears connected locally. `pta start` and `pta test connectivity`
then return `not_ready` with a fixed instruction to reconnect Microsoft in Settings.
Use `pta auth microsoft login`, complete the browser verification and check
`pta auth microsoft finish` followed by `pta test connectivity`. Preserve the profile,
encryption key and scopes; do not log out or replace credentials to renew MFA.
Failed token renewal never deletes the saved session or prints provider text.

`pta chat` or `pta test simulate` read a SimulationRequest JSON on stdin: session, text, group, mentioned, sources. Use enabled sources that allow external processing. The simulation calls the configured providers and may cost; it never sends messages to Graph or widens audiences.

`pta test self-chat` checks the membership of the configured conversation. It does not prove sending or reception. For the real check, the person writes a new question there and verifies the answer. Read `pta audit list --limit 20` and `pta self-chat status`. Repeat after a restart. The assistant's answers must be ignored without producing another send.

`pta audit show RESOURCE` and `pta logs --limit 50` are read-only queries. The audit omits content by default (`question`, `resolved_question`, `topic`, `proposed`, `sent`); `--content` is an explicit private query. Jobs are `pending`, `processing`, `refining` (an answer being written at the user's request), `ignored`, `dry_run`, `failed`, `sending`, `sent` or `uncertain`. Each entry has `created_at`, `intent` (`question`, `activity_review`, `greeting`, `shared_link` or `link`; for a message left unanswered since 0.7.18, `statement` (informational) or `personal` (a request for the person)), `trace` (timed steps whose detail never contains message content: received, eligibility, intent, context, follow-up, activity review, sources, evidence, model, references, withheld/notice, send; audits written before 0.6.1 have Spanish step names), `history_messages` (earlier messages used as context), `provider` and `provider_fallbacks`, `reference_selection` (`llm` or `code`) and `withheld_notice`. In the GUI, the **Messages** tab shows the same for the last 100 messages, with filters (Answered, Withheld or unanswered, Errors, In progress). Release files and shared reports carry metadata and results, never personal messages or credentials.

If a documentation question gets no answer, first check `trace`, `source` and `tools` in the audit: no `search_azure_devops_wiki` means the Wiki was not read. In a follow-up, the log event `follow_up_resolution_unavailable` means the topic could not be resolved with the previous exchange and the literal request was searched. `informational_message` means the message informed without asking for an answer; `deterministic_thanks`, that it only shared a link (a `?` inside a URL does not make it a question) and the sender was thanked by first name; `personal_request`, that it asked the person for a call, a meeting, a joint review or their availability (outside the personal chat it is not answered, even with `?`). `invalid_references` (an invented ID, an entity without a verified reference or a URL not in the evidence) and `unsafe_proposal` (sensitive data or size) are withheld by code: the proposal stays in `proposed` and, in the personal chat, a fixed notice is sent once (`withheld_notice`). Models never withhold answers: the chain classifies ambiguous messages (which may leave them unanswered as `informational_message` or `personal_request`) and picks the references an answer uses among those code did not see named (or cannot link by a distinctive name), with the words of the answer that name each one. Answers carry no sources section: code links each reference on those words; a page used but not named is linked in one closing sentence («Más detalle en …»). If no model can choose, code links the entities it sees named and the Wiki pages read (`reference_selection: code`). The full list stays in `references`/`used_sources` (Messages tab: «Cited references», «Wiki pages read, not cited»). A word shared by a project and a stage («Sección Desarrollo» / stage «Desarrollo») is not linked without the model. `reference_selection_failed`, `final_gate` and `final_check` appear only in audits written before 0.6.1; answers before 0.7.15 end with «Fuentes»/«Páginas consultadas». Wiki attribution is built by code from verified metadata. The language model writes the text and never copies source IDs. `audit.provider` names the provider that wrote the answer (`codex:model:effort`, `claude:…` or `deepseek:…`); the log events `llm_provider_unavailable` (with `failure`: `usage_limit`, `not_installed`, `invalid_answer` or `failed`) and `llm_fallback_used` show when a fallback answered. Never widen audiences to fix a selection failure. The context of a follow-up is the conversation's 10 earlier messages with author and date/time (`history_messages`), plus the last exchange; `conversation_history_unavailable` in the log means Graph did not return them.

**Activity reviews.** A question about the user's work that no task records («¿qué tareas o trabajo he realizado que no están registrados?», "what work did I do that isn't logged?") is an activity review: code recognizes the clear phrasings and the model chain classifies other questions about the user's work. It reads every authorized activity source at once: Azure DevOps (`get_azure_devops_status`: own commits, pull requests, pipeline runs the user queued, releases the user created and approvals the user gave, compared with the user's work items and their links), the Wiki (pages the user created or edited) and, if authorized, the user's own Teams messages (`get_own_teams_messages`). The window is two weeks unless the request names one («hoy», «esta semana», «este mes», «últimos N días», "today", "this week", "last N days"; at most five weeks), and the answer states it. The answer is a short reply: the period and how many pieces of work have no linked work item, one bullet per piece (date, what, identifiers) with the work items where it could be registered — code suggests up to three of the user's own whose titles match it, with verified links — and no request to register work. Registered work is not summarized, and only work items Azure DevOps returns are named by number. Activity reviews never create, link or change Azure tasks. No proposal or confirmation flow is offered by these reviews; old activity plans cannot write. Reviewed child creation belongs only to the separate implementation workflow (see [tools-and-todo.md](tools-and-todo.md)). Daily task snapshots are separate read-only operations (see [activity-registration.md](activity-registration.md)). A source that cannot be read or is cut to fit the context is named in the evidence (`trace` step `activity review` for unread ones) and coverage becomes partial; the answer still goes out. Raising `policy.max_context_chars` (up to 32000) gives a review more room. Check `intent: activity_review`, `tools` and `source` in the audit. The Azure DevOps read takes about half a minute; the whole answer about one to two minutes with Codex at medium effort.

**Rating answers.** `pta answer feedback RESOURCE` takes `{"rating":"good"|"bad"|null,"comment":"…","example":true,"context":"cobros"}` on stdin (also Messages › Your rating). The rating stays in the message's audit (`feedback`); it cannot be set while the message is being processed. `example` (only for a good answer) keeps the request and the answer as an approved example: later answers to requests sharing at least half of its words get it for structure and tone, never for facts (trace step `examples`). Clear a rating with `null`, which also forgets the example. To turn a corrected answer into knowledge, save it as a verified note (`pta notes add` with `"origin":"answer"` and the message as `reference`, or «Save as a note»).

**Status rounds.** A status question (avance, compromisos, riesgos o bloqueos, HU, pipelines…; "progress", "commitments", "blockers") reads the Azure DevOps activity source and, when a Wiki source is authorized for the conversation, the user's own Wiki pages of the last month (`tools`: `get_azure_devops_status` and `read_own_wiki_pages`; a Wiki read failure only makes coverage partial). A work item the request names («HU #23553», «bug 4512», «#23553»; not «run #345» or «PR #12») is read directly inside the catalog's projects, whoever holds it now, and described only if the user took part in it (assigned now or before, created or changed it, a child item or a comment of theirs; otherwise the answer says it is not theirs and who holds it): its state and since when, current assignee, dates on the item (target, due or custom commitment dates by their display name), parent and, from the last five weeks only, state and assignment changes, child items, linked commits and pull requests and comments. No activity read looks back more than five weeks, and all of them are limited to the user's own activity or work they took part in. Status rounds and activity reviews also read what the Activities section recorded, by day (`read_recorded_activities`), when the activity record source is authorized for the conversation (in a map without one, when Azure DevOps activity is): registered tasks with their links and detected work not registered yet; detected work drawn from Wiki pages or Teams messages shows only where those sources are authorized too. The user's work items also include the ones previously assigned to them and now held by someone else (handed over to validation). The answer goes part by part: progress from the item's state (development: tasks, code and comments with dates; past development: since when and who holds it now), the commitment from dated work items within two weeks and the user's production deployment pages, and blockers from pending items in those pages or comments. A named work item outside the catalog's projects is reported as not found and never named. Check the evidence step and `source` in the audit.

**What the user did on a day or period.** A question about the user's own work that names a day or period («¿qué hice ayer?», «¿qué hiciste el martes?», «mi actividad del 10 de octubre», «del 5 al 9 de octubre», «10/10», «la semana pasada», «en septiembre», "what did I do yesterday?", "October 5 to 9"; numeric dates are day/month, a date without a year is the latest one not after today) is answered from what the Activities section recorded for exactly those days, when it recorded anything there: saved existing tasks (with verified task links and an HU when available), explicit empty-day records and legacy activity. No other tool is read (`tools`: only `read_recorded_activities`; trace step `activity history` names the days) and the answer is a short day-by-day summary. It needs the Azure DevOps activity source authorized for the conversation, and an entry shows only if every source its activities come from is authorized there. Questions that name a work item, a status round (avance, compromiso, bloqueos, pipelines, releases…) or unregistered work keep their usual routes, and a period with nothing recorded falls back to them too. Older days are not limited to five weeks: the record is local.

**Answering a message by hand.** A message addressed to the assistant that was not sent an answer can get one written and sent from the app, with the assistant running: one the assistant left unanswered (informational, a request for the person, no authorized source) and one whose answer was withheld by the code checks or observed in observation mode. A message with sensitive data never can. `pta answer refine RESOURCE [--context-stdin] [--source ID]...` (or **Generate answer** in the Messages tab, then **Regenerate answer**) writes it in the background, never sending it: with the user's context (plain text, at most 4000 characters, without credentials or personal data), the previous proposal if any and freshly read sources. A message left unanswered keeps its intent (`statement` or `personal`) and is replied to, not answered as a question. `--source` (repeatable; the GUI's **Sources** chooser) restricts the answer to the chosen sources and reads every one of them: any enabled source with external processing, even one outside the conversation's audiences, because the user reviews and sends the result (an unknown, disabled or unauthorized one is `invalid_input`); without it, the conversation's authorized sources and the normal routing are used. The job shows `refining` and ends `ignored` with reason `draft_ready` (it passed the checks), a withheld reason, the reason the run stopped before writing (`no_authorized_resource`, `message_changed`) or `refinement_failed` (an earlier proposal is kept). Nothing is sent and no notice goes to the personal chat. `pta answer send RESOURCE` (or **Send answer**, which asks for a second tap) sends the shown proposal once, as the user: it requires a proposal and the message text unchanged, refuses sensitive data or an oversized answer, records `sending` before the request and ends `sent` (reason `manual_send`) or `uncertain` (check Teams by hand; never retried). A sent, sending or refining message cannot be written or sent again (`state_conflict`). The audit keeps the context in `refinement` (omitted without `--content`), the chosen sources in `chosen_sources` and the steps `refine`, `draft` and `manual send`. A restart while writing leaves the job `ignored` with `refinement_failed`; it is never queued again.

`pta test providers` tests each active provider of `llm.chain` on its own with synthetic facts: two answers (a brief one and a detailed one) and one intent classification. A provider passes when it returns non-empty answers in the JSON contract; the detailed mode it chose and the intent are reported in `checks` but not required. It uses API credit or subscription quota. `provider_checks` holds `ok` and, on failure, `failure` per provider (`empty_answer`, `invalid_answer`, `usage_limit`, `not_installed` or `failed`); `all_passed` is false if any failed. If none passes, the command fails with exit 5 (`dependency_or_network`), a message naming each provider's failure, and keeps `provider_checks` in `data`. `pta test connectivity` validates the connected Graph account by reading, without sending.
