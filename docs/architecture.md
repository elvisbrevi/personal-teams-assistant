# Architecture

Technical reference for coding agents. It describes how the system is built, how a message flows through it and which invariants cannot be broken. The operating manual (`pta` commands) is the [built-in skill](../desktop/skills/personal-teams-assistant/SKILL.md).

## 1. What it is

A personal Microsoft Teams assistant that answers **as the user** (delegated OAuth, no bot). It receives messages through Microsoft Graph webhooks, decides whether to step in, retrieves evidence only from sources authorized for that conversation, writes with a language model (Codex, Claude Code or OpenCode 2 through their installed CLI, or the DeepSeek API, in a fallback chain), checks references, URLs and sensitive data in code and sends once. If a code check withholds the answer, nothing is sent: the answer is left to the person (and in the personal chat they get a notice). The same model chain classifies ambiguous messages and picks the references an answer uses; no model decision withholds an answer or grants a permission. Azure evidence and daily task snapshots remain read-only (§6.10–11). The separate implementation flow can create reviewed children of a verified parent, only after the user confirms its new implementation plan (§16); older activity plans cannot authorize these writes. The explicit Create request flow (§16) separately creates one GitHub Epic or Azure HU/bug from the context and destination the user confirms.

An optional host schedule saves the existing tasks for the local day, with verified links, descriptions, optional HU and daily hours. The daily target only warns; no model or write credential is involved. The Activities screen lists saved days, their tasks and full task detail. The same record supplies concise recaps without live activity discovery.

Everything in the repository — code, comments, prompts, documentation, the GUI's source text, CLI and IPC messages, diagnostics and audit steps — is in English. What the user reads follows `llm.language` (Spanish by default, or English): the GUI, translated at runtime from its English source by `desktop/ui/i18n.js` (the only Spanish UI catalog), what the assistant writes to Teams, and the activity drafts and issues written for the user.

It is distributed only through Cargo. One package, `personal-teams-assistant`, installs three pieces (up to 0.4.0 the app came in a separate package, `personal-teams-desktop`, now obsolete):

| Piece | Binary / path | Role |
| --- | --- | --- |
| GUI + host | `personal-teams-assistant` | Tauri tray/menu bar app. It is the **only owner** of the profile, the credentials and the Teams service. It can run hidden (`--host`) or **headless** (`--headless`, or built without the `gui` feature for Linux/servers). |
| CLI | `pta` | Administrative client. Talks to the host over authenticated loopback IPC; starts it hidden if there is none. |
| Skill | `desktop/skills/personal-teams-assistant/` | Manual for agents, built into `pta` (`pta skill show/path/install`). |

## 3. Process model

```mermaid
flowchart LR
  GUI[Tauri window] -- invoke --> D[control::dispatch<br/>operations mutex]
  CLI[pta] -- HTTP 127.0.0.1 + instance bearer --> IPC[/control/] --> D
  D --> HOST[DesktopState: settings, OAuth, tunnel, GitHub]
  HOST -- start --> RT[runtime::serve]
  RT --> W[job worker]
  RT --> R[subscription renewer 60 s]
  RT --> P[personal chat polling 10 s]
  RT --> L[public listener :bind<br/>/healthz /graph/notifications /graph/lifecycle]
  T[optional cloudflared] --> L
  Graph[Microsoft Graph] --> T
```

- **Host and shell.** `Host` = `DesktopState` (operations) + `Shell` (what the owning process can do: show/hide the window, open a URL, quit). `gui::TauriShell` implements it with Tauri; `headless::HeadlessShell` answers `not_ready` to `app open/hide`, returns URLs to the caller and ends the process on `app quit`. No operation depends on Tauri.
- **One host per profile.** `control.lock` (flock) proves ownership; `control.json` publishes port, random token and `wiki_support`. A descriptor without a lock is stale. A process is never signaled by PID.
- **IPC.** `POST /control` on an ephemeral loopback port, constant-time bearer, rejects any `Origin` (browsers). Body at most 1 MB, client timeout 120 s (no limit for `chat` and `test_providers`, which wait for the model).
- **Single dispatcher.** GUI and CLI go through `control::dispatch`, which serializes with `operations` and checks `revision` (SHA-256 of config + map + tunnel) for writes based on a snapshot. While Microsoft, GitHub or Azure CLI login is pending, profile mutations wait for completion or cancellation.
- **Operation diagnostics.** Failed GUI/CLI/MCP host commands append `app_operation_failed` to the existing event log (`pta logs`) and tracing output. Each entry records operation, error/exit code, duration and bounded typed cause chains with source location and available app stack frames. Causes include I/O kind/OS code, HTTP status/connection/timeout, JSON/TOML position, SQLite code and Azure CLI login phase/reason/exit code/output size, bounded AADSTS error codes and transport category. Arguments, raw exception/provider text, tokens, device codes and message content are never logged. Pending authorization is progress, not a failure. Appending an event initializes a missing schema without running job recovery or changing in-flight work; an unavailable log destination leaves the original reply intact and emits a tracing diagnostic.
- **Update.** A newer release is found and prepared (built and verified beside the installed one, installing nothing) by [installation updates](#installation-updates-discovery-and-staging) and, on the owner's request, installed with a restart and rollback by [applying an update](#applying-an-update-restart-and-rollback). `cargo install` runs nothing when it finishes and replaces the file while the previous host keeps running. `control.json` publishes `binary` (size and date of the executable at start; older hosts do not have it). If the running host was started from the **same installed path** and its fingerprint no longer matches, it is outdated (`control::outdated_host`): the first `pta` (except `capabilities`, `skill` and `doctor --offline`) or the new app retires it (`retire_outdated_host`: reads whether the assistant was running, sends `app_quit` — which stops assistant and tunnel — and waits for the lock, 60 s). If it was running, `pta` asks on the terminal whether to keep it running with the new version (without a terminal, `--json` or `--non-interactive` keeps the state); the new GUI shows the `restart_offer` notice (`start_assistant` or `dismiss_restart_offer`); the headless host asks if there is a terminal or keeps the state. `start`, `restart`, `stop` and `app quit` decide the state themselves. A host started from another path (e.g. a development build) is never retired this way.
- **The CLI starts the host** (`host_executable`: sibling binary or `host-path.txt`) with `--host` in its own process group and waits for the descriptor. The host inherits `pta`'s environment (`NAME`/`NAME_FILE` credentials, `PTA_HEADLESS`).
- **Service.** `runtime::serve` runs as a Tokio task inside the host. `app.rs::start` launches it, waits for `ready` (60 s; `runtime::Service` hands over the Graph handle and the `Pipeline`, kept in `Running` to write and send answers at the user's request, §6.12) and then starts `cloudflared` if needed. Failure before readiness retains the service's error category; a readiness timeout still stops and aborts it. `stop` kills the tunnel, sends `true` on the `watch` and waits 20 s before aborting. Closing the channel also counts as a stop.
- **Daily task record.** `control::launch` owns a separate 30-second scheduler. Snapshot runs return immediately and run in a tracked task; reads remain available and settings/identity mutations are blocked during a run. It needs neither Teams, Graph nor a model. Quitting aborts the read and preserves the previous saved day; legacy in-flight writes still recover as uncertain, never retried.

### Private browser GUI and owner profiles

`personal-teams-assistant --web` serves the same `desktop/ui` assets on a separate
loopback listener (default `127.0.0.1:38656`), with an HTTPS origin through the
dedicated Cloudflare Tunnel. Cloudflare Access owns the interactive GitHub login,
using a dedicated OAuth App unrelated to repository GitHub Device Flow. Access
protects the complete hostname and API; an explicit email allowlist plus the
configured GitHub login method gates admission at the edge. Admission never
creates or selects an application profile. `web/settings.json.owner_github_id` pins the
installation owner. Owner-only admission remains the upgrade default; legacy non-owner
profiles stay closed. The operator can explicitly admit another private assistant account
with `web users authorize USER`, then bind its verified immutable provider identity and
enable it. Additive `Account.authorized` defaults to false and never grants access to
`--current-profile`; only the configured owner can bind that original profile. Existing
settings infer an owner only from exactly one operator-associated identity; fresh or
ambiguous settings fail closed. `web configure` requires an explicit owner. The public
crate contains no maintainer portal/provider credentials or hosting defaults.


`app/web/access.rs` accepts exactly one `Cf-Access-Jwt-Assertion` and verifies
RS256 signature, pinned issuer/application audience, required subject/issuance/
not-before/expiration and application token type. Keys come only from the team's
HTTPS `/cdn-cgi/access/certs`, with bounded responses, five-minute freshness and
rate-limited rotation refresh. Expired keys are never used after a failed refresh.
The exact verified assertion is sent as `CF_Authorization` to the pinned team's
`/cdn-cgi/access/get-identity`; account, GitHub IdP ID/type and `user_uuid == sub`
are checked. Positive identity responses are cached by assertion hash for at most
30 seconds; JWT validity and local revocation are checked on every request.
Identity/email headers, service tokens and caller-selected URLs grant no access.

`pta web configure` writes private `web/settings.json`, whose additive `access`
configuration contains issuer, audience, account and dedicated GitHub IdP ID.
Legacy settings remain readable for inspection; a portal cannot start without
Access. `pta web users add/authorize/bind/unbind/revoke/disable/enable/list` manages private
`web/accounts.json` under the existing operator-local lock. `bind` takes the
operator's verified Access identity JSON on stdin. Its binding is the issuer,
GitHub IdP ID and provider subject (`id` from get-identity). GitHub's positive
integer IDs are normalized losslessly to decimal strings; legacy string subjects
remain readable. Floats, negative/zero integers and other JSON types are rejected.
The binding is never an email, name or email-associated Access `sub`.
Bindings cannot belong to two accounts. Existing
IDs, profile selection and retired password hashes survive additive schema reads;
hashes are never used to authenticate. Local association/reassociation is the
recovery path; there is no public registration or password endpoint/form.

`GET /login` exchanges a verified, enabled, explicitly associated identity for a
random local session and serves the shared panel document without another form.
This ends the cross-site OAuth navigation before asset/API requests need the
SameSite=Strict cookie, avoiding a redirect loop without weakening its protection.
An existing first-party session may redirect to `/`. Sessions
are bound to the exact Access assertion, provider binding, Access subject and
account version, and expire at the earlier of local duration or JWT expiration.
Cookies are HttpOnly/SameSite=Strict and host-only Secure on HTTPS. HTTPS responses set hostname-only HSTS (`max-age=31536000`), including denied and public asset responses; Access-generated edge responses require matching edge configuration. Every browser
POST requires the exact configured Origin and a session-specific CSRF header.
Logout revokes the local session and persists the assertion fingerprint until its
expiration in private `web/access-revocations.json`, then the browser visits
`/cdn-cgi/access/logout` to revoke Access and clear its application cookie. Local
`users revoke` also sets an issuance cutoff so old Access assertions cannot open
new sessions. Disable, unbind and rebind take effect on the next request.

Hosts advertise additive `machine_pairing_support` (0.9.4+), `machine_login_support` (0.9.12+) and `web_access_support` in their IPC descriptors and CLI
capabilities. IPC rejects `machine_login*` operations, and the portal rejects forwarding a sign-in registration, to a host without `machine_login_support`. The portal refuses to reuse a password-era or pre-pairing host. IPC rejects `machine_connect` before delivery to a host without `machine_pairing_support`, preventing fallback to older GitHub-token enrollment, and account edits
refuse to migrate the schema while one is running. A controlled Mac transition
updates the compatible host/CLI pair and preserves the previous assistant state.
The native transport remains unchanged and never accepts browser credentials.

Each web account gets an opaque-ID directory `web/profiles/<id>/`, its own settings,
map, SQLite data, file credentials and provider home, and a separate instance of
the same headless host binary. `PTA_PROFILE_DIR` selects that explicit absolute
profile; the existing desktop profile and Keychain identifiers remain unchanged
when it is absent. New web profiles use DeepSeek, with their own key, by default.
The portal and CLI scrub inherited app/provider credentials when launching isolated
hosts, preserve proxy/CA configuration, and use private credential files on all OSes.
These are application profiles under one trusted operator's OS account, not OS isolation. Admitted ordinary accounts use only their own API configuration and file credentials, never inherited environment values/mounts or the operator's keychain. Their data/map/repository paths are confined and rechecked for native CLI/MCP as well as browser calls. Provider probes, CLI sign-in, Git subprocesses, local coding and request/child creation on the shared OS identity fail closed; personal trusted machines remain the coding path. Provider catalogs for ordinary accounts are static API catalogs and never probe installed commands.

One account may instead use `pta web users add USER --current-profile` followed by a local identity association to operate
the existing GUI/headless host and its actual data without a copy or re-login.
The portal selects each IPC descriptor from the authenticated account, strips browser
transport headers and uses the existing instance bearer. IPC itself still rejects
Origin and never accepts cookies. A web command allowlist, immutable hosting/data
paths, canonical repository roots and confined imports prevent access to another
profile's data through GUI operations. Current-profile repositories already in the
saved desktop map remain available. Tenant/user identities cannot be reused across
profiles: portal operations and host start check them, and a duplicate new Microsoft
login is logged out locally before an assistant can start.

Graph URLs use optional `server.webhook_prefix` (empty and omitted for existing
profiles, `/webhooks/<opaque-id>` for isolated profiles). The portal forwards only
the matching notifications/lifecycle POST to that host's loopback service, with no
browser cookies or administration token. All existing Graph batch checks remain
in that host. One Cloudflare hostname covers the GUI and every user's callbacks.
The prefix is canonical and validated; it does not change OAuth scopes or redirects.
On a remote device the GUI offers the existing loopback redirect paste/forward
workflow, while GitHub uses its existing device flow. Activities open in the web tab.

The portal owns its own lock, starts enabled profile hosts for offline scheduling,
remembers explicit Assistant Start/Stop state in private `web/resume/<id>` files,
and stops only processes it started on exit. Disabling an account revokes access
immediately and its portal-owned host on reconciliation. The tunnel setup helper
`scripts/configure-web-cloudflare.py` needs a Cloudflare API token, creates a
dedicated remotely managed Tunnel/DNS route, saves its connector token privately
and refuses to replace unrelated DNS or Tunnel routes. The existing static landing
and desktop tunnel remain separate. `scripts/configure-web-access.py` separately
creates/reuses only the dedicated GitHub IdP and panel/Graph/icon Access applications,
rejects overlapping unmanaged resources, installs only explicit callback paths
exported by `pta web callbacks` before protecting the hostname, and verifies
readback before writing private portal settings. No broad `/webhooks/*` bypass is
allowed. The backend exempts only canonical notification/lifecycle POST paths and
GETs of the exact static icons and PWA manifest (`PUBLIC_ASSETS`, which the helper
also bypasses, because WebKit fetches a page's icons without cookies);
Graph forwarding and its existing batch authentication stay unchanged. The current
profile's separate desktop Graph hostname/tunnel remains unchanged. See the [web operating guide](../desktop/skills/personal-teams-assistant/references/web-access.md).

### Account and invocation authority (0.9.11)

The host derives its account binding from the canonical profile and the operator's
account registry. Each invocation carries that scope and its authenticated
transport inside Rust; JSON IDs, paths, owner flags and transport/maintenance
fields never grant authority. The profile binding is rechecked before dispatch,
including implementation operations that bypass the ordinary operations mutex.
Reassociation requires a fresh host. Rejections happen before diagnostics can
read or write data under a changed binding. Existing per-profile settings, sources,
notes, indexes, activity records, implementation ledgers and asynchronous results
retain their owning host; machine session summaries and call results retain their
existing machine checks. Graph callbacks still select only the exact bound profile.

IPC descriptors advertise additive `account_authority_support`, an account/version
binding and separate random local, browser and machine credentials. The portal
checks the expected binding before forwarding and uses only the appropriate
scoped credential. The host repeats browser operation/path checks and limits
machine authority to the existing coordinator protocol; nested calls retain their
transport through a task-local invocation. A machine cannot forward coding,
provider discovery or directory browsing into the coordinator's local OS context.
The new CLI/portal refuse older hosts before transmitting an operation; there is
no fallback to the operator bearer. A matched local installation upgrade may only
inspect (`snapshot`) and stop (`app_quit`) its older owner host to preserve the
existing running state; this private retirement path cannot perform other actions
or forward portal requests. Native GUI, CLI and MCP use the same dispatcher.
The native bearer and portal administration remain trusted local OS operations.

Explicitly admitted accounts can use the shared GUI, CLI and MCP with their own API
assistant, notes/index, sources, activity records/schedules, Microsoft/GitHub API sessions
and machine coordination. `shared_accounts_support` is mandatory before a host receives
ordinary-account requests or account-schema edits; no fallback to an older host exists.
The snapshot exposes only the current account identity and its local-execution capability.
The GUI translates account failures and explains personal-machine requirements.

Disable, revoke, unbind and rebind change the account version. Every checked browser,
machine and host request rejects stale authority. Graph callback forwarding checks the
host's exact binding too. OAuth completion rechecks authority before exchanging and
persisting tokens and before saving identity; GitHub device login also checks before
persistence. Daily snapshots and asynchronous results recheck before storing. Reconciliation
stops only tracked app-managed hosts whose account is disabled, removed or changed;
unrelated desktop/operator hosts are preserved. A new host is required after reassociation.

Without verified OS isolation, provider/coding rejection directs the user to a personal
trusted machine. Private profile directories, provider homes, working-directory limits and
tool-less prompts are not an OS security boundary. Different people sharing a computer
need distinct OS security contexts: switching app accounts cannot protect against someone
controlling the same OS account. No container sandbox is introduced here and none is silently assumed to exist;
variables are used only through the consumers of [Account variables](#account-variables),
which never run generic processes for a shared account.

### Account variables

A stored variable is the only secret an assistant account owns directly. Its user-facing fields are exactly a **name**, a **description** and a **value**; the host adds an entry ID, a version, timestamps and the encryption version as implementation metadata. There is no credential type, TOKEN/KEY suffix or key-pair structure, and no automatic import of existing credentials (the opt-in [migration](#credential-migration) copies selected ones). Existing application credentials, `STATE_ENCRYPTION_KEY` and the Teams OAuth vault are untouched.

- **Limits.** Names are environment-compatible identifiers (`[A-Za-z_][A-Za-z0-9_]*`, at most 128), unique per account without regard to case. Descriptions are required, one line of plain text of at most 500 characters without control or bidirectional-override characters. Values are 1 byte to 16 KiB of UTF-8 (newlines allowed, no NUL). At most 500 variables per account. Consumer-specific validation belongs to the consumer, not to a type selector.
- **Storage.** `variables.rs` keeps SQLite tables `account_keys` and `variables`, all qualified by an account key. A profile store (`Store::open_profile`) uses a random, stable account key written at first use and records the portal account ID it serves: a profile later associated with a portal account keeps its variables, and a profile bound to one account refuses another. Names and descriptions are clear metadata so they can be listed and searched; values exist only as ciphertext.
- **Cryptography.** AES-256-GCM-SIV (the existing dependency) with independent keys: every account has a random 256-bit data key, wrapped by a master key; values are sealed under the data key. The associated data of a value is a length-prefixed encoding of a variable-record domain string, the account key, entry ID, name, revision and data-key version, and the one of a wrapped data key uses its own domain with the account key and both key versions, so ciphertext moved to another account, entry, name or revision fails authentication. It never reuses the Teams state vault's key or domain.
- **Key custody.** Master keys are private files `keys/master-N.key` in a directory apart from the database. A key is generated only for a store with no key material and no variables; a missing, unreadable or wrong key for existing data fails closed (`not_ready`, exit 3) and never regenerates anything. Operator-local commands (`pta variables key backup|restore|rotate`, plus `verify`) are available on the native local channel only: they are neither browser, machine nor MCP/tool operations. `backup` writes the master keys, not values or ciphertext, to a new private file (never overwritten) that must be kept apart from the profile and its routine backups; `restore` reads that file on stdin and never replaces a different key with the same version; `rotate` re-wraps every data key under a new master key and re-encrypts the account's values under a new data key in one transaction after each value authenticated, keeps the earlier master keys so older database backups stay readable, and a failure changes nothing. A routine copy of `variables.db` alone is ciphertext without its keys; copying the whole profile directory also copies `keys/`, so exclude it from routine backups.
- **Trust model.** The operator/server decrypts for unattended operations; this is not end-to-end encryption and does not protect against an administrator or a fully compromised server (ADR 0001).
- **Operations (shared by GUI, CLI and MCP).** `variable_list` (optional `query`, `limit`), `variable_create`, `variable_update`, `variable_delete`, `variable_reveal`, `variable_entry_start|status|complete|cancel`, `variable_rotation_start` and `variable_audit`, and the operator-local `variable_verify`, `variable_key_backup|restore|rotate`. They bypass the profile operations lock like the implementation operations, are independent of settings revisions, and are refused to machine credentials. The browser may list, create, edit, delete, reveal and complete or cancel an entry; starting an entry or a rotation request, the audit and every key operation require the local channel. Hosts and CLI capabilities advertise additive `account_variables_support`; a CLI or portal refuses to send `variable_*` to a host without it.
- **Discovery.** List/search responses contain the entry ID, name, description, version and timestamps, plus pending protected-entry requests, never a value, ciphertext or key. Names and descriptions are untrusted text: the GUI sets them with `textContent`, and the tool descriptions tell agents they are data, not instructions.
- **Creation.** `variable_create` takes a client-chosen entry UUID, name, description and value and never overwrites. The same entry ID with identical content reports `replayed: true`; the same ID with other content, or another entry with an existing name, is a conflict (`state_conflict`, exit 6) that names the existing variable so the caller inspects first. The CLI prints the entry ID after an uncertain failure so a retry repeats the same creation; the GUI keeps one ID per typed form.
- **Protected entry.** A value reaches the host only from the GUI's masked field (a textarea masked by the engine with an explicit «Show the value while I type» choice) or from the CLI's standard input, which must be a pipe, never a terminal, never an argument (one final line break is not part of the value). No MCP tool, tool argument or result carries a value. An agent calls `variable_entry_request` with a name and description; the host keeps that request in memory for 15 minutes (at most 20 open, one per name; a host restart abandons it), the user completes it in Settings › Variables or with `pta variables entry complete REQUEST`, and the agent only reads `variable_entry_status`. Completion uses the request ID as the entry ID, so repeating it is a replay.
- **Authority.** Operations resolve the account from the host's binding, never from arguments (account, profile and transport arguments are rejected). Each portal account has its own profile, host, store and key directory; the portal allowlist includes the variable methods for ordinary accounts. Failures are logged by operation name, code and duration only. Migration of existing credentials is [its own workflow](#credential-migration).
- **Edit, rotate and delete.** `variable_update` takes the entry ID, the **version the caller saw** and a new description, a new value or both; the GUI sends them as two independent edits. A rotation keeps the ID, name and description (references keep working) and seals the value again under the new revision. A different current version is a conflict (`state_conflict`, exit 6) that names the version now stored and changes nothing, except that an identical repeat of an update whose reply was lost (current version = seen + 1 with the same content) is reported as `replayed`. An update that changes nothing is refused. `variable_delete` takes the same version, writes a **tombstone** (ID, name, deletion version and time; never a value) and removes the row in one transaction: a stale write, a replay of the creation or any later resolution of that ID fails with «was deleted» instead of bringing it back, an identical repeat of the delete is a replay, and the name becomes free again for a new entry with a new ID. Deletion does not revoke the credential at its external provider and cannot retract a value a program already received; the GUI and the tool say so.
- **Reveal and copy (human only).** `variable_reveal` is the only operation that returns a value, and only for one entry of the current account after an explicit tap in the GUI (Reveal, or Copy value). The in-process window marks its calls with its own transport (`Window`, `authority::from_window`) and the browser has `Browser`; a call without a marked invocation (a spawned task, the tray, a scheduler) counts as `Local`, so nothing reveals by default; the CLI, MCP, tools and `pta tools call` share the control endpoint's local token with agents (`Local`) and are refused, as are machines. A refusal leaves a `denied_client` audit event. The browser reply carries `Cache-Control: no-store` like every account reply. The GUI keeps a revealed value only in memory and the DOM, never in storage, a URL or history, and clears it on Hide, on changing tab or Settings category, when the page is hidden or unloaded, on logout and after 30 seconds. Copy writes the exact value (line breaks included) without showing it in a notice, and a minute later clears the clipboard only if it still holds exactly that value (compared by SHA-256 fingerprint, best effort; unrelated clipboard contents are left alone). There is no agent-facing reveal, copy or read tool.
- **Protected replacement.** An agent that needs a value changed calls `variable_rotation_request` (MCP; `variable_rotation_start` on the host) with the entry ID; the request records the version it saw and the user completes it like a creation (GUI or `pta variables entry complete REQUEST`). Completion rotates only if the entry is still at that version, so a typed value never overwrites a newer state.
- **Consumers.** A variable is used only through a consumer chosen in code (`consumers.rs`); the variable stays generic and the consumer's rules apply at use. Operations `variable_consumer_list|bind|unbind|check` and `variable_launcher_define|remove|run` (same dispatch, profile-lock bypass, `account_variables_support` gate and authority as the other `variable_*` methods; machines are refused; the portal allowlist admits the four `variable_consumer_*` methods, never launchers). Every use re-runs `authority::invocation` (live account binding and admission) and resolves the entry ID now: a deleted entry is a `state_conflict` («was deleted»), a pinned `version` that no longer matches is a conflict naming the current one, another account's ID is absent, and nothing falls back to another account, the environment or a stored credential. Results carry the reference (ID, name, version) and a status, never a value; uses and changes append `bind`, `unbind`, `use`, `launcher_define` and `launcher_remove` audit events.
  - *Built-in consumer `deepseek`.* A binding (table `consumer_bindings`: account, consumer, slot, entry ID; account-qualified, kept even after the entry is deleted so it fails closed) makes the DeepSeek API key come from the variable. `security` consults an installed `AccountSecrets` source before the environment, files and system store for configured application credentials (`secret_source` reports `variable`); a bound credential whose entry is gone, unreadable or invalid is an error, never another source. The host installs the resolver at start (`consumers::install`), so the service chain, local chat and `pta test providers` use it. The value is validated when chosen and at each use (8-256 visible ASCII characters, no spaces) and is held only by the running chain: a running assistant keeps the key it read at start, so bind, unbind and rotation report `restart_required`. `check` sends `GET /models` with the key as a bearer token to the fixed `https://api.deepseek.com` (no redirects, 15 s) and returns `ok`, `rejected`, `failed` or `unreachable`. Binding and `check` need confirmation (MCP, `confirmed:true`, CLI `--confirmed`); the GUI tap is the confirmation (Settings › Variables › Where variables are used).
  - *Launchers (generic local process).* A launcher is machine-local (`<profile>/launchers.json`, 0600, never synchronized): name, description, canonical program path and its SHA-256, fixed arguments (at most 32), a working directory inside the machine's allowed roots (the same `directories` check as implementation runs; empty roots grant nothing; the profile is refused), up to eight `ENV_NAME → variable entry ID` pairs and a timeout (1-600 s). `ENV_NAME` is validated in code and may not be a protected runtime or application setting (`PATH`, `HOME`, loader, allocator and profiler hooks (`LD_*`, `DYLD_*`, `MALLOC_*`, `GLIBC_TUNABLES`, `COR_*`, `CORECLR_*`, `DOTNET_*`), interpreter and module paths, `OPENSSL_*`/`SSLKEYLOGFILE`, proxy/certificate, editor/pager, `GIT_*`, `PTA_*`, `STATE_ENCRYPTION_KEY`, webhook, tunnel and OAuth names, compared without case). A run re-checks the program path and digest, the directory and the allowed roots, resolves every entry (all-or-nothing, optional per-name version pins) and only then starts the program with `env_clear`, the vetted minimal environment shared with provider CLIs and the selected values; stdin is closed and stdout/stderr are not captured, so no program output reaches an agent and no redaction is relied on. One run at a time; the result is `succeeded`, `failed`, `timed_out` (killed) or `not_started`, the exit code, the duration and the references used. Definition and run need confirmation and are available only to an installation owner on the application window or the local CLI/MCP channel: shared-portal accounts (no verified OS boundary, `check_shared_operation`), browsers and machine credentials are refused. A definition is only a proposal (`approved_at` unset): it runs nothing and resolves no value until the user approves it with `variable_launcher_approve {id, digest}` in the application window (Settings › Variables, which shows the command, folder and variables). Only the `Window` transport may approve, because the CLI, MCP and `pta tools call` share the local channel with agents; the digest must be the one shown, so a definition that changed since is not approved. Headless installations have no window and cannot approve a launcher. The environment is the protected execution channel; an approved program can still keep or forward what it receives, which neither the digest nor the minimal environment prevents.
- **Catalog synchronization.** The coordinator (the host that owns the account: a portal account's host, or the owner's own installation) is authoritative; every browser, window, CLI and MCP client of it already reads its store directly, and `variable_list` reports `sync: {mode: "authoritative", revision}`. An installation signed in to a coordinator (`implementation/connection.json`) instead keeps a **mirror** of the catalog: entry ID, name, description, version and timestamps plus the coordinator's revision, in the private file `variables/catalog-mirror.json`, qualified by coordinator origin, account number, machine ID and an opaque fingerprint of the account source. It never holds a value, ciphertext or key, and a connected installation opens no local value store for these operations, so there is no durable offline copy of a secret. `variable_list` on such an installation shows the mirror (offline inspection works) with `sync: {mode: "mirror", state, revision, synced_at, entries, attempted_at, error, conflict}`; `state` is `never`, `syncing`, `synced`, `error` or `conflict`.
  - *Coordinator side.* The machine protocol's coordinator calls (`app/implementation/fleet.rs`, authenticated by the machine credential and its account version) admit exactly `variable_catalog`, `variable_resolve`, `variable_create`, `variable_update` and `variable_delete`; every other `variable_*` method (list, reveal, audit, consumers, launchers, keys) stays unavailable to machines. `variable_catalog {offset, limit ≤ 100}` returns one consistent page ordered by entry ID: `schema`, `source`, `revision`, `total`, `offset` and `items` (metadata only). The **revision** is the sum of every entry version and every tombstone version, so each create, edit or delete adds exactly one and it only grows; key rotation does not change it. Pages of at most 100 entries keep the 500-variable catalog far below the 1 MB reply bound.
  - *Client side.* `variable_sync {reset?}` (CLI `pta variables sync [--reset]`, MCP `variable_sync`) reads all pages, restarting up to three times if the revision, total or source changes between pages, validates every entry as the store would (UUID, name and description rules, version ≥ 1, unique IDs and case-insensitive names, `revision ≥ Σ versions`, at most 500 entries, eight pages) and only then replaces the mirror atomically. `variable_sync_status` (CLI `pta variables status`, MCP `variable_sync_status`) reads local state only and is the retryable read path. The connected host's poll loop starts a background synchronization at most every 30 seconds (the first one right after sign-in) without delaying presence; a first `variable_list` with no mirror also synchronizes once. Failures keep the previous mirror and set a sanitized `error` (`dependency_or_network`, `not_ready` for an older coordinator or schema, `operation_failed` for a refusal, revoked machine or invalid snapshot, `state_conflict` for a stale revision, a different account source or a catalog that kept changing); no raw transport text is shown, and nothing selects a fallback account, coordinator or cache.
  - *Replays and restores.* A snapshot with a lower revision than the mirror, the same revision with different entries, or another account-source fingerprint is refused with `state_conflict` and changes nothing; `reset` discards the mirror first and is the only way to accept a coordinator restored to an older state. The mirror is discarded when the connection's coordinator, account or machine changes, on sign-in, on `machine_disconnect` and on `machine_connect`, so switching accounts never shows the previous catalog, revision or status.
  - *Edits from a connected installation.* `variable_create|update|delete` and the completion of a protected entry (`variable_entry_complete`; `variable_entry_start` and `variable_rotation_start` check names and targets against the mirror) are sent to the coordinator, which alone decides them with the same version rules as for any client: a stale version is `state_conflict` (the mirror is refreshed and `sync.state` is `conflict` with the message until the user synchronizes explicitly or a later edit succeeds), a deleted ID stays a tombstone, so neither a disconnected nor an old client can resurrect it, and an identical repeat is a replay. A value travels only inside a create or a value replacement, over the existing HTTPS machine channel to the coordinator that already decrypts for the account, and is never returned, logged or stored on the installation. An unreachable coordinator is reported as an uncertain outcome (`dependency_or_network`): edits are not queued or retried, so inspect after synchronizing. The coordinator audits update and delete without a value. `variable_reveal` on a connected installation is refused: reveal or copy from the portal or the coordinator.
  - *Not covered here.* Synchronization grants no consumer permission and never fetches a value; using one is the live, online operation of [Account standing](#account-standing-and-the-live-fence). Legacy credential migration is [its own workflow](#credential-migration).
- **Audit.** Every edit, rotation, deletion and reveal appends an event with time, account, action (`update`, `rotate`, `delete`, `reveal`, and for consumers `bind`, `unbind`, `use`, `launcher_define`, `launcher_remove`), entry ID and a fixed outcome word (`ok`, `replayed`, `stale`, `deleted`, `rejected`, `failed`, `denied_client`) to `variable_audit` (newest 5,000 kept). Events contain no value, name or description and are shown only on the local channel (`pta variables audit`, operator-local). Forged or malformed entry IDs, another account's entry, stale versions and malformed payloads are refused before any change.

### Unified application variables (0.10.1)

Settings › Variables is the single editor for application credentials and other stored variables. `DEEPSEEK_API_KEY` and non-internal names configured in `[secrets]` resolve through this account's encrypted variable store by name (case-insensitive); an explicit existing consumer binding still takes precedence. The legacy Credentials panel is removed. Reveal/Hide includes an eye icon and retains the human-only transport fence, audit and 30-second lifetime.

Before listing or first using application credentials on an authoritative installation, `app/variables/credentials.rs` imports existing `NAME_FILE`, environment or system-store values. Each import inserts ciphertext, decrypts it for comparison and commits an account-qualified completion marker in the same SQLite transaction. Originals remain untouched recovery copies. The marker prevents a restart from reimporting an older value after replacement or deletion. A different existing variable is preserved and reported as a conflict; the catalog stays readable so the user can review it. Missing originals do not complete migration, so a later import is still possible. The compatibility `credentials set/delete` commands edit these same variable entries.

Internal encryption, webhook, machine/control, tunnel/hosting, provider sessions and retired credentials keep their existing names, stores and lifecycle. They are not portable application variables. No profile, data directory, Microsoft token, encryption key or legacy audit is moved or deleted. The explicit cross-account migration tool remains under Advanced and still requires destination review; merely signing in never uploads this machine's originals into another account.

On signed-in execution machines, configured names resolve through the synchronized catalog and a fresh authorized `variable_resolve` exchange for each use, including tools running after startup. The synchronous credential contract bridges that exchange on a separate thread/runtime; account values are never persisted or used offline. Existing explicit consumer bindings retain their staged operation flow. Missing, deleted, revoked or unavailable variables never fall back to the environment or the old credential store. Removing an explicit binding returns to the configured named variable.

### Credential migration

An existing installation moves the credentials it already uses into the signed-in account with `app/migration.rs` (operations `variable_migration_inspect`, `variable_migration_run`, `variable_migration_status`; they reuse `variable_*` dispatch, so they share the `account_variables_support` gate, bypass the profile lock and are refused to machine credentials). It never changes the original stores, `STATE_ENCRYPTION_KEY`, profile IDs, data directories or Microsoft sessions.

- **Discovery.** `inspect` lists only the credential names this installation is configured for (`credential_names`: the DeepSeek key, the `[secrets]` allowlist…) with a safe origin word (`environment`, `file`, `system`; never a path or value), eligibility, the built-in consumer that would use it, the account variable already holding the name (ID, version, description) and the earlier outcome. The system environment is never scanned. `security::legacy_source`/`legacy_secret` read the installation's own stores even while a consumer is bound to an account variable. State-encryption, machine/control (`PTA_*`), webhook, hosting/tunnel (Cloudflare), provider-session (OAuth/session) and retired credentials, and protected runtime names, are listed as `excluded` with the reason and cannot be selected by any client.
- **Destination.** The reviewed account is named by an opaque `destination.key` (the coordinator/account/machine qualifier on a signed-in installation, a hash of the portal account or the installation otherwise) plus a human label. `run` must echo the key: another account, or one that changed since the review, is a `state_conflict` that transfers nothing.
- **Selection and review.** `run {destination, items[{credential, name?, description, existing?{action: use|replace, version}, bind?}], settings?}` takes at most eight items. Every item is validated before anything is written: configured and not excluded, name/description rules, an original that can be read and is valid for the account store and its consumer, no duplicates, `bind` only where a consumer exists, and a name already in the destination catalog (read live; a connected installation synchronizes first) needs an explicit `use` (the existing value must match; its description is kept) or `replace` (rotates the value at the reviewed version) naming the version the user saw. Otherwise nothing is transferred (`invalid_input`, or `state_conflict` for collisions) and the problems are listed. Descriptions are the user's: the host supplies none.
- **Protected transfer.** The host reads the value from its own store and creates or updates the variable through the ordinary `variable_create|update` path (locally, or forwarded to the coordinator over the machine channel). No value is an argument or result of any client operation, appears in a journal, audit event, log or file, or passes through an agent. The entry ID is deterministic for account and credential, so a repeated creation is a replay.
- **Verify, then switch.** After the write the host reads the entry back as a consumer would (`consumers::resolve_entry`: the local store, or a live `variable_resolve` on a signed-in installation), compares it with the original and applies the consumer's rules. Only then does `bind` call `variable_consumer_bind`. A failed verification (`verification_failed`) leaves the consumer on its original credential; `variable_consumer_unbind` returns the consumer to its configured named variable.
- **Durable outcome.** `<profile>/migration/<destination key>.json` (0600, qualified by account, no values) records per item `planned → writing → written → verified → complete`, with `uncertain` for a write whose outcome is unknown (coordinator unreachable) and `verification_failed`. Repeating the same `run` resumes: a completed item is only confirmed present; a `writing`/`uncertain` item first inspects the refreshed catalog and skips the write if the entry (or the rotated version) is already there, otherwise repeats the same idempotent write. Offline, revoked or key failures stop the remaining items (`dependency_or_network`, `not_ready`) with each item's stage reported; the reply is an error with `data.items`, and the original setup stays usable. An authoritative installation appends `migrate` audit events (entry ID and outcome word).
- **Settings.** `settings: adopt_account` (signed-in installations only) runs `portable_sync {reset: true}`, the existing «replace this computer's settings with the account's» with its private backup; folders, sign-ins and providers stay local. `inspect` shows the portable state so the user knows whether that would replace unsaved local changes.
- **Surfaces.** GUI: Settings › Advanced › Move existing credentials (choose rows, edit name and description, resolve a collision, optionally switch the consumer, confirm the destination account; both the application window and the portal). CLI: `pta variables migrate inspect|status|run CREDENTIAL --destination KEY --description TEXT [--name N] [--bind] [--existing use|replace --expected-version N] [--settings] --confirmed` (one credential per command; the host reads the value). MCP: `migration_inspect`, `migration_status`, `migration_run` (needs confirmation; no tool accepts a value). The portal allowlist admits the three methods for the account's own host.
- **Still local.** Microsoft sign-in, coding-provider and GitHub/Azure CLI sessions, repository folders and allowed directories are never migrated; `inspect` lists them as «remains local». Credentials with no consumer yet (for example a `[secrets]` token for a tool) are stored as account variables but nothing switches to them; their configured names now resolve through Variables.

### Account standing and the live fence

`app/standing.rs` is what an installation signed in to a coordinator knows about its authority. The coordinator is the only authority for the account's variables and machines, so every exchange (`fleet::exchange`) classifies its outcome as a typed `Refusal` that travels in the error chain: `Rejected` when the portal answers 401/403 or the local machine credential is missing (the machine was revoked or signed out, the account was disabled, rebound or its version changed) and `Unavailable` for every other failure (network, timeout, 5xx). `standing::note` records each one (the 2-second presence poll, the Teams lease check and every account call) as `live`, `offline` or `revoked` with the time of the latest exchange and of the latest `live` one; `signed_out` is simply no `connection.json`, and `unknown` is a signed-in host that has not exchanged anything yet (an offline restart starts there). The record is qualified by the link (coordinator, account, machine) and is not reused for another. `standing` appears in `variable_list`, `variable_sync`, `variable_sync_status`, `portable_status`, `portable_sync` and `variable_consumer_list` with `state`, `coordinator`, `checked_at`, `last_live_at`, `variables_usable`, a `recovery` sentence and an opaque `account_key` (a hash of the link, never an identity) that the GUIs use to notice a switch. It never carries a token, a value or raw transport text. A refusal is not sticky: the next successful exchange is `live` again.

- **Cached state is readable, use is not.** Offline, revoked or stale, the mirror and the portable replica stay inspectable with their own `state`/`synced_at` (`stale` says the loaded copy is older than the account's). Anything that would use an account variable needs a live answer at that moment: `variable_consumer_bind|check`, `variable_launcher_run`, and the credential lookup of an operation. Offline is `dependency_or_network` (exit 5) and a refused credential is `not_ready` (exit 3) with the sign-in instructions; removing a local authorization (`variable_consumer_unbind`, launcher removal) never needs the network.
- **Online resolution (`variable_resolve`).** The coordinator serves one entry's value to a machine credential of the same account (`{id, version?}` → metadata and value), through the same `use_entry` rules as a local use (deleted, rotated-since-pinned and foreign IDs fail), and audits a `use` event with the entry and outcome. It is the live check of the machine credential, the account version and the revision at once, and it is the only value a machine can obtain: not a reveal, list or audit. The reply must name exactly the asked entry (and version) or it is discarded. Consumers on a signed-in installation (`app/consumers/connected.rs`) never open a local value store: bindings are references in `variables/account-bindings.json` and launchers in `launchers-account.json`, both qualified by the link and read as empty under any other link, so an account switch (or an interrupted sign-out) cannot expose the former account's references; the installation's own bindings and `launchers.json` apply again only when it is not signed in. Launchers keep all-or-nothing resolution before a start.
- **Credential lookup for the assistant.** `security::AccountSecrets` is synchronous, so a signed-in installation asks the coordinator at the start of each operation that may need the bound DeepSeek key (`consumers::stage`: assistant start after the lease check, local chat, `test_providers`) and holds the value only in memory for 60 seconds (or a recorded denial per credential). The lookup uses only that value: no staged value is a denial, never the environment, the system store or a local binding. A late answer is dropped if the installation signed in elsewhere meanwhile, and any `revoked` observation, sign-out or account change clears staged values and pending protected-entry requests. A running assistant keeps what it read at start (the existing contract); the Teams lease check still stops it on revocation or a lost lease and nothing restarts it or retries a send.
- **Sign-out and switching.** `standing::forget_account` runs on sign-in, sign-in finish and `machine_disconnect`, which hold the portable synchronization gate across the whole switch (so a synchronization read for one account can never install after the switch to another): it resets the standing, discards the catalog mirror and the portable replica status, drops staged values and pending entries, and takes the former account's portable configuration and verified notes out of the profile (`portable::leave`: the portable fields return to a fresh profile's, a private backup is kept in `portable/backups`). A durable `portable/account-content` marker, written before an account's state is installed and removed only after it was cleared, makes an interrupted install or clear still count. A profile that never installed an account's state (an owner's own configuration, kept by a conflict) is left untouched; local identities (paths, repository folders, sessions, Microsoft sign-in) are not portable and stay. `machine_disconnect` always succeeds locally and is safe to repeat: a coordinator that already refuses the credential counts as notified, an unreachable one leaves the machine listed there until another client revokes it (`coordinator_notified: false`). Stored data on the coordinator and every account's own state are never touched. The GUIs keep an epoch: every account reply carries the `account_key`; a reply requested before a switch is dropped and one for another key clears revealed and typed values, lists, consumer results and the account panel before drawing, so a late answer never fills the next account's screen.
- **What is not promised.** There is no durable offline value cache. A program that already received a value (a launcher's child, a check in flight, a running assistant) keeps it; revocation cannot retract it and does not revoke the credential at its provider. The user rotates it there and replaces the variable's value. Detection is at the next exchange (seconds with the poll running), not instantaneous.

### Account configuration

The account's **portable configuration** follows it to every installation signed in to its coordinator ([CONTEXT](../CONTEXT.md)). `portable.rs` is the only definition of what travels, as a positive allowlist; a field added to `Config` or `KnowledgeMap` stays local until it is added there deliberately.

- **Allowlist.** Settings: `llm.language`, `llm.style`, `llm.chain`, `policy.greeting`, `policy.max_context_chars`, `policy.max_message_age_seconds` and `policy.sensitive_patterns`. Collections: sources (ID, description, topics, enabled, external processing, `allowed_conversations`, `allowed_senders` and the access definition: URL/tool definitions, or the repository **alias** with a relative path), contexts, questions with their associated requests, and verified notes. Never portable: data and repository paths, `repositories` bindings, allowed roots, bind, public URL, tunnels and webhook prefix, `[secrets]`, Microsoft tenant/client/user and chat IDs, `allowed_chats`, `allowed_senders` of the policy, people profiles, legacy cases, activity records and settings, the knowledge-index settings, machine/control credentials, internal keys, and Microsoft, GitHub, Azure and coding-provider sessions. `Document`, `Settings` and the patch types use `deny_unknown_fields`, so a local field cannot be smuggled into a snapshot or a change.
- **Revision.** The coordinator's revision is `{generation, digest}`: the digest is a domain-separated SHA-256 of the canonical document plus its notes, and the generation (private `portable/revision.json`) moves forward whenever the digest differs from the last one it observed, however the content was changed (GUI, CLI, MCP, a hand edit or a forwarded change), so it only grows. A change is checked against the digest, not the counter. The installation shows the **loaded** revision (installed in its profile) next to the **saved** one (the newest the coordinator reported).
- **Coordinator side.** The machine protocol admits exactly `portable_snapshot`, `portable_apply`, `portable_note_save`, `portable_note_remove` and `portable_records` (machine credential and account version as for the variable catalog; windows, the CLI and browsers are refused; no other method is proxied). `portable_snapshot {section}` returns `config` (the document, its revision, the account-source fingerprint and the note count) or `notes` in pages of 8 ordered by ID; it refuses a document larger than 900 kB or more than 2,048 notes instead of truncating. `portable_apply {base, patch, unavailable}` holds the profile operations lock, rejects a `base` that is not the current digest as `state_conflict`, applies the patch to the full document, re-validates with the knowledge-map and configuration rules and the real `validate_local`, and commits through the journaled `commit_settings` without restarting a running Teams service (the existing «restart to apply» notice shows). A note change names the content token of the note it read; a note changed since is a conflict (timestamps have a one-second resolution, so they are not used). A patch can **never broaden access** (`Patch::apply_to`): a new source must be disabled with no audiences or external processing; an existing one may not gain `enabled`, external processing, an audience entry or an unrestricted audience, nor change its destination while enabled; narrowing is allowed. Granting access is done on the coordinator's own surfaces.
- **Installation side.** `portable_sync {reset?}` (CLI `pta account sync [--reset]`, MCP `portable_sync`) reads the config document and every note page (restarting up to three times if the revision, total or source changes in between), validates them as the coordinator would (`Document::check`, note rules, digest equality) and installs them under the operations lock: settings are applied to the profile's own `Config`, sources whose repository alias is not bound here (or whose file source is not readable) are left out and recorded as **unavailable** together with the questions that read only them, contexts and questions that lose references are `partial`, local bindings, people, cases and identity are kept, the whole is validated with `validate_local`, committed with the journaled `commit_settings`, notes replaced in one transaction (`Index::replace_notes`) and `portable/replica.json` records the link (coordinator, account, machine), the source fingerprint, loaded and saved revisions, the digest of the installation's own projection right after (`applied`) and the unavailable items. Nothing starts Teams, selects a machine, enables a root, installs or signs in to a provider, or defaults a source: the document's flags are installed exactly. A profile is **pristine** when its projection equals a freshly created profile's; only then does the first synchronization install without `reset`. Otherwise, and whenever the profile's projection differs from `applied` (unsaved local changes, a hand edit, `config import`), nothing is replaced: `state_conflict` with `local_changes`, and the equal-revision check still records the newest saved revision. `reset` backs up the portable parts being replaced to `portable/backups/replaced-<time>.json` (private, last three) first. A different account fingerprint, a lower generation, a different coordinator/account/machine link or an invalid snapshot also change nothing (`state_conflict`/`operation_failed`); a changed link discards the replica and its reported status.
- **Edits from a connected installation.** `save_settings` (GUI, `config set/apply`, question association) computes the patch between the profile's previous and next projections. An empty patch is a local-only save (works offline). Otherwise the installation needs a loaded replica equal to the saved revision with no unsaved local changes, sends `portable_apply` with the loaded digest and the unavailable source IDs (so a context or question edited here keeps references only the account can resolve, and unavailable sources can be neither edited nor removed from here), and saves locally only after the coordinator accepted; on acceptance with `previous == loaded` the new revision becomes loaded and saved. A conflict records `sync.conflict`, saves nothing and tells the user to synchronize; an unreachable coordinator saves nothing (`dependency_or_network`); never queued or retried. `notes_save`/`notes_remove` do the same per note. A deletion therefore cannot be undone by an old copy: the old client is `stale`/conflicted until it synchronizes, and replacing the notes removes what the account removed.
- **Status.** `portable_status` (CLI `pta account status`, MCP `portable_status`) reads local state: `mode` (`replica` or `authoritative`), `state` (`never`, `syncing`, `synced`, `stale`, `diverged`, `conflict`, `error`), `loaded`/`saved`, times, a sanitized `error`/`conflict`, `local_changes`, `unavailable`, `local_setup` (repository folders to connect, providers not installed or signed in, Microsoft sign-in, empty coding directories) and the allowlist. The connected host's poll loop synchronizes at most every 30 seconds, the first time right after sign-in, without delaying presence. The GUI shows it in Settings › General › **Account configuration** (only on a signed-in installation): state badge, loaded versus account revision, Synchronize now, the local setup list, and a two-tap «Replace this computer's settings with the account's» when there is something to resolve. Hosts and CLIs advertise additive `account_portable_support`; `portable_*` is refused to a host without it, and the portal allowlist admits `portable_sync` and `portable_status` (a portal account's host is its own coordinator, so it reports `authoritative`).
- **Retained records.** Records that stay on the coordinator (the saved daily task record) are read through `portable_records` / `account_records` / `pta account records`: read-only, one of two fixed kinds, reply bounded to 900 kB, authorized by the machine credential and account. It is not a proxy and copies no database or history.

### Account setup and readiness

`app/readiness.rs` composes the first-run path ("add this computer to my account and configure the app") without a second implementation of anything: `setup_readiness` (CLI `pta setup status [--expect NAME]...`, MCP `setup_status`, GUI Home › Your account on this computer) is a read that calls the operations that already own each fact and orders them as a person meets them. It runs outside the operations lock, is refused to machine credentials, takes no authority from its arguments (`expect` is the only one: up to 20 variable names, validated like any name) and is listed for browser sessions so an ordinary portal account can read its own.

- **Steps.** `coordinator` (connected, signed out, a sign-in pending, ended without trust, or not wanted), `connection` (the latest `standing`: live, unknown, offline, revoked), `machine` (this computer on the coordinator's machine list, which is the same list every client shows), `configuration` (the portable state, loaded versus saved), `variables` (catalog availability; each `expect` name is `present` with id and version, `waiting` for a pending protected entry or `missing`; a consumer bound to a vanished variable is `attention`), `migration` (the journal; `done` only when verified), `providers` (the existing local-setup check), `roots` (count and paths of the directories this computer allows; none is a safe default), `teams` and `versions`. Each carries `scope` (`coordinator` or `this_machine`), `required`, `state` (`done`, `todo`, `waiting`, `attention`, `unknown`, `optional`, `not_applicable`), a fixed English `detail` (the GUI translates it by exact match; `scripts/test-ui-i18n.cjs` fails when a text has no catalog entry), small `facts` and `actions` naming a GUI place, a `pta` command or a tool call. `next` is the first required step that is open, else the first open optional one.
- **Distinct states.** Configured, running, received and sent are different facts: `teams` reports the Microsoft sign-in, whether another machine is selected, whether the assistant runs, and from the recorded jobs how many messages arrived and how many answers were sent (simulations excluded); only `running` with a sign-in is `done`. Installed, running and available versions are separate, and a newer installed version than the running one is `attention` (restart). Account scope and this-computer scope never merge.
- **Live check.** For a signed-in installation the report performs one coordinator exchange (the machine list) through the same account call as synchronization, so the standing it shows is current: an unreachable coordinator is `offline` (nothing is used, configuration stays readable), a refused credential is `revoked` (sign in again) and neither is confused with the other.
- **What it never does.** It never signs in, trusts a machine, enters, reveals or returns a value, creates a request, grants a directory, installs or signs in to a provider, changes an audience, starts Teams, migrates or updates anything; every step that needs one of those names the person or the operation. A browser session is never a machine: the `machine` step is `not_applicable` for it and the machine list is not touched. Variable descriptions, provider messages and names are not copied into `detail` or `facts` (names appear only for the caller's own `expect` list).

### Installation updates: discovery and staging

(Applying a prepared pair is [the next section](#applying-an-update-restart-and-rollback).)

`maintenance.rs` (core, no application dependencies) and `app/maintenance.rs` (host operations `crate_update_status`, `crate_update_check`, `crate_update_stage` and `crate_update_dismiss`, which bypass the profile operations lock because a build takes minutes) let the owner of a computer find and prepare a newer release of this exact package. Discovery and staging **install nothing**; installing the prepared pair is [the next section](#applying-an-update-restart-and-rollback). The shared server's timer (`scripts/vps-update.py`) is independent and never calls any of it.

- **Versions.** Status keeps `running` (the host's own version), `installed` (read from Cargo's install record next to the executable) and `available` apart. `available` is the newest **stable, not yanked** version of `personal-teams-assistant` in the sparse index that is greater than both the installed and the running one (numeric `MAJOR.MINOR.PATCH` ordering, so 0.10.0 > 0.9.0); pre-releases and build metadata, yanked versions, lines about another crate and malformed lines are ignored, and an answer that does not describe this crate at all fails the check instead of reading as «nothing newer». `restart_required` is true when the installed version is newer than the running one (the existing outdated-host retirement handles it).
- **Pinned source.** The registry is the constant `https://index.crates.io` and the crate is `personal-teams-assistant`; the request is `GET` on the crate's index path, with no redirects, 20 s and 4 MiB bounds and no credentials. No argument, description, browser field or model output chooses a URL, crate, registry, directory or command: `crate_update_stage` takes only `{version}` and the version must equal the newest the registry lists *at that moment* (a stale or forged one is `state_conflict`), and unknown or authority-bearing fields are rejected. The installation root and features come from the running executable's own location and Cargo's record, never from input. A source replacement in the user's own `CARGO_HOME` configuration is the user's configuration and is honored by Cargo.
- **Supported installations.** The executable must sit in `<root>/bin` with `<root>/.crates2.json` holding exactly one record for this package from crates.io (`registry+…crates.io-index` or `sparse+https://index.crates.io/`), a release profile, both binaries (`personal-teams-assistant`, `pta`) and only the `gui` feature. A development build, a `--path`/`--git`/custom-registry install or a custom feature gets a `diagnostic` and `can_stage: false` instead of a silently different package or feature set.
- **Authority.** Check, stage and dismiss need `is_local_owner`: the control endpoint's own token or the application window (`Transport::Local|Window`) on a profile that is an owner and not a shared portal account. A portal session, a machine credential and an ordinary account are refused (`authority_denied`); the portal allowlist admits only `crate_update_status`, which answers `{managed: "server", can_stage: false, message}` without versions, paths or build details. A model-supplied `confirmed` is not authority: the CLI (`--confirmed`) and MCP (`update_stage`, an `External` tool) ask the user, and the GUI button is the user's explicit request. No download or build ever starts on its own; the host only checks the registry (read-only) about every 6 hours (at most every 12 h, first after 90 s) on an owner's supported installation, and the Home notice can be dismissed per release.
- **Staging.** `crate_update_stage` runs `cargo install personal-teams-assistant --version X.Y.Z --locked --root <profile>/maintenance/staged/X.Y.Z.partial/root --color never` plus the installed choices (`--no-default-features`, `--features gui`, `--all-features`, `--target` only when it differs from the compiler's host), in the background, one build per profile (`state_conflict` otherwise). The old executables are never opened for writing and keep running; any earlier prepared pair is replaced. Before building it checks that Cargo runs and satisfies the release's `rust-version` (`not_ready` with `rustup` advice otherwise) and, once built, verifies the pair (`verify`): Cargo's own record in the staging root names exactly this version from crates.io with the installed feature choice and both binaries; `pta --version --json` and `personal-teams-assistant --version` (a flag that prints one line and exits, so it never starts a host) report the same version; SHA-256 and size of each are stored in `manifest.json`. Only then is `X.Y.Z.partial` renamed to `X.Y.Z`. A failed build or verification removes the partial directory and records the error.
- **Build environment.** Cargo runs with `env_clear` and only an allowlist (`PATH`, home and Cargo/Rustup locations, temporary directories, Windows and macOS toolchain discovery variables, compiler and `pkg-config` locations, proxy and CA variables) plus fixed `CARGO_TERM_COLOR=never`, `CARGO_TERM_PROGRESS_WHEN=never`, `CARGO_INCREMENTAL=0`. Account variables, credentials, registry tokens, `RUSTFLAGS`, `CARGO_BUILD_*`, `PTA_*` and every other variable are dropped; registry credentials of another account are never imported. The captured output is bounded (last 20 lines of 300 characters, redacted), shown only to the local owner and never contains the environment; known failures (no C compiler or linker, missing GTK/WebKit packages, no disk space, network) add a fix.
- **State.** Private `<profile>/maintenance/status.json` (schema 1: last check time and result, newest release seen, dismissed version, last staging record; no path or secret) and `staged/<version>/{root,manifest.json}`. A build recorded as running by a process that no longer exists is reported `failed` («stopped before the build finished»). `state` is `idle`, `staging` (with `phase` and compiled-package progress), `staged` (only while the files still have the recorded sizes and the version is still newer than what is installed and running) or `failed`.
- **Surfaces.** GUI: a Home notice (prepare or dismiss; install once prepared) and Settings › Advanced › Updates (versions, diagnostics, progress, failure with the build tail, installation progress and outcome); in the portal the panel shows only the managed-server notice. CLI: `pta update status|check|stage VERSION --confirmed|apply VERSION --confirmed|cancel|dismiss VERSION`. MCP: `update_status`, `update_check`, `update_stage`, `update_apply`, `update_cancel`, `update_dismiss`. `status` makes no network call.
### Applying an update: restart and rollback

`crate_update_apply {version}` (CLI `pta update apply VERSION --confirmed`, MCP `update_apply`, the desktop's Install update, which needs a second press), `crate_update_cancel` and the status fields `can_apply`, `apply`, `deferred` and `apply_unsupported` complete the update on the owner's computer. They need the same `is_local_owner` authority as staging, and the version must be the prepared one whose files still match `manifest.json` byte for byte. No path, URL, command or package is an argument. The portal allowlist does not admit them, so an ordinary account or a machine credential cannot replace executables, and the shared server's timer remains the only thing that updates the server.

- **Request.** The host holds the profile operations lock (so nothing new starts while it decides), takes the maintenance lock, recovers an interrupted earlier update, and **defers** if anything an update would interrupt is running in any affected profile: the profile itself and the isolated profiles of a portal under it. Checked: Teams jobs being answered, sent or refined (`assistant.db`), an activity review or task being written, implementation runs and child sends (`implementation/registry.json`, `runs.db` agent and request runs), a migration, a protected variable entry waiting for its value, and a profile operation that does not release the lock within two seconds (a configuration or variable write, a chat). A database that cannot be read counts as work. A deferral is `state: deferred` with fixed, path-free reasons; nothing is stopped, no journal is written, and the request is retried every 30 seconds until it can proceed or `crate_update_cancel` withdraws it. The request also refuses when the safety copy or the new executables would not fit on disk (`not_ready`, with the fix), and on a headless host started by a systemd unit (`INVOCATION_ID` with `--headless`), which would start a second copy: that one updates through its service (`cargo install … --locked --force`, then restart the unit).
- **Journal and lock.** `<profile>/maintenance/journal.json` (atomically replaced, private) records the update's ID, versions, install root, the prepared manifest, what the previous host was doing (launch flags `--headless`/`--host`, assistant running, active subscriptions, tunnel), the affected profiles, the digests of the executables being replaced, the data copies and each completed step, in the phases `requested`, `stopping`, `backing_up`, `replacing`, `restarting`, `verifying`, `committed`, `rolling_back`, `rolled_back` and `failed`. `apply.lock` is held by whoever drives the update for as long as it does, so a second update cannot run and a dead driver releases it. An unfinished journal whose lock is free and that was last written more than 60 s ago is an interrupted update: `recover` undoes it (status, a host start and the CLI's host start all do this first); within 60 s it is the hand-over between host and helper and is left alone. No host is started while an update is in progress (`pta` says to try again; `PTA_UPDATE_HANDOVER` marks the host the helper itself starts), and `pta update status` reads the journal directly while the host is down.
- **Helper.** There is no separate updater: the helper is `personal-teams-assistant --maintenance-apply`, run from the **prepared** copy (so it never holds the installed files, which matters on Windows). It re-checks the work list, asks the running host to quit with the ordinary `app_quit` (assistant and tunnel stop first), waits for the profile lock to be released (a host that does not quit leaves everything unchanged: `rolled_back`, «nothing was changed»), copies the data, replaces the executables, starts the new host with the previous launch flags, asks it to start the assistant only if it was running, waits for the health check and commits.
- **Replacement.** Before anything changes, every database (`*.db` in the data directory, the profile and `implementation/`) is copied with `VACUUM INTO`, plus the profile's `*.toml` and `implementation/registry.json`, and Cargo's two install records, under `maintenance/backup/<id>/`. Each executable is replaced by: a copy of the prepared file next to it (verified against the manifest digest), the live file **renamed aside** (`.name.<id>.previous`; Windows allows renaming a running image, which is why nothing is overwritten in place) and the copy renamed into its name, with bounded retries for a scanner holding the file; then this package's entry in `.crates.toml`/`.crates2.json` is replaced by the prepared root's, leaving other packages' entries alone, so Cargo later sees the new version and the same install root, features and target. A crash or failure at any step leaves a state the undo understands; every step has an inverse that is safe to repeat.
- **Health and rollback.** The new host must answer a snapshot with the new version; if the assistant was running it must run again (started once by the helper, never retried as a send), with active subscriptions and the tunnel as before. Failure of any step, or no health within three minutes, rolls back: the new host is stopped, both previous executables and Cargo's records are restored and checked against the digests taken before, the previous host is started with the same flags and the assistant restored (the safety copy is then deleted; it stays after a failed rollback or an interrupted update). The data keeps what happened meanwhile; only if the previous version does not start on it is the safety copy put back (`data_restored`), and if that fails too the outcome is `failed` with a recovery path (reinstall the exact version with `cargo install … --locked --force`; nothing is deleted). The schema of the data is additive, so the previous version normally reads what the new one wrote; the copy covers the case it does not. The helper never touches a Graph send or a work-item write: it waits for them (deferral) and the assistant's own start/stop owns Teams ownership, the lease and the account, none of which the update changes.
- **After success.** `committed` is the only success, written after the health check; `installed` or `running` alone never mean done. The helper then refreshes the **application's own** skill copies: only directories registered by `pta skill install` and still identical to the manifest `.pta-skill.json` it wrote (version and SHA-256 per file); modified or extended copies are never overwritten and are reported with how to reinstall, and the notes always say that agents keeping `pta mcp` running must reconnect to read the new catalog. The skill and catalog embedded in the binary report the new version immediately. The backup, `.previous` files and the prepared pair are swept by the new host once no update runs (a program still holding an old file on Windows only delays that).
- **Not covered.** The update cannot see work in a profile that is not under this profile (an unrelated host started with another `PTA_PROFILE_DIR`); a host that exits before the helper's last check is fine, but one that starts work between the helper's check and the quit is stopped by the quit like by `pta app quit`. A rollback after the new version has run cannot recover work only the new version could read. Cargo's own lock is not taken: do not run `cargo install` for this package while an update is applying.


### Headless host (Linux and servers)

```sh
cargo install personal-teams-assistant --no-default-features --locked   # no Tauri/WebKit
personal-teams-assistant --headless --start                              # foreground; `--start` starts the service
```

- Without the `gui` feature the binary is always headless; with it, `--headless` or `PTA_HEADLESS=1` force it. Same profile, contract and operations as the GUI; operated only with `pta`.
- It runs in the foreground: `pta app quit`, SIGTERM or Ctrl-C stop service and tunnel before exiting. A second host on the same profile exits with code 1. Logs go to stderr (no ANSI outside a terminal), fit for journald.
- `--start` tries to start the service; if it fails, the host stays alive to diagnose with `pta status/doctor/audit`.
- Remote Microsoft login: `pta auth microsoft login --no-browser` returns the URL; after authorizing on any device, the browser cannot open `http://localhost:PORT/?code=…`; that URL is pasted into `pta auth microsoft finish --redirect 'URL'` and the host forwards it to its own loopback listener (`forward_microsoft_redirect`: same pending port, rejected at once if the callback does not accept it). Alternative: migrate an existing profile with `pta config import` plus `STATE_ENCRYPTION_KEY`.
- The server still needs a stable HTTPS URL to the listener (Cloudflare tunnel with a token) and must not coexist with another active instance of the same account: it would duplicate answers and cause loops in the personal chat.

Known credentials: `DEEPSEEK_API_KEY` (required at start only if DeepSeek is active in `llm.chain`; otherwise `credentials list` shows it as `unused`), `GRAPH_WEBHOOK_SECRET` and `STATE_ENCRYPTION_KEY` (both generated at the first start if missing), `CLOUDFLARE_TUNNEL_TOKEN` (tunnel mode with a token), `GITHUB_OAUTH_TOKENS`, and those mapped in `[secrets]` (e.g. `AZURE_DEVOPS_TOKEN`). `TYPESAFE_API_KEY` is retired (`app::RETIRED_CREDENTIALS`): nothing reads it, it cannot be set, and a stored one is listed as `retired` so it can be removed; it is never deleted automatically.

**Local development without Keychain prompts (macOS).** Every `cargo build` produces a new ad-hoc signature, so the Keychain treats each build as a different application and asks again for the items of `personal-teams-assistant.default`. Resolve the credentials from private files instead. Bootstrap once (each read may ask for the login password; let the human click "Always Allow" — `/usr/bin/security` is Apple-signed, so that grant sticks):

```sh
mkdir -p ~/.config/pta && chmod 700 ~/.config/pta
for n in STATE_ENCRYPTION_KEY GRAPH_WEBHOOK_SECRET DEEPSEEK_API_KEY AZURE_DEVOPS_TOKEN GITHUB_OAUTH_TOKENS CLOUDFLARE_TUNNEL_TOKEN; do
  f="$HOME/.config/pta/$n"
  if v=$(security find-generic-password -w -s personal-teams-assistant.default -a "$n" 2>/dev/null); then
    printf '%s\n' "$v" > "$f" && chmod 600 "$f"
  else
    rm -f "$f"
  fi
done
```

Then `source scripts/dev-env.sh` before `cargo run` / `cargo tauri dev`: it exports `NAME_FILE` for every non-empty file in `~/.config/pta` (override the directory with `PTA_DEV_CREDENTIALS_DIR`). `STATE_ENCRYPTION_KEY` must keep its current value or `assistant.db` cannot be decrypted. Reads use the files; `pta credentials set` and the GitHub login still write to the Keychain.

Invariants:

- `STATE_ENCRYPTION_KEY` (base64 of 32 bytes) encrypts the OAuth tokens in `vault` with AES-256-GCM-SIV (AAD `teams-oauth-v1`). It cannot be replaced or deleted while `assistant.db` exists; importing a different key is rejected (`validate_state_key`).
- A database is never reused with another tenant/client/user (`protect_identity`).
- Profile writes: temporary 0600 file + atomic rename; `commit_settings` writes a journal and rolls back on failure; the next host recovers a pending journal.
- Directories 0700 / the account's ACL on Windows.
- On Linux the file store keeps values in clear (protected only by permissions), next to the database whose tokens `STATE_ENCRYPTION_KEY` encrypts. On a server, prefer systemd credentials or a secret manager mounted through `NAME_FILE`.

## 6. Message pipeline

Input: webhook or polling → `Store.enqueue(resource)` → worker → `Pipeline::process` (`src/pipeline.rs`).

```mermaid
flowchart TD
  M[Incoming message] --> E{Eligible and clean?}
  E -- no --> I[Ignored]
  E -- yes --> Q[Identify configured question by meaning]
  Q -- none or unavailable --> R[Unanswered for review]
  R --> A[Associate with a question or create one with sources]
  Q -- match --> S[Intersect question sources with authorized sources]
  S --> F[Read fresh evidence for actual requested dates]
  F --> V[Retrieve good and bad evaluations for this question]
  V --> G[Generate response]
  G --> C{Evidence, links, sensitive data and rejected-repeat checks}
  C -- fail --> R
  C -- pass --> D{Observation mode?}
  D -- yes --> P[Proposal]
  D -- no --> T[Re-read message and send once]
```

Details that matter when changing it:

1. **Eligibility** (`teams::IncomingMessage::eligible_in`): a user message, not deleted, not own (except a validated personal chat after `enabled_at`), ≤16,000 bytes, within `max_message_age_seconds`, the global `allowed_senders`, and in groups only with a real mention by Graph ID (never by `@name` text).
2. **Question recognition.** Loaded maps initialize the configurable Questions registry (§6.13). Exact owner-associated requests match directly; other wording is confirmed semantically with closed question IDs and a confidence threshold. No match, unavailable recognition or unavailable sources leaves the message for review. Legacy built-in case routing is not used by loaded profiles; only direct library maps with `questions: None` retain it for compatibility.
3. **Context and follow-ups.** `MessageAdapter::history` reads the `HISTORY_MESSAGES` (10) earlier messages of the same conversation (Graph: recent page of `chats/{id}/messages` by `createdDateTime desc`; excludes deleted messages, system events and those after the current one), once per message. Each carries its author (`me`, `assistant` if it is a recorded output of the app, or the display name) and local date/time; it is redacted, bounded to 6000 characters (the most recent are kept) and ends with the time of the current request. It goes as `conversation_history` to `classify_intent`, `standalone_request` and `generate_response`: it helps interpret the request, never as evidence. If Graph fails, it continues without history (`conversation_history_unavailable`). Besides, `conversation_context` keeps the last exchange per conversation (expires after 30 min): the resolved question and the answer **without** its links (copied URLs would fail verification). «dame más detalles», "tell me more" and equivalents reuse that question as the tool query. With another message, some authorized tool and either context (history or last exchange) or, without context, an authorized Wiki source and a request that is not a status question, `LlmProvider::standalone_request` rewrites the request as a standalone one (`question`) and extracts the topic to search (`topic`), e.g. «¿cómo se invoca si quiero pagar 2 servicios?» → topic «Crear SPS». `question` decides the tool, picks passages and is saved as the context question; `topic` is the Wiki Search query. Both are validated (length, no control characters, `Redactor::clean`); if the provider fails or does not apply, the literal request is used. Without context the call only extracts the topic: searching the whole first request («¿qué parámetros recibe en el body el endpoint crear usuario natural?») ranked generic API pages above the service's own page. It only shapes the query inside sources already authorized by code. Earlier context goes as reference, never as evidence; the current request wins. Activity reviews skip the rewrite.
4. **Sources.** `KnowledgeMap::available` requires `enabled`, `external_processing`, an exact conversation or `*`, and the source's `allowed_senders`. A matched question reads all of its selected sources that pass those checks; local simulation selections are intersected too. No source is added by an old case route. Repository and notes sources use the incremental SQLite FTS5/optional-vector index, returning relevant sections. File/URL sources read configured locations; `urls` groups 1–10 exact public URLs. A Wiki tool with nonempty `page_urls` reads only those pages through its authorized catalog and credential, with canonical references and authorship, without Search. Other tools retain their native read methods. The activity record reads the requested days, defaulting to the incoming message's day in the configured time zone. See [Questions](questions.md) for scope, migration and review details.
5. **Evidence.** Redaction before trimming. For normal answers every source is read first and `max_context_chars` is then shared by need (`evidence::shares`): a source whose evidence is shorter than an even share keeps all of it and the rest share what remains (an even split gave the Wiki half the budget while the other source was a 1.3 KB page). The Wiki and Azure DevOps return typed JSON (`ado::wiki::WikiResult`, `evidence::Evidence`) with a reference registry (ID, verified URL, authorship) and Teams messages with their author; the rest is trimmed with `knowledge::excerpt`. `excerpt` returns a text that fits whole; otherwise it splits Markdown into sections at headings (a too-long section into paragraphs), never inside a fenced code block, weighs each question word by how few parts contain it (the page's own topic barely counts) plus a bonus when the part's heading or a parent heading has it, always keeps the most relevant part (cut if it alone exceeds the budget), adds the next ones whole while they fit, gives the room left to the best one that did not fit, cut, and keeps document order, so a parameter table or a curl example is not displaced by prose that repeats the page title. Inside the Wiki evidence the budget is also shared by need: a page found identical in several wikis is written once (the copies add only their reference), and a repository file whose lines are at least 80% in a page (a README copied into the Wiki) adds only its other lines. The status tool cuts each project at 5,000 characters with work items and run results first and commit details last. A work item the request names (`ado::progress::requested`: «HU #23553», «bug 4512», «AB#77», a bare «#23553», not one after «run», «build», «PR», «release», «pipeline», «commit» or «stage»; at most five) is read first and directly in the catalog's projects, whoever holds it now, and its block leads the evidence. It is described only if the user took part in it (assigned now or at some point in its update history, created or changed it, a child item assigned to, created or changed by them, or one of its recent comments); otherwise the block only names it with its current assignee and says it is not the user's work. A described item gives type, title and state, since when (`StateChangeDate`), the current assignee and the last change, and, from the last five weeks only, its state and assignment changes, the child items changed (all children still count by state), the commits and pull requests linked to it or its children with the latest link date and the newest comments as plain text; plus the dates on the item (non-system dates such as target, due or a custom commitment date, custom fields named through `_apis/wit/fields`, at most eight lookups) and its parent. A named ID outside the scope is reported as not found («do not write its number»). A pull request the request names (`ado::progress::requested_pull_requests`: «PR !4848», «PR #4848», «PR 4848», «pull request 4848», a bare «!4848»; at most five) is read by ID at the organization (`_apis/git/pullrequests/{id}`) and kept only in a project the **configured** catalog allows (`*`: any project the credential reads, not just the user's team projects, because a review request often concerns another team's repository): title, repository, project, state, who created it and when, closing date and branches, with a verified `pull_request` reference (aliases «PR #N», «PR !N», «PR N», «pull request N», «!N»), so the answer can link it; a 404 or a project outside the catalog is reported as not found. The user's work items also include those ever assigned to them and now held by someone else (`EVER [System.AssignedTo]`, changed in the window; a failed read loses only them), marked «previously assigned to the user, now assigned to X», with the state change date and the item's dates; the window keeps ten items.
6. **Legacy activity-review helper.** The specialized multi-tool review remains for direct library maps without Questions; migrated application profiles use only their question's selected source reads.
7. **Generation.** `LlmProvider::generate_response` returns JSON `{answer, detailed}`; the model chooses the mode. The prompt sets the voice: the user replying to a colleague, natural, warm and professional — never robotic, vulgar, slangy or overly casual —, with varied wording and without reusing earlier replies, without the app's internals (evidence, context, references, tools, searches, verification) or stock disclaimers, and without menus of options or generic offers of help. A missing fact is mentioned briefly, in plain words, only when the request needs it. A status round («avance, compromiso, riesgos o bloqueos») is answered part by part in the order asked: progress of a named work item from its state (still in development: child items, linked code and comments with dates; past development: since when and who holds it now, never «I don't have its progress»), where a work item previously assigned to the user is their work handed over; the commitment from the user's dated work items within two weeks and their production deployment pages with their date (or the nearest dated one when none falls within two weeks); and blockers from the pending items in those pages or comments (missing configuration, accesses, definitions), naming who was asked when the evidence says so. When the user has an answer written from the app (§6.12), `owner_guidance` and `previous_draft` (if any) reach the model: the user's statements about their work count as true and override the draft and the evidence, identifiers they give may be used, and nothing else may be invented; a message left unanswered is written as the user's reply (`unprompted`), not as an answer to a question. `answer` is bounded Markdown, without links, citations or a sources section (code links what the text names, §8): a work item, pull request, run or release it mentions goes with its identifier (#123, PR !45, build #678), a stage with the word «stage», and a Wiki page it relies on is named by its title so it can be linked. A direct first sentence, then formatting only where it makes the answer clearer (concise, never decorative): **bold**, *italics*, `-`/`1.` lists and `- [x]`/`- [ ]` checklists, pipe tables for items that share attributes, `code`, ```json blocks, `>` for one key warning, `###` headings only in long answers, ~~strikethrough~~ for something obsolete and `{green:…}`/`{orange:…}`/`{red:…}`/`{blue:…}`/`{gray:…}` to color a status in a word or two. A URL or endpoint is written only if it appears literally in the evidence (e.g. an environment address documented in the Wiki); otherwise the model says so and uses placeholders in examples (`<BASE_URL>`) so it does not trip the URL check or the `Redactor`. No character limit: only that the HTML fits in a Teams message (27,800 bytes). No autonomous tools.

   **Providers and fallback** (`src/llm.rs`). Prompts and contracts live in `Model` and are the same for every provider; each transport implements `Backend::complete_json(system, user, schema)`. `llm::from_config` builds a `Chain` with the active providers of `llm.chain` in order. **Every call** (`classify_intent`, `standalone_request`, `select_tool`, `generate_response`, `select_references`, `propose_registration`, `plan_links`) starts with the first and moves to the next only if it fails; the next call starts with the first again, so the default resumes as soon as it gets its quota back. Failures carry only a class (`usage_limit`, `not_installed`, `invalid_answer` — the reply broke the JSON contract —, `failed`; `llm::Unavailable`), never provider text, and are logged as `llm_provider_unavailable`/`llm_fallback_used`. `audit.provider` stores `provider:model:effort` of the one that wrote. Falling back is safe because it only repeats a model call; no Graph send is ever retried.

   - **DeepSeek** (`llm/deepseek.rs`): direct HTTP to `/chat/completions` (no SDK), JSON mode, the configured `reasoning_effort` (`none` turns `thinking` off), no `max_tokens` or temperature and **no deadline** (only the connection, 30 s, and TCP keepalive are bounded). 402/429 = `usage_limit`. Only `content` is used; `reasoning_content` is discarded and never logged.
   - **Codex and Claude Code** (`llm/agent.rs`): the installed CLI with **its own login** (the app stores no OpenAI/Anthropic credentials). Found in `PATH` or the usual locations (`~/.local/bin`, Homebrew…), because a GUI opened from Finder has a minimal PATH; they are looked up on every call, so installing a CLI needs no restart. Each call runs in an empty private temporary directory, with a minimal environment (`HOME`, `USER`, locale, proxy, `CODEX_HOME`/`CLAUDE_CONFIG_DIR`; **never** the host's `NAME`/`NAME_FILE`), the request and evidence on **stdin** (not argv) and the contract's JSON schema. Codex: `codex exec --ephemeral --ignore-user-config --ignore-rules --sandbox read-only --json --output-schema`, instructions as `developer_instructions` and `-c features.X=false` for shell, exec/code, apps, plugins, browser, computer use, sub-agents, skills, memories, hooks and web search (the `-c` form tolerates versions that do not know a feature); the last `agent_message` of a `turn.completed` turn is used. Claude: `claude -p --output-format json --tools "" --safe-mode --strict-mcp-config --no-session-persistence --system-prompt --json-schema`; `structured_output` is used, and `is_error` with HTTP 402/429 or credit/limit text = `usage_limit`. 20-minute deadline per call (the CLIs retry on their own); when it expires the process is killed and the next provider answers.
   - **Catalog** (`llm::catalog`, IPC `llm_providers`, `pta llm providers`): detected CLIs and their version; Codex models from `codex debug models` (visible, without the `ultra` effort, which delegates to sub-agents); OpenCode 2 metadata from `opencode api --standalone model.list`, filtered by `favorite` in the TUI’s `model.json` (state directory from `opencode debug paths state`); Claude and DeepSeek from a fixed list. OpenCode efforts are `default` plus the selected model’s reported variant IDs; safe variant syntax is validated in code and OpenCode resolves support at execution. Other efforts are validated in `llm::efforts`; model IDs with a closed alphabet and no leading dash because they reach argv.

   **Holding notice** (`Pipeline::awaiting_model`): if the model is still working 5 minutes after processing of a Teams message started, the fixed text `holding_reply` («Déjame revisarlo.» or «Let me look into it.», per `llm.language`) is sent once and the answer is still awaited. `audit.holding_reply` records `sending` before the POST and then `sent` or `uncertain`; a retried job with that field never sends it again, and a failure is not retried. It does not apply to `dry_run` or simulations (`pta chat`), nor to intent classification (the message may not need an answer). In the personal chat it carries the same output marker, so it is not processed as a question.
8. **References and inline links.** There is no sources section: references are linked on the very words of the answer that name them, and the full list stays in the audit (`references`, `used_sources`), shown in the Messages tab as «Cited references» and «Wiki pages read, not cited». Code first finds the entities it sees named in the text (`evidence::named_references`: alias or `#id`, matched as whole words so «Notificador» does not name the entity inside «notificadorimport», and Wiki pages by a distinctive title). It links a reference by itself (`evidence::code_linked`) only on a **distinctive** name — one with a digit or a symbol (`#26477`, `PR !4848`, `sag.portalpagos.ms.solicitud`) or of several words — or on a single word right after a word saying what it is («stage QA», «la página Runbook», «commit cccccccc»), outside code, existing links and bare URLs, joined with names of the same reference that follow, so «#26477 — PR Pipeline Transversal» becomes one link. A single common word is not linked by code: «Sección Desarrollo» is a project, not the stage «Desarrollo». `LlmProvider::select_references` then gets every reference code did not see named or cannot link and returns, per used one, the exact words of the answer that name it (`{"used":[{"key":"r1","mention":"PR !4848"}]}`, `""` when the text uses it without naming it). The model sees short closed keys (`r1`, `r2`…) with kind, label, project and authority — never IDs or URLs — and any key outside the list is an `invalid_answer` (the next provider answers); words not found in the answer only leave that reference unlinked. `audit.reference_selection` is `llm`, or `code` when no model could choose (or nothing was left to choose); when no model could choose and no Wiki page was named, code counts every Wiki page read as used. `evidence::complete_answer` verifies every used reference, then links code's spans first and the model's words next, once per entity (the same entity captured twice is linked once); a Wiki page used but not named goes into one closing sentence in the language of `llm.language` («Más detalle en [A](url) y [B](url).» / «More detail in …»), so a Wiki-based answer always links its pages, and a third-party page with a known last editor carries «(última edición de Ana)» / «(last edited by Ana)» right after its link unless the text already names that person; own pages and unknown authorship add nothing (nothing is invented). URLs in the body must be verified references or appear literally in the evidence. Code still withholds the answer for: an invented ID, a concrete entity without a verified reference or a new URL (`invalid_references: …`), and sensitive data or size (`unsafe_proposal`/`unsafe_answer`). The withheld proposal stays in `audit.proposed`. `teams_message` references accept only `https://teams.microsoft.com/l/message/…` links; every other reference must be a `dev.azure.com` URL inside its organization and project. Answers recorded before 0.7.15 end with a «**Fuentes**»/«**Páginas consultadas**» section; the context saved from one sent by hand drops it.

   **Withheld answer** (`Pipeline::withhold`): in the personal chat, outside `dry_run` and simulations, a fixed text in the language of `llm.language` («No envié la respuesta a tu mensaje: <cause>…» / «I didn't send the reply to your message: …») is sent once, without the withheld content. `audit.withheld_notice` records `sending` before the POST and then `sent`/`uncertain`; a retry never repeats it. In chats with other people there is no notice.

   **The record of each message.** `Audit` also keeps the user's context for an answer written at their request (`refinement`, §6.12; omitted without `content`) and the sources they chose for it (`chosen_sources`, omitted when empty), the redacted text of the eligible message (`question`; never for ineligible ones), the interpreted request and the topic searched, the intent, the conversation type, the message time, the number of context messages, the provider and those that failed first (`provider_fallbacks`), the links of a confirmed plan with their result (`links`), and `trace`: timed steps with an explanation that never includes message content (step names in English; audits before 0.6.1 have Spanish ones). `Store::inspect` returns `created_at` and, without `content`, omits `question`, `resolved_question`, `topic`, `proposed` and `sent`. `final_check` exists only in audits written before 0.6.1.
9. **Send.** `teams::html` turns the Markdown into Teams HTML: escaped text; `<b>`, `<i>`, `<s>`, `<code>`; only `https` links as `<a>`; fences as `<codeblock>`; `#` headings as `<h2>`/`<h3>` (never `<h1>`); lists, with checklists as ☐/☑; one level of `<blockquote>`; `<hr>`; pipe tables as `<table>` with a `<thead>`; colors only from a fixed palette of five names, as `<span style="color:#…">`. Anything else (raw HTML, other color names, images) stays text. The URL check ignores a `|`, `}` or `~` right after a URL; every chat is sent with `contentType: html` and the personal chat adds its output marker. `valid_answer` also requires the HTML to fit Graph's limit (27,800 bytes) before `sending`. Re-read the message: same text and still eligible, with the age measured when processing **started** (`max_message_age_seconds` + processing time; no limit once the holding notice went out); persist `sending` with `synchronous=FULL` before the POST; never retry a send. A failure or restart during the send = `uncertain` (manual review).

10. **Retired Azure writes.** The installed `Tools` adapter reports `links_work=false` and implements no Azure write methods. Reviews do not propose registration or ask to create tasks. A persisted personal-chat plan from an older host cannot write: its source is no longer writable, and the result is reported without a request. Legacy types, audit records and generic test adapters remain readable for compatibility; stored write credentials are never removed or repurposed.

11. **Local/scheduled daily task record** (`app::activity`, `ado::tasks`, `activity::store`). The existing schedule keeps daily/interval slots, workdays and local/IANA time zones. Slots are claimed durably once; no historical catch-up. Selected enabled Azure sources use only their existing read credential; an empty selection means every enabled Azure activity source. Legacy Wiki/Teams selections and write settings are ignored. No model, commits, PRs, pipelines, Wiki pages, Teams messages or call discovery is involved.
    - `list_azure_tasks` accepts an exact `day`, optional `user` (catalog user by default), `source` and `project`. Project/team/catalog boundaries remain enforced. It discovers the project's task category and completed states, queries candidate IDs with historical assignment (`EVER`), and reads up to 1,000 revisions per task. A task belongs to the day when actual effort changes or it enters a completed state while assigned to the user inside the configured day. Later edits/reassignments do not change the day or owner. Hours are daily net deltas, never capped to `daily_hours`. The last pre-end revision supplies title, state and description. A task without an HU or hours can still be recorded on verified completion. Candidate limit: 200 per project; overall Azure deadline: 110 seconds. Bounds/errors fail the snapshot and retain the old day.
    - A successful run replaces one row in the additive `task_days(day,payload)` table of the existing `activity-registration.db`. It saves the day/time zone, verified task and optional parent URLs, titles, descriptions, daily hours, advisory target and timestamp. Task URLs deduplicate overlapping sources. Empty days get rows too; failures leave previous records untouched. Legacy confirmed tasks remain in the daily history unless a new snapshot supersedes their day; original rows and uncertain attempts remain intact.
    - `activity_history` returns `days` (newest first, counts/hours), `record` (selected day with tasks), `running`, runs and settings. `activity_run` is a local operation. `activity_pending` is empty and `activity_resolve` rejects writes; non-empty legacy run context is rejected. The CLI, MCP and GUI use the same operations.
    - `Database::recorded` reads the new daily rows as verified evidence through the existing `activity_record` source, falling back to legacy entries on days without snapshots. Tasks without HUs still carry verified task links; a saved empty day explicitly says no tasks were recorded. Recaps and task reports use this saved record, without live Azure activity reads. Source audiences/external processing remain enforced when answering; no schedule grants new Teams audiences. The record is local knowledge and needs no FTS re-index.

12. **Answering a message by hand** (`Pipeline::begin_refinement`, `Pipeline::refine`, `Pipeline::send_draft`; IPC `answer_refine`/`answer_send`, `pta answer refine|send`, the Messages tab). Any message addressed to the assistant that was not sent an answer qualifies (`unsent`): a job `ignored` or `dry_run` with a recorded `question` and no `sent`, outside simulations, except `sensitive_question` (its text never reaches a model). That covers messages the assistant left unanswered (`informational_message`, `personal_request`, `no_authorized_resource`) and answers it wrote but did not send (withheld, observed or written earlier at the user's request, `unsent_draft`). The assistant must be running (`not_ready` otherwise), because it reads and writes Teams with the service's session.
    - **Generate or regenerate.** `begin_refinement` validates the user's context (plain text, at most 4000 characters, `Redactor::clean`; `invalid_input` otherwise) and the chosen sources (each one must exist, be enabled and allow external processing; `invalid_input` otherwise), records them as `audit.refinement` and `audit.chosen_sources` and sets the job to `refining` under the operations lock, so a second request is a `state_conflict`; the IPC returns at once and `refine` runs in a host task. It runs the normal path in draft mode: the message is read again without the age limit, there is no link conversation or intent decision (the earlier intent is kept, so a review stays a review and a message left unanswered stays `statement` or `personal`; audits before 0.7.18 take it from their reason), no holding notice and no registration proposal; the sources are read again and `generate_response` receives `owner_guidance` and `previous_draft` (empty for a first answer). A message left unanswered is generated with `GenerationInput::unprompted`: the prompt asks for the user's reply to a message that asks no question (a brief acknowledgment and what it implies), not for an answer to a question, and an empty evidence does not ask the model to explain a limitation. Chosen sources replace the conversation's audiences for this answer only, like a simulation (enabled with external processing), and every chosen source is read, without tool routing, recap or status extras: the user reviews and sends the result. Without a choice, the conversation's authorized sources and the normal routing apply. Every check still applies: a failing answer is stored with its withheld reason, a passing one as `ignored`/`draft_ready`. Nothing is sent and the withheld-answer notice is never repeated. While it works the job is `refining`, never `processing` (which a restart would queue as a new message): `Store::open` turns a leftover `refining` into `ignored`/`refinement_failed`. A run that stops before writing restores the earlier audit with the reason it recorded (`no_authorized_resource`, `sensitive_question`, or `message_changed` when the message was deleted or stopped being eligible); any other failure restores it with `refinement_failed`. The earlier proposal stays until a new one is written.
    - **Send.** `send_draft` requires a proposal, re-reads the message and requires its redacted text to equal the recorded `question` (`state_conflict` otherwise), checks `valid_answer` (sensitive data, redaction markers, Teams' size), records `sending`, POSTs once and records `sent` (reason `manual_send`, saving the conversation context without its links) or `uncertain`. It is the user's own decision on a held answer, not a retry: like any send it happens once, and a sent, sending or uncertain job cannot be sent or written again.

13. **Questions** (`questions::Question`, `map.questions`, `pta questions`, Knowledge › Questions). Questions replace configurable Cases. The initial daily-activities question selects the activity record; equivalent requests keep their own date parameters. Unknown messages are reviewed through `question_associate`, which saves an owner-associated request or creates a question with source IDs. Legacy case fields are retained and ignored by loaded profiles. [Questions and answer evaluations](questions.md) documents recognition, permissions, storage, review, CLI and tools.

14. **Ratings, evaluations and people.** `answer_feedback` rates sent/proposed Teams or local-test answers good/bad with a comment. Ratings for an identified question automatically update its indexed evaluation in `knowledge-index.db`; later answers retrieve both kinds within the same question and authorized source set. Good evaluations suggest an approach; bad ones tell the model what to avoid, and code blocks identical rejected repeats. Clearing a rating removes its guidance. Facts always come from current evidence; no weights are trained. Legacy approved examples remain readable for direct library maps without Questions. **People** (`[[people]]` in the map: `id`, `name`, `senders` (Graph user IDs), `aliases`, `address`, `notes`) say how the user addresses each person: the sender's profile, by Teams ID or else by name (accent- and case-folded), reaches `generate_response` as `recipient` only when answering that person (never in the personal chat), for the form of address, tone and length, never as evidence (`audit.person`, trace step `person`). Eligible messages record `audit.sender_id` and `audit.sender_name` so the GUI can offer the profile. Messages › an answer has **Your rating** (Good answer / Needs work, comment, «Use it as an example for similar requests» with its context) and **Save as a note** (Knowledge › Notes prefilled, origin `answer`, reference the message); a sender links to their profile or adds them to People.

`jobs` states: `pending → processing → ignored | dry_run | failed | sending → sent | uncertain`; a message the user has an answer written for goes `ignored | dry_run → refining → ignored`, and one the user sends `→ sending → sent | uncertain`. Failed reads/providers retry with backoff 2^n s up to 5 attempts. When the database opens, `processing` goes back to `pending`, `sending` becomes `uncertain` and `refining` becomes `ignored` (`refinement_failed`). The audit (`jobs.audit`, redacted JSON) keeps reason, sources, tools, confidences, references and proposal; `pta audit` reads it.

Frequent reasons: `ineligible_message`, `sensitive_question`, `no_authorized_resource`, `informational_message`, `personal_request`, `deterministic_greeting`, `deterministic_thanks`, `unsafe_proposal`, `invalid_references: …`, `supported_answer`, `message_changed`, `send_result_unknown_manual_review`, for linking `links_planned`, `links_applied`, `links_cancelled`, `links_unresolved`, `links_not_configured`, and for unsent answers `refining`, `draft_ready`, `refinement_failed` and `manual_send`. `reference_selection_failed` and `final_gate` appear only in audits from before external reviews stopped withholding answers.


### Task registration reports (0.7.24)

The `report_tasks` case recognizes reminders to log hours and requests for registered tasks before activity-review phrases or model classification. It reads the authorized local activity record only, for the requested dates or today in the registration timezone, and includes saved `recorded` tasks, explicit `recorded_empty` days and legacy confirmed `done` / `already_registered` entries. Pending, uncertain and dismissed entries are excluded. The recap evidence route supplies verified task and parent links without remote tools or document searches; empty records produce an explicit no-confirmed-tasks answer, without falling back to an unregistered-work review. The case has configurable keywords and instructions, a fixed source kind, and appears as «Reportar tareas» in Spanish.

## 7. Microsoft Graph and Entra

- **OAuth** (`adapters/oauth.rs`): public client, system browser, PKCE S256, redirect `http://localhost:<port>/` served by the host during login (600 s). Fixed scopes `offline_access User.Read Chat.Read ChatMessage.Send` (`Config::scopes`). `/me` is checked against `graph.user_id` before storing tokens. Refresh is serialized and each rotated token is persisted encrypted before use.
- **Entra registration:** *Mobile and desktop* platform with `http://localhost`, multi-organization accounts, delegated permissions only. Do not add scopes: it would change the consent already granted.
- **Subscriptions** (`Graph::reconcile_subscriptions`, every 60 s): `discover_all_chats` → one `users/{id}/chats/getAllMessages` resource; otherwise `chats/{id}/messages` per chat in `allowed_chats`; plus the personal chat. 50-minute duration, renewed with <10 min left. Own subscriptions are recovered by exact callback and `applicationId` (Graph hides `clientState`). Lifecycle: `subscriptionRemoved`, `reauthorizationRequired`, `missed` (queues recovery of the recent page).
- **Webhook** (`adapters/webhook.rs`): validates the whole batch before queuing (constant-time clientState, tenant, persisted subscription, allowed collection, canonical path `chats/{id}/messages/{id}`). Never follows URLs from the notification. Answers 202.
- **Personal chat**: `48:notes` (notes) or a oneOnOne whose only member is the user; validated by `validate_self_chat`. Received by webhook + polling of 50 messages every 10 s. Each output carries a `https://personalteams.invalid/output/{nonce}` link registered in `outputs` before sending, to recognize echoes and ambiguous sends after a restart. An output without an ID pauses the personal chat until `pta self-chat reconcile`.
- **Own messages** (`Graph::own_messages`, activity reviews only): `me/chats` with the last message preview, then each readable chat's recent messages; only the user's own, non-deleted, in the window, never the personal chat or app outputs.

## 8. Knowledge and tools

`KnowledgeMap` = `repositories` (alias → local Git checkout) + `resources` (at most 250) + `people` (at most 500, §6.14) + `questions` (configured questions, §6.13) + `cases` (retained legacy data) + `contexts` (at most 50: `id`, `name`, `description`, `keywords` (≤50), `sources` (existing IDs), `instructions`; omitted when empty). Each resource: `id`, `description`, `topics`, `enabled`, `external_processing`, `allowed_conversations`, `allowed_senders` and an access:

| `kind` | Rules |
| --- | --- |
| `file` | Relative path inside a declared checkout, without `..` or escaping symlinks; Markdown/TXT/JSON/TOML/YAML; ≤1 MB. |
| `repository` | A declared checkout, searched through the knowledge index (§6.4); symlinks are never followed. |

## 9. Cross-cutting security

- No model withholds answers or grants permissions: the model chain classifies the intent of ambiguous messages (a step that can leave a message unanswered), decides whether a question about the user's work is an activity review, rewrites follow-ups, chooses a tool among authorized ones and picks references among verified ones. Audiences, paths, URLs, tools and limits are checked in code; sensitive data, IDs, unverified URLs and size are enforced by code (`Redactor`, `complete_answer`, `valid_answer`).
- Questions, documents, results and conversation history reach the models as untrusted data.
- Azure task reads and daily snapshots never create or change Azure work items. Legacy write credentials/attempts are preserved; old plans cannot write (§6.10–11). Model decisions grant no permissions.
- The model CLIs run without tools (no shell, file reading, web or sub-agents), without user configuration, in an empty directory and without the host's credentials; OpenCode 2 uses a generated `pta` agent with denied permissions and policies for all tools, plugins, MCP and skills, an isolated config directory, disabled project/Claude discovery and a private server. It keeps its provider login database and deletes only its fresh session after the call; cancellation schedules the same cleanup. Their output goes through the same checks (`Redactor`, references, limits) as DeepSeek's.
- `security::Redactor`: loaded secrets (exact match), tokens/JWT/keys, credentials in URLs, emails, phone numbers, RUT, `secret://` and `sensitive_patterns`. Applied to the question, evidence, proposal and audit; a proposal with sensitive patterns is blocked.
- Logs: only fixed own events (`tracing`, filter `personal_teams_assistant=info`); prompts, HTTP bodies and provider errors are never logged. Errors to GUI/CLI become sanitized messages (`app.rs::fail`, `cli.rs::run`); only fixed texts typed as `app::Rejected` (activity input or state the user can fix: `invalid_input`/`state_conflict`) pass through as they are. Entra token HTTP 400/401 with fixed OAuth `invalid_grant` or `interaction_required` codes becomes `AuthorizationRequired`, reported as `not_ready` with a Microsoft reconnection instruction through native GUI, CLI and web. Provider descriptions are never returned; failed renewal preserves the saved encrypted session. Stored Microsoft linkage alone does not prove live authorization.
- HTTP clients without redirects; bounded response sizes (`adapters::bounded_json`).
- WebView with a strict CSP (`connect-src 'none'`); only `control::command` is exposed to the UI.
- Git: managed clones with askpass (`PERSONAL_TEAMS_GIT_ASKPASS`), no token in URL/argv; `sync` requires a clean checkout and a fast-forward.

**MCP** (`app/mcp.rs`, `pta mcp`; `pta mcp config` prints the client configuration). A Model Context Protocol server over stdio (JSON-RPC, protocol 2025-06-18 with 2025-03-26 and 2024-11-05 accepted) that exposes the app's operations as tools, each a call to the same IPC contract (`cli::call`, profile edits through `snapshot` + `save_settings` with its revision), so every check stays in the host. stdout carries only protocol messages. Tools are `Read`, `Local` (notes, contexts, questions, people, ratings, answer drafts, index refresh, daily task snapshots and their schedule) or `External` (sending to Teams, source authorization, the mode and the assistant's state). An `External` tool needs the user's confirmation: when the client declared MCP elicitation, the server sends `elicitation/create` with the action in plain words and runs it only on `accept` with `confirm: true` (messages arriving meanwhile are queued and handled after), whatever the agent sent; otherwise it refuses until called with `confirmed: true`, which the server's instructions and the skill allow only after the user approved that exact action. Tool annotations mark `readOnlyHint` and `destructiveHint`/`openWorldHint` accordingly. A host left from an update is replaced first, keeping the assistant's state, like any `pta` command.

To add an operation: a method in `control::operate` (window or browser only through `host.shell`, so it works headless) (and in the lists allowed during login if it is a read) → a tool in `app/tools/mod.rs` (schema, effect, adapter and, if External, confirmation text), automatically available through CLI tools and MCP → optionally a dedicated CLI command (`HELP`, `validate_args`, mapping and `help_documents_every_accepted_command`) → if it changes a schema an older host does not understand, announce it in `Endpoint` like `wiki_support` → document it in the skill.

## 14. Current decisions and why

- **Daily tasks are read, never created (0.7.33).** Activities is a day → tasks → shared-detail history. The schedule saves existing Azure tasks; hours are advisory, and recaps read verified saved tasks without rediscovering activity. This supersedes the earlier registration/linking decisions below; their data and credentials remain compatible.

- **No model vetoes retrieval.** A selector used to decide the source before reading it; in a real sample (2026-10-01) it rejected half the documentation questions with confidence 0.29–0.38 and the Wiki was never read. Do not reintroduce a topic or relevance prefilter.
- **No model withholds answers.** On 2026-10-01 a follow-up («cuál es el endpoint para el ambiente de test») was written well but the external reviewer did not tie it to any page and the rule «every Wiki answer cites a page» discarded it silently. Reference selection is informative; if no page is chosen the consulted ones are listed. What withholds an answer is decided by code, and the personal chat is notified.
- **The language model replaced the external classifier (0.6.1).** A separate classification API classified ambiguous messages, picked references and ran an informative final review; it was a second provider, credential and point of failure, and `pta test providers` failed on it without detail. The model chain now does the first two with closed contracts and code validation; the final review was dropped because it never blocked anything.
- **Unregistered work is reviewed, not guessed.** On 2026-10-03 «¿qué tareas o trabajo he realizado que no están registrados en tareas?» went to the Wiki, cited one page and asked which system the user used. The review reads the user's real activity in every authorized source, compares it with work items in code and lets verified authorship speak in the first person. Only work items Azure DevOps returns are named, because an unverifiable number would withhold the whole answer.
- **New tasks are tasks, under open HUs (0.6.6).** The first real task was created as a Product Backlog Item, because the user owns more backlog items (under features) than tasks, under an HU in state «Abortada» the model chose. The type now comes only from the user's task-type items, and code accepts as a parent only an open user story or backlog item.
- **The proposal never withholds the review (0.6.5).** The first real proposal named a release «DESA-<date>-<n>», which the RUT pattern redacts, and the whole review was withheld as sensitive; a link to a project with parentheses in its name would also have failed the body's URL check. The section is now built from clean short identifiers and added after the checks.

Its form revision now changes only when it reloads or writes; a stale save gets `revision_conflict`.
- **The review proposes where to register, the user confirms once (0.6.4).** In the first real test of 0.6.3 the review ended asking «¿en qué work item…?» and «determina tú mismo dónde registrarlas» was answered from the Wiki with titles and no IDs. The user expects the assistant to decide: per activity, an existing work item or a new task in an HU, with the reason, and one «¿Confirmas?». Creating a task is a write like a link: same credential, same confirmation, recorded before the request and never retried.
- **Linking is planned by the model, confirmed by the user and written by code (0.6.3).** After the concise review of 0.6.2 asked «¿en cuál de estas HU la registro?», answering it still meant opening Azure DevOps. The model only turns the reply into closed keys and IDs; code verifies them, the user sees the exact plan and confirms it, and each write is recorded before it is sent and never retried, like a Teams send. The write credential is separate so a read-only setup stays read-only.
- **Completed tasks follow the process's transitions (0.7.9).** On 2026-10-14 a real process only allowed creating a Task in «En espera», required Remaining Work there, and required «Evidencias de finalización» and «URL Commit» and an empty Remaining Work in Done; the single creation in Done was rejected and the app showed a generic message without Azure DevOps' reasons. Registration now learns those rules with `validateOnly` before writing, asks for the missing fields, and completes the task with a second request in the same attempt, still never retried.
- **Tasks may go under a bug being worked on (0.7.6).** The incident behind the 0.7.5 report (#26321, «En progreso») was where the user wanted the diagnosis registered, and teams also hang tasks on bugs in development. A bug, defect or incident that is not closed now holds tasks like an HU; tasks, features, epics, impediments and closed, resolved, removed or aborted items still do not.
- **An activity's result is shown where the user acted (0.7.5).** On 2026-10-13 a user on an iPhone completed an activity's details, chose incident #26321 as «Other HU» and pressed «Create task in Done»; the host rejected it with «choose an open HU», wrote that issue above a long form, out of sight, discarded the typed details, and the browser had no notification, so the user could not tell whether the task existed. The rule stays (tasks go only under an open HU), but the explanation names the item's type and state in the user's language, offers its parent HU, keeps the edits, and the form follows the operation to its end and shows the outcome next to its buttons.
- **The app speaks the user's language (0.7.5).** The interface was English while the user's answers and tasks were Spanish. The source stays English for code and agents; one catalog translates the GUI, and a test keeps it complete.
- **Answers sound like the user, not like the app.** The same 2026-10-13 reply («El contenido y el estado del elemento enlazado no se pueden verificar con la evidencia disponible. ¿Necesitas un resumen, revisar su estado o ayuda para redactar el hotfix?») repeated the prompt's own vocabulary and offered a menu. The prompt now asks for a colleague's natural, professional voice, forbids internal terms, stock disclaimers and menus, and mentions a gap only when the request needs it; attributions are plain phrases too.
- **A shared link is thanked, not answered.** On 2026-10-13 «Hotfi: <work item URL>» was taken as a question only because the URL had `?showParents=false&workitem=…`; the Wiki was searched and the answer said the item could not be verified and offered help. Someone sharing a link expects an acknowledgment: code ignores `?` inside links and answers a bare share with a fixed thanks by first name, without a model.
- **Requests for the person are not answered.** On 2026-10-02 the assistant answered «te puedo llamar», «necesito llamarte» and «necesito que revisemos lo que se debe subir…» with unrelated Wiki pages. Calls, meetings, joint reviews and availability can only be answered by the person: code discards them before the question shortcut and the intent classification has the `personal` category for those code does not recognize.
- **Conversation context, not only the last exchange.** The 10 earlier messages with author and time let short follow-ups be understood; they go as context, not evidence.
- **Wiki attribution is built by code** from verified metadata.
- **Links go where the entity is named.** On 2026-10-14 a reply ended with «Fuentes» and «Páginas consultadas»: a release stage cited because «Sección Desarrollo» contains «Desarrollo», three deployment pages the text did not use, and «PR !4848» without a link. Answers now carry no sources section: code links the distinctive words that name each entity («#26477 — PR Pipeline Transversal»), the reference model marks the words for the rest and tells a project from a homonymous stage, a pull request the request names is read by ID so it has a verified link, and the full list of what was cited and read stays in the audit and the Messages tab.
- **The model does not copy IDs or page links.** It returns only text and mode; links come from the verified registry, placed by code on the words that name each entity. It may copy a URL that appears literally in the evidence (a documented endpoint), because forbidding it prevented answering «¿cuál es el endpoint de test?».
- **Fallback per call, without memory.** The chain holds at most 16 model choices; providers and models may repeat, including different efforts. Every call starts with the default provider; it is not remembered that it was out of credits. It costs a fast failed attempt while the exhaustion lasts, in exchange for returning to the default as soon as it recovers. It falls back on any failure, not only credits: an invalid contract or a missing CLI must not leave the question unanswered either.
- **CLIs instead of APIs for Codex and Claude**: they use the subscription already signed in on those CLIs, with no new keys in the app. In exchange they are invoked without tools or customizations so they behave like one model call, like the API.
- **Formatting is decided in code.** The model writes bounded Markdown and code turns it into Teams HTML; links are built from the registry. Colors are names mapped to a fixed palette, not CSS from the model, so a model cannot inject styles or markup.
- **Follow-ups are resolved before searching, not vetoed.** Searching only the words of «¿y si quiero pagar 2 servicios?» did not find the page. The standalone rewrite only changes the query; tool selection and audiences stay in code.
- **One tool per normal answer**, to bound cost, latency and surface; activity reviews are the exception because comparing activity with registered work needs every source at once, status rounds add only the user's own recent Wiki pages, because a committed deployment date and its pending items live there, and an answer written from sources the user chose reads all of them (§6.12).
- **A status round reads the HU itself and the user's deployment page (2026-10-14).** «Ronda de actualización: 1) avance de lo que tienes en curso: HU #23553, 2) compromiso, 3) riesgos o bloqueos» was withheld (the answer named HU #23553 without a verified reference) and its proposal said the progress was not at hand. The HU had been sent to validation and reassigned to Luis Felipe, so the status tool, which kept only items assigned to or last changed by the user, never read it; and the committed production date and the missing production variables were in the user's own Wiki page. Code now reads a named work item directly with its owner and history, keeps handed-over items, adds the user's own recent Wiki pages, and the prompt says how to answer each part.
- **Status reads stay within five weeks and the user's own work (2026-10-14).** Reporting activity or status is about what the user did recently. Every activity and status read looks back at most five weeks, a named work item is described only if the user took part in it (otherwise the answer says it is not theirs and who holds it), and the work the Activities section recorded by day is added as context, filtered by the conversation's authorized sources. On the same day the user's real deployment page, «PAP - HU 23796 - …», was missed because «PAP» was not a deployment word and its date sat far down a 23 KB page: «PAP» in a title now marks a plan, and its excerpt favors dates and pending items.
- **What the user did is answered from what they approved (2026-10-15).** The Activities section already kept every approved task by day in `activity-registration.db`, but «¿qué hice el martes?» went to the status tool or to a full activity review, which read Azure DevOps for two weeks and answered at length. A question that names a day or period now reads only the record of those days, so the answer is short and matches the tasks the user approved; the GUI shows the same record as a History view. The store stays SQLite: one user and one profile per host need no server, the file already lives next to the other databases, and a move online would go to libSQL/Turso (SQLite's dialect and schema, unchanged SQL) rather than Postgres, only if several devices ever need to share it.
- **The user decides on a held answer (2026-10-14).** A withheld proposal could only be read in the app. The user can now give the agent context to rewrite it (never sent automatically) and send the reviewed text once; code still refuses sensitive data, oversized answers and an edited message, and records the send before the request like every send.
- **The user may answer what the assistant left unanswered, from the sources they choose (0.7.18).** On 2026-10-15 a colleague's instruction («para un hotfix de producción va como Bug Desarrollo (no HU): describe el síntoma…, la causa y el cambio, y vincúlalo al incidente») was correctly classified as informational and left unanswered, but the user wanted to acknowledge it without typing the reply in Teams. Any unanswered message (except one with sensitive data) can now get an answer generated on request, written as a reply rather than as an answer to a question, then regenerated with context and sent once. The user picks its sources, which may lie outside the conversation's audiences because the user reviews and sends the result; Teams-triggered answers still read only the conversation's authorized sources, and conversations without one still never reach a model unless the user chooses a source.
- **The activity record is a source of its own (0.7.19).** On 2026-10-16 the user expected what they approved in Activities to be a source to choose, and could not find it: it was read only as part of Azure DevOps activity, and an answer from chosen sources never read it, even with that source chosen. It is now an `activity_record` tool authorized on its own. Its registered tasks show wherever it is authorized, because their title, HU, hours and description are what the user approved and wrote to Azure DevOps (the first production check, choosing only the record, found every task of the day hidden: each had a Wiki page or Teams message among its activities); work not registered yet still needs the Wiki and Teams sources it was drawn from; a map without one keeps the old behavior so existing profiles answer as before. The Azure DevOps catalog moved into the map too (`catalog`), so a knowledge repository is no longer required to read Azure DevOps.
- **Agents operate the app through MCP, and the user confirms what leaves it (0.7.23).** On 2026-10-16 the user asked to operate everything the app does from agents such as Codex or Claude Code, with the agent asking when it must confirm. The MCP server is a thin translation of tools into the existing IPC contract, so it adds no permission and every audience, check and record is the host's; it runs as `pta mcp` because `pta` already finds or starts the host. Writes the user can undo in the app (notes, contexts, questions, people, ratings, drafts) run directly; what reaches others or grants access (Teams, Azure DevOps, sources, mode, the service) needs the user's confirmation, asked by the client itself through MCP elicitation when available so an agent cannot confirm on the user's behalf, and otherwise required as an explicit `confirmed` argument.
- **The app learns from what the user approves, not from what it wrote (0.7.22).** On 2026-10-16 the user asked to rate answers, tie information to contexts and improve how each person is answered. Ratings are kept with the message; the improvements come only from what the user explicitly approves: a corrected answer saved as a verified note (evidence, authorized like any source), a good answer kept as an example (structure and tone only, never facts, because an example may carry facts from a chat the next conversation may not read) and a note on how to address each person (only when answering them). Nothing is learned automatically from sent answers, so a mistake is never reinforced without the user seeing it.
- **The user's cases change texts and routes, not rules (0.7.21).** On 2026-10-16 the user asked for the kinds of request and their prompts, hard-coded until then, to be configuration: how the model recognizes a progress question, which sources each case reads and how it is answered. The built-in routes stay in code (their Spanish and English detection, recaps by day, status rounds part by part) and the map keeps only the user's changes, so an unchanged profile answers exactly as before and an update can still improve the defaults. What the user can replace is the descriptive part (the category descriptions, the voice, each case's instructions) and what each route reads among the authorized sources; the rules that make answers verifiable — evidence only, no invented identifiers or URLs, verified links, sensitive data, the closed JSON contracts — cannot be replaced from a profile. Subjects of the user's own are contexts rather than new cases, so one concept groups a subject's sources, words and instructions; a model may recognize a context by its description, but its choice only guides.
- **The knowledge index is SQLite, not a vector database (0.7.20).** On 2026-10-16 the user asked for repositories as sources of their own, notes, contexts such as «cobros» and a possible move to a vector database for semantic search, keeping SQL for configuration. One user and one profile per host hold thousands of sections at most: SQLite's FTS5 (already compiled into the bundled SQLite) gives BM25 ranking with folded accents and no new dependency, and vectors are optional, stored next to each section and compared by brute force, fused with the text ranking. A separate vector server (Qdrant, LanceDB) would add a process, a dependency of tens of megabytes and a second store to back up, for no gain at this size, and none of the configured models (Codex, Claude Code, DeepSeek) offers embeddings, so they come from an optional OpenAI-compatible endpoint (or Ollama on the same computer). The activity record stays in `activity-registration.db`: it is answered by day, not by meaning. Contexts are code-matched keywords rather than a model decision, so they never veto retrieval: they only narrow to sources the user grouped and add the user's instructions.
- **No send is retried**: Graph has no idempotency; skipping an answer is preferred to duplicating it.
- **Public desktop OAuth with the scopes already granted**; the existing Entra registration allows `http://localhost` and other organizations. Asking for new permissions would require a new consent. Own Teams messages are read with `Chat.Read`, already granted.
- **Cargo only**: no signed/notarized bundles or Docker server; the host (with a GUI or headless) is the only runtime.
- **GitHub Actions for CI/CD, the server pulls (2026-10-17).** Merging, then installing on the server, restarting and publishing by hand took every delivery. The repository is public, so GitHub's standard runners are free on Linux, macOS and Windows; Cloudflare Workers Builds (3,000 minutes a month, 20-minute builds, no Rust or GUI libraries) only keeps publishing the landing. The server is never a runner, because on a public repository a pull request from anyone could run code there: it pulls releases from crates.io, which only the release workflow (or the owner) publishes to. Publishing uses crates.io Trusted Publishing, which rejects `workflow_run`, so the release runs on push and waits for CI itself.

- **CI work split by event (2026-10-26).** PRs retain the complete path-selected Linux/UI/macOS/Windows checks. Pushes to `main` retain security, Linux tests with and without GUI and verified Cargo packaging for the exact delivery commit, while skipping duplicate linting and UI/macOS/Windows jobs. A new unpublished version always requests Linux verification. The weekly run checks the complete matrix on `main` and refreshes its trusted caches. No PR result/artifact authorizes publishing a different commit. The release gate, read-only CI permissions and standard hosted runners remain unchanged. See [delivery](delivery.md).

## 15. Known limits

Ordinary shared accounts support API-backed assistant operations. SQL sources that could
use OS-integrated authentication require a personal trusted machine. Their embeddings
requests reuse public-source DNS/IP pinning and reject operator-local destinations.
Request/child creation, Git clone/sync and configurable CLI providers on the shared
server remain unavailable to ordinary accounts. Profile folders are not OS isolation.


- **Account configuration.** Synchronization is whole-document with per-item patches, not a merge: two clients editing at once get a conflict for the later one, resolved by synchronizing and repeating. A profile configured before signing in must be adopted with `reset` (a private backup is kept); there is no field-by-field merge of local and account settings. People profiles, legacy cases, the Graph chat allowlist, policy sender allowlists, activity settings, knowledge-index settings and launchers are not synchronized yet. More than 2,048 notes or a document over 900 kB is refused. Granting a source access, including enabling or widening it, is done on the coordinator, not from a connected installation. The Activities screen still reads this installation's own record; the coordinator's saved days are reachable with `account_records`/`pta account records`. Legacy migration is a separate slice.
- **Account readiness.** `setup_status` reports each step from the operations that own it and never acts; the optional Teams and version steps are never required for `ready`, and `ready` says nothing about Teams having received or sent a message (see the counts). The directory choice it points to is the shared directory sheet in Settings › Execution machines; there is no second selector. The real-host CLI/MCP flow of the setup path is covered on Unix like the other host-process tests; on Windows the report's own unit tests run in CI but the whole path against a real Windows host, a sign-in with a second client and the update are exercised by their own slices' tests, not by one end-to-end Windows run.
- **Updates and rollback.** `pta update apply` installs a prepared pair and rolls back an unhealthy one, but only for installations the helper can restart itself: a headless host under a systemd unit, a development build or a non-crates.io install updates the way it was installed. It does not retract work only the new version could read after a rollback, and the safety copy needs free disk space. The check sees only crates.io's sparse index, so a mirror that replaces it in the user's Cargo configuration is not consulted for discovery. A staged build needs the Rust toolchain and, with the desktop app, the platform's GUI libraries; there is no download of prebuilt binaries by design.
- **Variable consumers.** Supported consumers are exactly the DeepSeek API key and owner-only local launchers. A running assistant keeps the DeepSeek key it read at start until it restarts. Only the first slot of the registry exists; further built-in consumers are added in code. Launchers are proposed and run from the CLI/MCP and approved only in the application window (the GUI lists, approves and removes them), only on an owner's trusted machine, so a headless installation cannot use them; their output is deliberately not captured, and an approved program can retain what it receives (rotate the external credential if a program is no longer trusted). Redaction is never relied on. Machine-local launcher files and bindings are not yet synchronized or migrated. Which variable a consumer or launcher uses is enforced on the trusted machine, not by the coordinator: `variable_resolve` serves any entry of the account to a trusted, unrevoked machine of that account, one audited entry at a time. Trusting a machine grants it the account, so a stolen machine credential is handled by revoking the machine (every later resolve is then refused) and rotating the affected values at their providers; a coordinator-side allowlist registered by the same credential would not stop its thief.
- A new execution machine joins through browser sign-in and one Trust this machine confirmation (0.9.12+, both installation and coordinator), or through the operator-local CLI and a private single-use pairing file. A pending sign-in lives in host memory: restarting the host abandons it and the coordinator request expires unused. The unauthenticated start endpoint is bounded and rate limited but can be crowded by anyone who knows the portal address; the user then retries after a minute. Approval pages show the confirmation code; users must compare it, because approving a stranger's request (consent phishing) would add that computer to their account. Individual machine revocation is available from any connected account client (0.9.13+); it denies future access but cannot retract information already given to an external process. Stored variables exist per account ([Account variables](#account-variables)); their consumers (DeepSeek key, owner-only local launchers) re-run this live account check at each use, and no machine credential reaches them. The portal supports one owner per installation. Profiles and provider working-directory permissions are not OS/container isolation and must not be offered to unrelated tenants.
- Tauri's Linux GTK 3 dependencies retain RustSec maintenance/GLib Variant notices; the app does not directly use that Variant API, and the deployed headless server excludes the GUI stack. Dependency audits keep the notices visible; see [the security policy](../SECURITY.md). The SQL Server adapter uses Tiberius 0.13 with patched Rustls, and Access tests use a public synthetic DER signing fixture instead of the vulnerable RSA test dependency.

- Maps saved with `questions`, URL groups or pinned Wiki page URLs require host/CLI version 0.9.0 or later. Enrolled machines must be updated before they can run Teams with the new question configuration.

- Implementation machines need explicit enrollment with the user's HTTPS portal before presence is discovered across networks. The coordinator must remain reachable. The native/headless host on each machine must support `implementation_support`; no additional server or package is installed. Coding runs retain changes in the selected directories and report blocked permissions; they do not automatically push, publish or deploy. OpenCode requires V2; CLI-specific permissions still apply, and selected directories are not a general OS isolation boundary. Isolated portal profiles are restricted to their own `data/repositories` roots.
- Implementation history persists every run in SQLite, lists up to 100 matching runs within an 800 KB response budget (`partial` reports older results omitted; retrieve a run by ID) and bounds an active run to two hours. The card/detail session index shows up to three summaries per item, prioritizing active executions. Interrupted runs are never resumed automatically. Machine calls time out after 40 seconds and are not requeued after a lost claim; inspect runs before starting another attempt. Child creation has no automatic reconciliation after an uncertain write; its recorded links and provider state need human review.

- To-Do GitHub epics are issues of type Epic, with native open/closed states. Project-board custom
  workflow states and dates are not read; unavailable issue start dates remain null. The GitHub
  App must already have Issues read access. Detail images/attachments remain original links,
  without inline image previews; process form extensions and GitHub Project-board layouts are
  not reproduced. Large discussions/histories report their documented bounds. Azure To-Do stays within the configured catalog and
  team projects; it does not widen the source to unrelated organization projects.

- One Teams identity per profile. Team channels are not supported.
- Daily task records are local snapshots, refreshed by schedule or on request. Task detail reads current Azure fields; a saved daily list retains its original day. Large/old historical reads may exceed the candidate/revision deadline and retain the previous snapshot (§6.11).
- The app must stay open for scheduled snapshots. Native notifications require OS support/settings. No call or chat discovery is involved in daily recording.
- Reception needs the computer on and a stable HTTPS URL to the listener (Cloudflare tunnel with a token, an own `cloudflared` file or an external tunnel).
- A normal answer reads one tool (it does not combine a Wiki search with activity); activity reviews combine sources, and status rounds add only the user's own Wiki pages of the last month (pages by other people, such as a validation page, are not read). Writing or sending an answer from the app needs the assistant running.
- An activity review takes about two minutes with Codex at medium effort (about half a minute of Azure DevOps reads, the answer and the reference selection), and a busy period may hit its bounds (60 commits, 15 pull requests, 10 runs, 10 releases, 10 approvals, 12 Wiki pages and 40 messages); it says so when coverage is partial. Approvals depend on what the Release API returns for the account.
- Teams documents that inline styles in messages sent through Graph "may not function as intended": if a client ignores them, colored text shows in the default color (the word is still there). Table borders and heading sizes depend on the Teams client.
- Question recognition uses model semantics even without embeddings. Broader mistakes described in negative ratings depend on the model following corrections; code blocks identical rejected repeats. A person is recognized by Teams ID or exact name only.
- A repository source reads Markdown and text files only (no code), at most 5000 per repository; a context is matched by its words, not by meaning, so a request that names a subject only through a synonym missing from its keywords is answered without it. Semantic search needs an external or local embeddings endpoint; the configured models offer none.
- `repository_docs` reads only root README/OpenAPI files of repositories named like the topic; it does not search code (validators, DTOs) or folders, and a repository whose name does not carry the topic words is not found.
- `pta chat` returns the answer as unconverted Markdown (the GUI renders it). In the native app, links in answers are copied; they do not open in the browser (the web portal opens them in a new tab). The local test chat has no Microsoft session, so the own Teams messages source reports itself unread there.
- The GUI does not create tool sources (except the activity record) or edit their parameters (`tool`, including the Azure DevOps catalog) or `allowed_senders`: use `pta sources add`/`sources edit`/`pta config set`.
- `missed` recovery covers only the recent page; there is no guarantee of processing messages during outages.
- It does not detect whether the user answered manually while the proposal was being written.
- The context history comes from the chat's recent page (50 messages); the test chat (`pta chat`/GUI) has no history. In chats with other people, answers sent by the app show as `me` (only the personal chat marks them as `assistant`).
- Without a model's selection, a Wiki answer lists every consulted page, even if it did not use them all.
- With maximum reasoning an answer can take several minutes, and the worker processes one message at a time: the next ones wait in the queue. If the default provider fails slowly (e.g. a CLI that hits its 20-minute deadline), the fallback adds that wait.
- OpenCode requires version 2. Its GUI model dropdown offers only available TUI favorites from the host’s OpenCode state, with no free-text IDs; missing/unreadable preferences or metadata offer no models. Mark favorites in OpenCode on the host, then use Detect CLIs again. Effort offers `default` plus only that model’s reported variants; changing the model resets an unsupported effort to `default`. A saved non-favorite or unsupported effort remains in the profile and is shown as a notice, never inserted into the options or silently replaced. Without favorites, adding an OpenCode row is disabled. Discovery and calls use the same isolated configuration, so project/user customizations are not loaded. A failed session cleanup makes the call fail, and an abrupt host exit can leave an OpenCode session in its own database. The Claude and DeepSeek models in the catalog are a fixed list (their CLI/API publish no local catalog); other valid IDs are set with `pta config set llm.chain`. The Codex/Claude/OpenCode CLIs are not tested on Windows (looked up as `.exe`).
- Windows MSVC host builds reserve 8 MiB of main-thread stack at link time (`/STACK:8388608`), with the default commit size; `pta`, non-MSVC Windows and other OS targets keep their defaults. In 0.9.8, Windows startup overflowed the default 1 MiB stack (`0xc00000fd`); changing only the reserve to 8 MiB allowed startup. The stack-consuming function has not been identified and infinite recursion has not been established. The native event loop remains on the main thread. See [Microsoft's /STACK reference](https://learn.microsoft.com/en-us/cpp/build/reference/stack-stack-allocations?view=msvc-170).
- Windows CI performs a clean release Cargo installation, checks the host and CLI PE stack fields, and opens the native GUI on a disposable account. It verifies host version/state with Teams stopped, native window close/reopen, and full host quit/relaunch twice (`scripts/test-windows-startup.py`), then runs clippy. This full native check runs on PRs and weekly, and is skipped on pushes to `main` to avoid repeating the clean release build. The Windows job remains informative; the full Rust test suite does not run there, and the smoke check does not cover an existing user's profile or every Windows configuration. Linux only as a headless host (the GUI on Linux is built and tested in CI but not run).
- Cargo has no post-install hooks: the previous host keeps answering with the old version until the first `pta` or opening the new app.
- The version published on crates.io may lag the repository; GUI and CLI must come from the same build (the CLI rejects Wiki schemas against a host without `wiki_support`). A profile saved from 0.6.0 includes `llm.language`, which an older host or CLI does not load, and one saved from 0.6.1 lacks `[jev]`, which 0.6.0 requires (`deny_unknown_fields`). A knowledge map with `repository_docs: true` (0.6.7) is not loaded by 0.6.6 or earlier. A profile saved with `[activity_registration]` (0.6.8) requires a host and CLI from 0.6.8 or later; older profiles still load with registration disabled. A map with an inline Azure DevOps `catalog` or an `activity_record` source (0.7.19) is not loaded by 0.7.18 or earlier, and one with `contexts` or `repository`/`notes` sources, or a profile with `[knowledge_index]` (0.7.20), by 0.7.19 or earlier; a map with `cases` (0.7.21) by 0.7.20 or earlier, and one with `people` (0.7.22) by 0.7.21 or earlier.
- `llm.language` covers the GUI, Teams and activity drafts, not the CLI, audit log, step names or diagnostics (English), and the configured greeting (`policy.greeting`) stays as written. Host errors outside the GUI catalog, and parts of provider or Azure DevOps error details, are shown in English. Model-written drafts follow the language as well as the model does. Detection without a model covers Spanish and English phrases; other phrasings go to the model's intent classification.

## 16. Work item implementation and execution machines

`app/implementation.rs` owns durable implementation runs, reviewed child creation and canonical directory checks; `app/implementation/store.rs` records executions and native sessions in SQLite. `app/implementation/fleet.rs` owns enrollment, presence, one-shot remote calls and the Teams lease; `app/implementation/login.rs` owns the installation side of browser-assisted sign-in. Both are host operations shared by the GUI, CLI tools and MCP, with no dependency on Tauri. Machine settings and child-send intents live in private `implementation/registry.json`; every agent execution is recorded in `implementation/runs.db`, with indexed work item identity/link, provider/model/effort, machine, native session ID, state and request/start/finish timestamps. Durable update events replicate session summaries into the coordinator's SQLite index, so an offline machine retains its last reported sessions; the account's existing profile identity, credential names and data directory are unchanged. `implementation/connection.json` contains the coordinator origin, account and machine identity; `PTA_MACHINE_TOKEN` is kept in the existing credential store. Snapshots never expose it. Hosts and CLI capabilities advertise additive `implementation_support`.

To-Do cards and shared details place Implement before the original-link action. HUs/bugs and GitHub epics produce a bounded, validated child plan using the chosen machine's installed CLI and selected model/effort. The user edits and selects children, then confirms creation. Tasks (including process-defined custom task types and Bug Desarrollo) and ordinary GitHub issues launch coding directly. GitHub's All issues filter and `get_github_issue` support ordinary issues, and verified sub-issues can open shared detail. Provider type/category verification happens on a fresh read before starting or creating anything; IDs, URLs and source scope are not supplied by a model.

The implementation form selects context, execution machine, multiple canonical directories, an installed Codex/Claude/OpenCode CLI, model and supported effort. Changing machines clears directory/model selections. Its directory browser lists only permitted roots and directories, rejecting symlink escapes; isolated portal profiles can use only their own repositories. A run records its intent before launching, rejects overlapping working directories and has a stable UUID to avoid repeated remote starts. Cancellation terminates the CLI process tree. Startup marks in-flight runs interrupted and pending creations uncertain; neither is replayed.

All GUI directory choices use the same modal directory sheet (a bottom sheet on phones), including remote implementation directories, this machine's allowed roots and local checkout add/edit paths. A `../` row starts each open directory's list. Selections are staged across parent/child navigation and applied explicitly; Cancel/Escape discards them. `implementation_browse` remains confined to the selected execution machine's saved roots. Read-only `machine_browse` lists this host's filesystem root (the home drive on Windows) for configuring roots and local checkouts, independently of saved execution roots; isolated web profiles remain confined to their own `data_dir/repositories`. Both use the same canonical directory listing and reject symlink escapes. Browsing never changes roots or grants execution access; roots still require `machine_save`, and existing portal isolation checks still govern checkout changes. The Connection portal field explains that its HTTPS address is entered on another computer to enroll it and left empty on the coordinator itself; the last validated origin is remembered and prefilled (`machine_settings.coordinator_origin`). In the browser GUI the coordinator never offers Connect this machine.

`llm/implementation.rs` is separate from the tool-less answer transports. Planning uses a closed JSON interface in its own persistent, tool-less CLI session; coding runs the selected CLI in the first directory with additional directories passed through provider controls. Prompts travel on stdin, the inherited environment is restricted to the existing CLI/login/proxy allowlist, output is bounded and redacted, and no assistant Graph/ADO credentials enter the child environment. Codex uses workspace-write, Claude uses acceptEdits, and OpenCode V2 uses a dedicated agent with explicit directory permissions/policies. A provider can refuse permissions; Claude permission denials produce needs_attention. The CLI's own login and permission system remain in force. Relevant command references: [Codex](https://developers.openai.com/codex/cli/reference/), [Claude Code](https://code.claude.com/docs/en/cli-reference), [OpenCode V2 permissions](https://opencode.ai/v2/docs/permissions/).

Browser-assisted sign-in (0.9.12) is the normal enrollment path; `app/implementation/login.rs` is the installation side and `app/web/enrollment.rs` the coordinator side. `machine_login` validates the coordinator's HTTPS origin (no credentials, path, query or redirects), remembers it in private `implementation/installation.json` and posts `login_start` with the machine ID, name, OS, the SHA-256 of a private installation key kept in that file, and the SHA-256 challenge of a random verifier that stays in host memory. The coordinator stores the request in private `web/machine-logins.json` (locked, at most 100, ten-minute expiry, rate limited per machine and globally) and returns a 256-bit public transaction handle and a short confirmation code; the installation builds the approval URL `ORIGIN/login?enroll=HANDLE` itself and opens it in the system browser (headless hosts and agents only return it). GUI, CLI and MCP see only the origin, URL, code, expiry and state. `/login` and `/` keep a valid `enroll` handle across Access and local-session redirects; the shared GUI then shows a Trust this machine dialog naming the computer, OS, code and signed-in account. Its `inspect`/`trust`/`deny` calls use POST `/api/enrollment`, which requires the Access assertion, the local session, exact Origin and CSRF. A decision is single and binds the request to the session's account ID and version; a request started by an installation already connected to an account carries that account's provider subject and only that account can see or trust it. Opening or signing into the portal never creates a machine. `machine_login_status`/`login_status` reads the state; `machine_login_finish`/`login_finish` presents the verifier and machine ID, and only an approved request whose account is still admitted at the same version is consumed (before any host is contacted) and forwarded as `machine_register` with `enrollment: "login"` through the existing account-bound machine transport. Wrong verifiers or machine IDs are refused; replayed, expired, cancelled, denied and revoked requests issue nothing. The account host refuses a sign-in that claims an enrolled machine ID with a different installation hash (operator pairing files may still replace it), so repeating sign-in from the same installation rotates its own credential without duplicates and another installation cannot clone it. The installation rechecks the account, stores the returned credential as `PTA_MACHINE_TOKEN` in its own credential store and only then writes `connection.json`; any failure leaves an existing connection unchanged. A finish returns `authorization_pending` until approval. Trust grants no roots, Teams machine, assistant start or provider login. CLI: `pta auth machine login [URL] [--no-browser]|status|finish [--wait]|cancel`. The Access bypass for `/api/machines` covers these unauthenticated `login_*` actions, which never accept a bearer token; `/api/enrollment` stays behind Access. The flow follows the device-authorization pattern of [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628) and the native-app guidance of [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252); it does not change the Teams OAuth flow.

The portal's exact POST `/api/machines` endpoint is separate from authenticated browser control. Pairing-file enrollment requires a single-use, ten-minute, machine-bound pairing credential authorized locally on that installation with `pta web machines authorize MACHINE_ID [USER] --output PRIVATE_FILE`. The command writes a 0600 JSON file for `machine_connect` on stdin and persists only a hash under the private portal directory. Consumption is locked and persisted before contacting the host, and checks explicit account admission, account version, expiry and machine ID. GitHub tokens never authorize enrollment and are never sent to a coordinator. No account is created. Enrollment issues a random machine credential and stores only its hash, bound to the account version. All subsequent calls are authenticated with it; re-association, disabling an account or disconnecting the machine revokes access. Browser Origin requests, cookies without a machine credential and other methods/paths do not authorize machine operations. `configure-web-access.py` installs one exact Access bypass for this machine protocol; the backend still authenticates every request, and `/api/control` remains Access/session/CSRF-protected. Workers poll outbound, so the Mac needs no listener reachable from the Internet.

A coordinator defaults to itself as the Teams machine. Every service start requires a lease for the selected machine; renewal runs separately from implementation polling every ten seconds. Handover blocks the new machine until the old 120-second lease expires. An existing service stops if it loses renewal or is deselected. The updater also checks implementation runs and child sends before restarting a host. This coordination covers enrolled hosts of the same account; an independent, unconnected installation is not discoverable.

Machine management (0.9.13+, `machine_management_support` in the host descriptor and CLI capabilities) uses the coordinator-authoritative registry from every account client. `machine_list`/`machine_detail` expose only that account/version's names, OS, trust, online/unknown/offline presence, last-seen time, last-known assistant state, allowed roots and management/directory/assistant capabilities. Worker polls persist last-known state; older workers have unknown capabilities until upgraded. No machine credential/hash, installation key or control token enters these results. `machine_update` edits names centrally, including offline machines. Root edits and `machine_directories` run once on the selected online compatible target; both GUIs reuse `chooseDirectories()`. Root writes canonicalize existing absolute directories and reject symbolic-link aliases. Successful browser sign-in and private-file pairing clear previous local root grants before switching the connection; pending/denied attempts preserve them. Empty native roots grant no execution access (there is no home-directory fallback); isolated portal browsing/execution retains its repository confinement, and the portal operator still controls its roots.

`machine_revoke` works for selected/offline remote machines: persist a tombstone, clear its credential hash/root metadata, remove queued calls and deselect it without starting a successor. Authentication, remote dispatch, Teams selection and lease renewal reject revoked machines. Preserve the prior lease expiry under a retired holder identity so even a fresh enrollment of the same installation must wait for handover. A host connected as a worker rejects coordinator protocol requests, so credentials it issued in its former coordinator role cannot proxy into the newly connected account. Only new browser trust or operator-local pairing can issue a new credential; a revoked credential cannot enroll. The coordinator cannot revoke itself through account operations. Revocation does not retract data an external program already received. A timeout never replays an action; GUI controls refresh the authoritative list before another deliberate attempt, and agents must inspect list/detail first. CLI and MCP share the same catalog operations and confirmation requirements.

Both Settings machine lists expose the existing `machine_teams` choice as radios, preserving the saved default. Each row adds a small Start/Stop button backed by the shared `machine_assistant` operation (`machine`, `action: start|stop`; CLI/MCP confirmation required). It forwards once through the account-bound worker protocol and invokes the ordinary `start_assistant`/`stop_assistant` dispatcher on the target, preserving ownership/lease, activity and login guards. Selecting a radio does not start the service or move the coordinator's portal/data. Start is offered only for the selected, online, stopped machine; Stop remains available for an online running machine during handover. Worker polls publish additive `assistant_phase` (`stopped`, `starting`, `running`, `stopping`); a missing report from an older worker is unknown and disables its control, and offline reports are labeled last-known. Assistant commands run concurrently with the worker's presence/status polling so Graph readiness cannot make the machine disappear. Timeout or failure refreshes the list without replaying the command. Directory/name edits survive ownership and service controls.

Child creation is a new operation, independent of activity registration and its legacy write adapters. Azure uses the enabled source catalog/read credential to discover the process's default task type, preserves parent area/iteration and assigns the child to the catalog user. Azure CLI obtains a current Entra token for Azure DevOps and the host sends it as a Bearer credential; no separate write PAT is used. GitHub uses the existing connection with Issues write access to create and link same-repository sub-issues. Each plan is marked sending before its first write and cannot be submitted twice. A GitHub issue whose parent link fails is recorded as created_unlinked with its verified URL, and further children stop. A transport/readback failure is uncertain and never retried. Existing daily snapshots and all normal evidence tools remain read-only.

The coordinator owns the child-creation ledger, including submissions from enrolled workers. After validation and a durable sending intent, creation proceeds in the background. `implementation_creation` reads its outcome and verified child links. A repeated submission returns the recorded outcome without issuing new provider writes; an uncertain outcome is never replayed.

Native agent session IDs are streamed from Codex thread events, Claude session events and OpenCode session events; they are distinct from PTA run UUIDs. An execution is recorded as started only after its CLI process starts or the shared daemon accepts its thread; its native ID becomes available as soon as the provider reports it. Successful coding ends in `done`, with a finish timestamp. Native sessions are retained for inspection. An interrupted session has no fabricated completion time. Cards and details read the session index, and shared detail shows provider, native ID, state and start/end times. Codex desktop links use the verified `codex://threads/<thread-id>` format ([official reference](https://learn.chatgpt.com/docs/reference/commands)); local CLI sessions are not assumed to exist in mobile/cloud apps. Mobile browsers offer the provider connection sheet; unsupported providers show a reason. The native opener accepts only a recorded session on that host, never an arbitrary custom URL.

Implementation sessions also attempt provider-owned mobile access by default, independently of whether PTA is a browser tab or an installed PWA. Codex starts/reuses its local Remote Control daemon and runs the thread/turn through that daemon's local WebSocket control socket (Unix socket or Windows named pipe). This gives the mobile client the same live conversation, rather than an `exec` thread omitted from the default interactive listing. Planning/request threads retain read-only, tool-less settings: shell and integration features are disabled, each configured MCP server is explicitly disabled, and the response uses the closed JSON schema. If a compatible daemon cannot be reached before creating a thread, execution can fall back to the existing CLI with mobile access marked unavailable; a started thread/turn is never replayed. Cancellation interrupts the daemon's turn as well as terminating ordinary CLI processes.

Claude uses its stream-JSON control protocol to initialize and enable Remote Control before sending the initial user turn. Its provider-returned `https://claude.ai/code/session_…` ID is stored separately from the local UUID; local IDs are never substituted into cloud URLs. After the initial result, the process can keep serving the provider's mobile client for up to two hours from connection, with at most 16 retained connections per host. Subsequent work in that provider conversation does not rewrite the completed PTA implementation run. Missing eligibility or connection failure does not authorize extra tools or fail an otherwise valid initial run. The ordinary tool-less Teams answer transports stay ephemeral and do not enable remote access.

`implementation_mobile_session` (`machine`, recorded run `id`, `action: connect|pair|close`, `confirmed: true`) routes once to the owning execution machine, rechecks the saved working directories against current roots, and reconnects completed Claude sessions without sending another model prompt. Running Claude sessions reuse their reported connection and cannot be resumed concurrently. Connection metadata is additive in run payloads and replicated session summaries. The authenticated response for Codex pairing contains only its short-lived manual code and expiry; pairing credentials are never saved in runs, the index or logs. Closing a retained Claude connection does not erase its transcript; Codex's machine-wide daemon is managed in Codex.

The mobile session sheet uses explicit user-clicked native and HTTPS links, preserving the gesture iOS requires when leaving a PWA. Claude uses its verified remote URL, the documented `claude://code/<remote-session-id>` native route and a separate web fallback. Older `exec` transcripts are resumed and, when still classified as non-interactive, forked once through the native protocol into an interactive mobile conversation; its real remote thread ID is saved separately and reused, preserving the original session. Codex exposes the connected computer, remote session ID and on-demand pairing code, then directs the user to that computer's conversation in the ChatGPT mobile app; there is no fabricated direct mobile URL for a local Codex UUID. See [Codex Remote Control commands](https://learn.chatgpt.com/docs/developer-commands), [Codex app-server protocol](https://learn.chatgpt.com/docs/app-server), [Claude Remote Control](https://code.claude.com/docs/en/remote-control), and [Claude mobile links](https://support.claude.com/en/articles/14898120-open-the-claude-mobile-app-with-a-link).

For a completed local Claude session, native PTA can use the official `claude --desktop --resume SESSION_ID` handoff on supported macOS/x64 Windows hosts. It does not move an active CLI session. Missing/unsupported desktop apps, CLI versions or subscription logins return a reason; browser/mobile sessions still need a verified remote URL. See [Claude CLI desktop handoff](https://code.claude.com/docs/en/desktop#cli-to-desktop).

### Request creation and agent history

To-Do places Create request below its filters. The form uses the selected provider: GitHub creates an issue of type Epic, while Azure offers HU/bug radios and resolves the default type from the project's Requirement/Bug category. Project/repository choices open a searchable modal sheet (a bottom sheet on phones), with the name filter first and up to three recent destinations before the remaining choices. Explicit requests enumerate all accessible projects in the enabled Azure source's configured organizations, independently of its team-project evidence catalog. GitHub runs `gh repo list --limit 100000 --json nameWithOwner,isPrivate` with the profile's GitHub CLI session, listing owned public and private repositories independently of GitHub App installation selection. Catalogs fail explicitly at their coverage bounds (1,000 Azure projects per organization or 100,000 GitHub repositories) rather than returning a truncated list. Recent choices come from this profile's latest recorded requests, deduplicated and intersected with the current catalog. The selected installed CLI/model/effort generates one bounded title/description in `llm.language`, in a retained, tool-less native session on the host. No directory selection is required: each session uses its private `implementation/requests/<run-id>` directory. The model never chooses URLs, targets, types, credentials or permissions.

Home shows the GitHub CLI installation/authentication state and verified login through the shared read-only `github_cli_status` operation. Its row refreshes directly; missing authentication explains `gh auth login` on the host. Child commands use a restricted environment, pin `github.com`, disable prompts and discard stderr. Isolated profiles pin `GH_CONFIG_DIR` to their own `home/.config/gh` and never inherit operator GitHub tokens or configuration. The existing GitHub App login, evidence and checkout flows remain separate.

Shared CLI/MCP/GUI operations are `implementation_request_catalog`, `implementation_request_start`, `implementation_request_status` and `implementation_history`. Create is explicit user authorization for this single new request, independent of reviewed child plans. Azure uses the host profile's authenticated Azure CLI session; read credentials and daily evidence adapters remain read-only. Catalog membership is checked before generation and again before writing. GitHub uses the same GitHub CLI account for explicit request creation (its token remains in host memory), requests Epic type and own assignment, and preserves the verified issue link with `needs_attention` if either property was silently dropped ([GitHub create issue contract](https://docs.github.com/en/rest/issues/issues#create-an-issue)). Azure uses the process-defined default HU/bug type, the matching To-Do assignment role and the type's description/reproduction field ([category contract](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-item-type-categories/list?view=azure-devops-rest-7.1)).

`implementation/runs.db` additionally stores `request_runs`: stable client UUID, exact confirmed submission, destination, CLI/model/effort, live native session ID, start/finish times, generated draft, durable send intent and verified created item. Repeated submissions with that UUID return the saved execution and never write again; a different submission cannot reuse the UUID. Startup marks generation interrupted and pending sends uncertain, retaining native IDs without inventing finish timestamps. Provider writes are never retried. The updater defers while generation or a send is active.

Agent history is a separate screen, reachable from To-Do and the navigation (More on phones). It merges local request executions, local implementation sessions and the coordinator's persisted session summaries from enrolled machines, showing the latest 100 within an 800 KB response budget and reporting bounded history. It shows app run ID separately from native agent session ID, model, effort, machine, state, dates and verified work item links. Opening a session reuses the existing recorded-session operation and its provider/platform limits. Request sessions run on the host serving the form; they are not dispatched to execution machines. Existing implementation runs retain their execution-machine selection.

### Azure CLI session

Explicit Azure request/child creation uses `az account get-access-token --resource 499b84ac-1321-427f-aa17-267ca6975798` on the host performing the write, with the existing catalog/read credential still confining destinations and process metadata. The resulting Entra token is held only in host memory and sent as Bearer authentication; it never reaches IPC, model processes, app logs or stored credentials. A fresh session is checked before generation/child submission and reacquired before a send. No Azure CLI write command is used, so the host retains its existing single-send/no-retry ledger. This follows the [Azure CLI Entra flow](https://learn.microsoft.com/en-us/azure/devops/cli/entra-tokens?view=azure-devops).

The shared read operation `azure_cli_status` reports `state`, `authenticated`, account `user` and `tenant`, never a token. It distinguishes missing CLI, no selected authenticated account and an account whose Azure DevOps token cannot be acquired or is expired. Authentication does not prove a project's write permissions. Home adds Azure CLI to its status rows, starts browser sign-in from an unavailable session and refreshes an authenticated session; checks run independently of the ordinary profile snapshot, once on load and every minute while Home is visible. The request form links to that status if no session is ready. The additive `begin_azure_cli_login`, `finish_azure_cli_login` and `cancel_azure_cli_login` operations (CLI `pta auth azure login|finish [--wait]|cancel`, plus `status`) run `az login --use-device-code --allow-no-subscriptions --scope 499b84ac-1321-427f-aa17-267ca6975798/.default` in that host profile, pin the configured Graph tenant, disable the terminal subscription selector and suppress account output. Both Microsoft verification prompts (`microsoft.com/devicelogin` and `login.microsoft.com/device`) are accepted with exact URL boundaries; the public IPC URL remains the former for existing clients. Only that known verification URL and a bounded user code leave the host; stderr is parsed with a bounded deadline/size for that prompt and otherwise discarded. The GUI shows the code and a link that opens Microsoft on the requesting device, polls completion, closes the dialog and refreshes the session automatically. Cancellation, host quit and a ten-minute deadline kill the CLI child. The [Azure CLI interactive flow](https://learn.microsoft.com/cli/azure/authenticate-azure-cli-interactively) handles browser authentication and MFA. Manual `az login` under the same OS user/profile remains available; a session on another execution machine is not the coordinator's session.

CLI subprocesses receive the existing restricted environment plus Azure CLI configuration and Python CA paths, never app secrets or PAT environment variables. Ordinary profiles reuse their configured/default Azure CLI directory. Isolated web profiles force `HOME`, `USERPROFILE` and `AZURE_CONFIG_DIR` under their own `home/.azure`; an inherited operator login cannot authorize their writes. CLI calls have bounded deadlines and no stdin; status/token calls discard stderr, while device login reads only its validated public verification prompt before discarding the remaining diagnostics. The retired `AZURE_IMPLEMENTATION_WRITE_TOKEN` name/store entry is preserved for compatibility, shown as retired only if already stored, and is no longer requested or read by creation flows. Graph OAuth and scopes are unchanged.
