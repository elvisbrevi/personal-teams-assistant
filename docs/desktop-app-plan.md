# Plan: aplicación de escritorio con Cargo

## Decisión de arquitectura

Empaquetar el núcleo Rust actual con **Tauri 2**: un ejecutable de escritorio para macOS y Windows, construido con `cargo tauri`, con icono de barra de menús o bandeja y dos ventanas pequeñas (Configuración y Chat de prueba). Mantener el binario CLI y Docker para los usos actuales. El código de Teams, decisiones, conocimiento y SQLite sigue en la biblioteca Rust; la GUI llama a comandos Rust de alcance limitado. No crear un segundo servidor ni duplicar el pipeline. Tauri ofrece bandeja en Rust y empaquetado `.app`/`.dmg` y Windows ([bandeja](https://v2.tauri.app/learn/system-tray/), [macOS](https://v2.tauri.app/distribute/macos-application-bundle/)).

Estructura prevista: crate actual como `core`/CLI, `desktop/src-tauri` como miembro del workspace y `desktop/src-tauri/ui` con HTML, CSS y JavaScript sencillos, incluido en el paquete de Cargo. La interfaz y la lógica son las mismas en ambos sistemas; solo cambian integración de bandeja, rutas de datos y almacén de credenciales. En macOS usar modo aplicación de barra de menús (`LSUIElement`); en Windows conservar el icono de bandeja y una ventana reabrible. Una única instancia controla el directorio de estado, respetando el lock existente.

## Experiencia de uso

1. Al abrir la app: bandeja con estado **Sin configurar / Detenido / Iniciando / Activo / Requiere atención** y acciones **Abrir configuración**, **Abrir chat de prueba**, **Iniciar/Detener asistente**, **Salir**. Cerrar una ventana la oculta; Salir detiene worker, servidor y túnel con cierre ordenado. Inicio automático con el sistema: opción desactivada por defecto.
2. Configuración separada por **Proveedores**, **Teams**, **Conocimiento** y **Red**. Mostrar para cada credencial `Disponible (entorno)`, `Disponible (archivo de secreto)`, `Guardada en el sistema` o `Falta`; no devolver ni renderizar el valor después de guardarlo. Permitir reemplazarlo y eliminarlo. Prioridad de resolución: `NAME_FILE`, variable `NAME` del proceso, almacén del sistema. No copiar automáticamente una variable de entorno al almacén.
3. Guardar valores no secretos en el directorio de configuración de usuario y SQLite/checkouts bajo datos de usuario, nunca junto al ejecutable ni en el repositorio de código. Guardar claves y tokens en Keychain de macOS o Credential Manager de Windows mediante una pequeña interfaz Rust y un backend nativo por plataforma. Generar `GRAPH_WEBHOOK_SECRET` y `STATE_ENCRYPTION_KEY` en el primer arranque de Teams; conservar la clave de estado entre actualizaciones. Migrar una instalación existente importando su clave antes de abrir la DB cifrada.
4. **Chat de prueba** puede arrancar con Jev, DeepSeek y al menos una fuente autorizada aunque Teams y su URL pública no estén configurados. Reutilizar la simulación y el contexto por sesión, sin llamadas de envío a Graph. La GUI pasa el mensaje al núcleo mediante IPC Tauri; la ruta HTTP `/test/chat` se mantiene solo para el CLI y se separa del router público. El túnel expone únicamente los callbacks de Graph. El usuario elige qué fuentes probar; esta autorización local no modifica `allowed_conversations` de Teams ni requiere `*`.
5. En Teams, la configuración muestra organización, cuenta conectada, permisos efectivos, `dry_run` y estado de suscripciones. Primer inicio siempre en `dry_run`; pasar a envío real exige una acción explícita en Configuración. Cada edición se valida antes de persistir y, si el servicio está activo, provoca un reinicio controlado con el mismo SQLite.

Una app abierta desde Finder o Explorer no hereda necesariamente las variables definidas solo en el perfil de la shell. La pantalla muestra únicamente el entorno **del proceso** y el almacén del sistema; para reutilizar valores de una shell, iniciar desde ella una vez o importarlos explícitamente. No ejecutar archivos de perfil para descubrir secretos ([nota de empaquetado de Tauri](https://v2.tauri.app/distribute/macos-application-bundle/)).

## Teams y red

Para la app de escritorio, cambiar el OAuth de Teams de cliente confidencial con secreto y callback en el túnel a cliente público de escritorio, navegador del sistema, PKCE y callback loopback. Esto quita `ENTRA_CLIENT_SECRET` de la instalación de escritorio; el CLI conserva el flujo actual durante la transición. **La migración de la instalación actual conserva su client ID y el conjunto exacto de permisos Graph ya concedidos.** Solo se añade la plataforma **Mobile and desktop** con `http://localhost` al mismo registro Entra; la GUI no solicita scopes nuevos ni activa funciones que los requieran. Se mantienen comprobación de `/me` y tokens protegidos. Puede ser necesario volver a iniciar sesión al pasar al nuevo flujo, pero no se plantea un nuevo consentimiento. Si Microsoft muestra una solicitud de consentimiento inesperada, detener la migración de Teams y revisar la causa antes de aceptarla ([Microsoft: aplicaciones de escritorio](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-app-configuration), [consentimiento existente](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/user-admin-consent-overview)).

### Acceso para personas de otras organizaciones

El registro Entra existente ya admite cuentas de trabajo o escuela de otras organizaciones y sigue siendo el predeterminado para tu perfil migrado. Conserva su client ID y **exactamente los permisos Graph actuales**, sin crear otro registro ni solicitar un consentimiento nuevo para tu cuenta. Cada organización aplica su propia política de consentimiento. La conexión usa `/organizations`, identifica y verifica la organización y el usuario conectados y usa credenciales delegadas de esa persona. No incluir tu tenant ni `user_id` como valores predeterminados del binario público. El perfil local debe separar configuración, mapa de fuentes, SQLite, tokens, suscripciones y repositorios por `tenant_id + user_id + client_id`, y detener el servicio anterior antes de cambiar de perfil; ese aislamiento aún requiere una prueba real ([Microsoft: aplicaciones multitenant](https://learn.microsoft.com/en-us/entra/identity-platform/single-and-multi-tenant-apps)).

Flujo en la GUI: **Conectar cuenta de trabajo → revisar permisos → iniciar sesión**. Si la política permite consentimiento de usuario, completar conexión. Si aparece **Aprobación necesaria**, dejar Teams en estado `Pendiente de administrador` y guiar a la persona para que envíe la justificación en el propio diálogo de Microsoft; la organización decide y Microsoft notifica el resultado cuando tiene habilitado su flujo de solicitudes. Si ese flujo no está habilitado, mostrar instrucciones para contactar al administrador, con el nombre, editor, client ID y permisos solicitados. Tras la aprobación, ofrecer **Reintentar conexión** y comprobar acceso real a Graph; no inferir aprobación por el cierre del navegador. Un administrador puede limitar los usuarios autorizados aunque haya consentimiento para toda la organización ([Microsoft: consentimiento y solicitudes](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/user-admin-consent-overview), [asignación de usuarios](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/what-is-application-management)).

Para adopción pública, configurar dominio y editor verificado del registro existente si se cumplen sus requisitos; un editor sin verificar puede topar con restricciones de consentimiento. Ofrecer además **Usar el registro Entra de mi organización** para organizaciones que solo acepten apps propias: su administrador proporciona el client ID público y registra `http://localhost`; nunca se solicita un secreto de cliente para el modo escritorio. El perfil migrado conserva su registro actual salvo que la persona elija otro. Ninguno de esos caminos concede acceso sin las políticas y el consentimiento del tenant ([Microsoft: editor verificado](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview)).

La recepción de mensajes sigue exigiendo un **endpoint HTTPS público y estable** para las notificaciones de Graph, aun cuando OAuth entre por loopback ([Microsoft: webhooks](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks)). La GUI configura una URL propia o un túnel con hostname estable y supervisa el conector correspondiente. Quick Tunnel y la modificación automática de redirect URI de `scripts/local.py` quedan como desarrollo; no son la ruta normal de escritorio. Mostrar explícitamente que apagar el equipo o el túnel detiene la recepción. Nunca abrir el puerto local a toda la red por defecto.

## Repositorios de conocimiento

La estructura `KnowledgeMap.repositories` ya admite varios checkouts. Añadir un gestor en la GUI para **agregar, editar y quitar** repositorios locales o remotos; al quitar uno, deshabilitar o reasignar sus recursos antes de guardar. Quitar de la lista no borra el directorio local. Validar checkout Git, ruta canónica y límites de lectura existentes. Un repositorio agregado no se vuelve fuente automáticamente: ofrecer selección de archivos admitidos, descriptor (`id`, descripción, temas) y audiencia. Las fuentes nuevas empiezan deshabilitadas para Teams hasta declarar conversación y autorización de procesamiento externo.

Para repositorios privados de GitHub: primero aceptar un checkout local ya autenticado. Si hay que conectar una cuenta, usar **GitHub App con device flow** y permiso `Contents: read`, instalación limitada a los repositorios elegidos; no pedir el scope amplio `repo` de una OAuth App. Guardar tokens en el almacén del sistema, renovar/revocar según el flujo de GitHub y pasar credenciales al proceso Git sin incluirlas en URL, argumentos, logs ni configuración. El catálogo muestra solo repositorios accesibles; clonar/actualizar en el directorio de datos con avance y errores sin credenciales. La instalación de la GitHub App puede requerir aprobación de una organización ([device flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), [repositorios seleccionados](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party)). Un client ID de GitHub App puede ir en el binario; ninguna clave privada o client secret.

## Publicación segura del repositorio

- Antes de hacerlo público, auditar **árbol actual, todas las ramas/tags e historial Git** con un detector de secretos y revisión manual de nombres, correos, dominios, rutas y datos de clientes. La revisión preliminar ya encontró el nombre personal en `static/test.html` y tests, y referencias al checkout privado en ejemplos/documentación. Sustituirlos por ejemplos neutros. `.gitignore` protege archivos nuevos, pero no sanea commits anteriores.
- Si alguna credencial estuvo en Git, revocarla/rotarla antes de publicar; reescribir historial solo después, coordinando a quienes tengan clones. No declarar el repositorio seguro solo porque el último commit esté limpio.
- Publicar únicamente ejemplos sintéticos. El bundle no contiene `config.toml`, `knowledge-map.toml`, `.env`, SQLite, logs, checkouts, tokens, certificados de firma ni credenciales de CI. Comprobar el contenido real de `.app`, `.dmg` e instalador Windows y hacer un arranque limpio sin secretos.
- Limitar comandos IPC a operaciones explícitas; no exponer APIs genéricas de shell o filesystem al WebView. Mantener CSP estricta y separar el servidor público de la GUI. Logs sin prompts, respuestas, tokens ni rutas privadas completas; los mensajes de error de proveedores se traducen a estados seguros.

## Orden de implementación y criterios de cierre

| Fase | Entrega verificable |
| --- | --- |
| 1. Núcleo reutilizable | Extraer `serve/check/simulate` de `main.rs`, separar requisitos de Chat y Teams y routers público/local. Tests del chat con recursos privados sin `*`; ningún POST a Graph. CLI actual sigue funcionando. |
| 2. Configuración y secretos | Esquema versionado, migración de TOML/DB, validación antes de guardar, resolución entorno/archivo/almacén; tests de precedencia, redacción y clave persistente. |
| 3. Escritorio común | Tauri, menú, ventanas, estado real y ciclo iniciar/detener; pruebas en macOS del cierre, segundo inicio y relanzamiento. Compilación Windows en CI desde esta fase. |
| 4. Fuentes y GitHub | CRUD de repositorios y recursos, selección de archivos, checkout local y login GitHub App opcional; tests de acceso, revocación, ruta y desactivación al quitar. |
| 5. Teams y distribución | Migrar tu perfil con el mismo client ID y sin scopes nuevos; verificar que los permisos ya concedidos bastan. El registro existente ya admite otras organizaciones y la redirección de escritorio; falta probar solicitud de consentimiento en un tenant ajeno y otro que exija aprobación. OAuth de escritorio y túnel local están implementados; faltan una URL estable real, prueba de suscripciones, firma/notarización de `.app`/`.dmg` e instalador Windows. Pruebas críticas manuales Windows antes de anunciar soporte estable allí. |
| 6. Apertura del código | Auditoría de historial, sustitución de datos personales, escaneo de artefactos y guía pública de instalación/privacidad. Publicar solo después de superar esa revisión. |

La primera versión distribuible puede usar repositorios locales y chat de prueba mientras se completa GitHub login y Teams. No debe anunciarse como integración Teams lista hasta contar con URL HTTPS estable, registro Entra aprobado y pruebas de suscripciones.

Para publicar en crates.io, exportar primero un snapshot limpio sin historial privado y publicar `personal-teams-assistant` antes de `personal-teams-desktop`. El crate de escritorio incluye `ui`, iconos y configuración de Tauri. `tauri-build` genera `gen/schemas` dentro del árbol extraído durante la verificación de `cargo publish`; por ello el segundo paquete requiere `--no-verify` después de compilar y escanear el `.crate` extraído por separado.
